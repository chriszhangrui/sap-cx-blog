做过 OData 服务的人多半见过这个场景。Employee 表上有一条记录，前端两个浏览器标签同时打开，一个改邮箱，一个改姓名，两个 PATCH 各自走自己的网络包发到服务端，服务端按时间顺序乖乖处理，后到的那次写入把先到的那次覆盖掉。前端没人收到任何提示，数据库里只剩一份，丢失的那条改动彻底没了痕迹——这就是 lost update。

真正棘手的不是这个错误本身，而是它**沉默**。两个用户都会以为自己保存成功了，业务方下个月对账时才发现某条记录的状态对不上，回头来追责，日志里却看不到任何冲突。CAP Java 已经把这件事内置成框架能力，但很多项目并没有启用，原因往往不是没听说，而是没意识到这是个必须主动开的开关。

## 悲观锁为什么不适合 Web 应用

第一反应是上锁。Alice 打开记录的那一刻就把这条记录锁住，Bob 想改就先排队，等 Alice 提交完再放行。逻辑无懈可击，放在 client/server 时代的 Oracle Forms 上跑了二十年都没出过事，但放到 Web 上立刻露馅。

原因很简单：Web 用户不会"提交完就走"。他们打开表单后会去喝杯咖啡、接个电话、切到其他系统看一眼数据再回来，整个编辑窗口可能持续半小时甚至更久。这期间这条记录被独占着，其他任何人都改不了。如果用户直接关掉浏览器走人，数据库里那把锁还得靠超时机制自己释放。在并发量稍微高一点的系统里，锁等待会迅速变成头号性能瓶颈。

所以行业的共识早就转向了乐观锁——读的时候不锁任何东西，所有人都可以并发读、并发改，但写入的那一刻必须证明你拿到的是最新版本。

## HTTP 早就给了答案：ETag + If-Match

这件事其实不需要 SAP 自己发明轮子。HTTP 协议在 RFC 7232 里早就定义了 ETag 这个机制。服务端在响应里塞一个 ETag 头，相当于这条资源当前版本的指纹；客户端做修改前发起 PATCH 时把上次拿到的 ETag 放进 If-Match 头里。服务端比对两个值，一致就放行并生成新的 ETag，不一致就直接返回 412 Precondition Failed。

这套约定的好处是它完全无状态。服务端不需要为每个用户记任何"谁正在编辑"的会话信息，所有冲突检测都靠请求里那一行头部完成。在 BTP 这种多租户、按 pod 横向扩缩的运行环境里，无状态是必须的——任何依赖会话粘连的方案都跑不远。

> OData 协议在 v2 时代就已经把 ETag 写进规范里。CAP Java 做的事是把 OData 实现这一层和 CDS 数据模型这一层串起来：你只需要在 CDS 里指出"哪个字段是版本号"，剩下的解析、对比、响应都不用你管。

## CDS 模型里的那一行注解

具体到代码层面，CAP Java 给开发者留的接口窄得不能再窄。一个 Employee entity 加上 managed 切面后会自带 createdAt、createdBy、modifiedAt、modifiedBy 四个字段。你要做的只是把 modifiedAt 标记为 ETag 字段：

```cds
entity Employees : managed {
  key ID    : UUID;
  name      : String;
  email     : String;
}

annotate Employees with {
  modifiedAt @odata.etag;
}
```

就这一行。从这一刻起，所有 OData 响应里都会带上 ETag 头，所有 PATCH/PUT/DELETE 请求都必须携带 If-Match，框架在写入前会自动比对当前数据库里的 modifiedAt 和请求带过来的值，不匹配直接 412。Java 业务代码不用改，自定义 handler 也不用动。

实际跑一下能更直观。客户端先 GET 这条记录：

```http
HTTP/1.1 200 OK
Content-Type: application/json
ETag: W/"2026-05-25T06:55:44.400909Z"

{
  "ID": "...",
  "name": "Alice Wong",
  "email": "alice@example.com",
  "modifiedAt": "2026-05-25T06:55:44.400909Z"
}
```

Alice 拿着这个 ETag 发起 PATCH：

```http
PATCH /odata/v4/hr/Employees(...) HTTP/1.1
If-Match: W/"2026-05-25T06:55:44.400909Z"
Content-Type: application/json

{ "email": "alice.wong@example.com" }

→ 200 OK
  ETag: W/"2026-05-25T07:07:15.691711Z"
```

Bob 此时拿的还是 06:55:44 那个老版本，他的 PATCH 一发出去就吃到 412：

```http
PATCH /odata/v4/hr/Employees(...) HTTP/1.1
If-Match: W/"2026-05-25T06:55:44.400909Z"
Content-Type: application/json

{ "name": "Robert Wong" }

→ 412 Precondition Failed
```

## 412 不是错误，是合约

这是大多数团队第一次接触 ETag 时容易卡住的地方——前端拿到 412 之后该怎么办？

把 412 当成 500 这类系统错误处理是错的。412 是 HTTP 协议层面的明确语义：你这次请求的前置条件没满足。它在告诉你的不是"系统出问题了"，而是"这条数据已经被别人改过了，你看到的版本已经过时"。前端正确的反应是重新 GET 这条记录，把新版本的字段展示给用户，让用户决定是合并自己的修改还是放弃，然后用新拿到的 ETag 再发一次 PATCH。

Fiori Elements 在这点上做得很好——它内置了 412 的处理路径，UI 会自动提示用户记录已被其他人修改并刷新表单。但很多自研前端用 React、Vue 直接调 OData 时会忽略这个分支，结果就是用户看到一个莫名其妙的弹窗或者干脆什么都没发生，体验比 lost update 还糟。

> 把 412 当成业务流程的一部分来设计，而不是当成需要"屏蔽"的异常。这是用 ETag 机制能不能落地的关键判断。

## 放进 BTP 整体架构里看

这件事单独看是 CAP Java 的一个小特性，放到 BTP 的扩展架构里看就是另一回事了。在侧扩展（side-by-side extension）模式下，自研应用普遍跑在 Cloud Foundry 或 Kyma 上，前端是 Fiori 或自研 SPA，后端通过 Destination 调 S/4HANA 的 API 做主数据，自己再拉一份在 HANA Cloud 或者 PostgreSQL 里维护扩展属性。

这个架构最容易在并发上出问题的不是 S/4 那一端——SAP 系统自己有强一致性的事务模型——而是扩展应用自己维护的那张表。出海企业经常会在 BTP 上写一个"客户偏好""审批意见""自定义状态"之类的表，多个角色（区域销售、总部客服、海外运营）会从不同入口同时改同一条记录。如果这张表没启用 ETag，并发问题随时会出现，而且因为它分散在各个扩展应用里，集中排查极其困难。

放在跨国制造和跨境电商的实施场景下，这件事和 OMF 把订单先按下暂停键、Sales Cloud V2 让你看见 API 的 429 红线一样，都属于"框架已经替你想好了，但你得主动用"的那一类设计。CAP Java 的 ETag 不是一个新功能，而是 BTP 上做扩展应用必须默认开的能力之一。

## 什么样的项目应该开，什么时候不要碰

- 多用户、多角色并发编辑同一类记录的扩展应用，ETag 是默认必须打开的能力。Employee、Customer、Order Header 这类核心表尤其要加。
- 纯展示型的应用、单用户作业系统、批处理产生的只读视图，可以不开。给只读资源加 ETag 没坏处但意义不大。
- 高频写入的事件类记录（日志、审计流水、IoT 上行数据）不要用 ETag。这类场景写入是单向的、append-only 的，用版本号反而会引入不必要的失败重试。
- 前端必须配套实现 412 的回退路径。没有 UI 提示和重试逻辑的话，用户拿到 412 只会觉得"系统坏了"，比 lost update 还糟。
- 跨服务调用时要把 If-Match 头一路透传。BTP 上常见的 Approuter → CAP backend → 内部微服务这条链路，中间任何一段把 If-Match 吃掉，乐观锁就形同虚设。

这种"只需要一行注解"的设计有它独特的价值——它把一个分布式系统里非常隐蔽的数据一致性问题，变成了一个开发者在画 CDS 模型时必须面对的明确选择。你可以选择不加 @odata.etag，但你不能假装不知道并发更新这件事。

对于在 BTP 上做扩展开发的团队，这件事值得在项目启动时就拉出来过一遍代码评审标准——所有 managed entity 的 modifiedAt 字段，是否需要标记 @odata.etag，以及前端是否实现了 412 的处理路径。这两个问题的答案，能省掉后期生产环境里大半的"灵异数据问题"。
