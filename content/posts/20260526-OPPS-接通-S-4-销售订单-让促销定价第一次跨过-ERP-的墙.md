做过零售项目的都遇过这道题：消费者在小程序看到的"满 200 减 30"，到门店收银台扫码出来是原价；同一张订单要换货走 OMS 的时候，价格又对不上了。问题不在哪个系统的促销规则没配好——问题在每个系统都有自己一套定价逻辑。

Cloud ERP 2602 版本里有一项被很多人略过的更新——SAP Omnichannel Promotion Pricing Service（OPPS，全渠道促销定价服务）正式接入 S/4 销售订单。它解的不是"加一个新功能"，而是把促销定价从"应用内逻辑"抽成"跨渠道服务"这件事，第一次在 ERP 这一侧落地了。

## 先说清楚 OPPS 是什么

OPPS 不是 2602 才有的东西。它本身是 SAP 零售生态里早就在用的一个独立服务——POS 那侧（Customer Activity Repository / CAR 体系下的 Omnichannel Article Repository）已经在用 OPPS 算门店促销价；电商侧 Commerce Cloud 调用 OPPS 服务计算购物车折扣也已经有几年了。

它的接口很纯粹——输入是"客户上下文 + 商品篮子"，输出是"促销结果 + 价格调整明细"。规则引擎本身支持的促销类型，覆盖到 Bonus Buy（买 A 送 B）、阶梯折扣、阈值奖励、会员价、优惠券、组合促销这些 ERP 原生定价过程做不动的场景。

所以 2602 这次的关键不是"OPPS 新增了能力"，而是 S/4 销售订单这条链路——以前一直走 ERP 自有的定价过程（Pricing Procedure / Condition Technique）——开始在创建订单时调用 OPPS。

## 为什么以前不接，现在要接

ERP 的定价过程是 R/3 时代留下来的设计。它擅长合同价、阶梯价、客户/物料维度的折扣，本质是"按条件查询价格记录表"。但全渠道时代的促销越来越多是这种形态："凡是会员等级 ≥ Gold 且购物车里同时有 SKU-A 和 SKU-B，B 算半价"——这种规则用 condition technique 写出来非常痛苦，而且规则一变就要改主数据。

过去的妥协方案是：跨渠道促销规则配在 CAR 里，POS 和电商用 OPPS 算价；S/4 销售订单走自己一套——只要不是涉及大金额订单，"价差"就靠运营手动拉平。

这次接通之后，销售订单创建时直接调 OPPS。所有渠道——POS、电商、店内销售订单——拿到的促销结果是同一份。表面上是"销售订单接了一个新服务"，本质是 ERP 把"价格计算"这个能力让渡了一部分给一个外部服务。这在 SAP ERP 的演进里是个比较少见的方向。

▲ OPPS 从「POS / 电商专享的服务」变成「跨 POS、电商、S/4 销售订单的共享规则池」

## 接通之后，订单流的几个细节

文档里给出的初版集成有几个值得注意的点：

- **调用时机**：销售订单（SO）创建过程中触发 OPPS，OPPS 返回促销结果后，系统把折扣 / 赠品作为订单行项目自动写回。这是同步调用——价格依赖促销返回结果，订单不能在 OPPS 之前定。
- **覆盖范围**：2602 是"foundational integration"。SAP 在文档里明确说了这一版只是底座，未来 release 会逐步扩展功能边界。这意味着初期能用的促销类型，仍然以 Bonus Buy 这种 ERP 原生定价做不动的场景为主。
- **规则一致性**：因为 OPPS 也是 POS 和电商在用的服务，规则只配一份。运营同事不用再在三个系统里维护三套促销活动。
- **失败处理**：原文没展开，但从架构上能看出来——OPPS 调用失败时销售订单的 fallback 路径是个绕不开的设计点。同步调用 + ERP 不能停服 = 必须有降级开关。

调用形态大致是这样（伪代码示意，参数以原文为准）：

```http
POST /opps/v1/promotion-determination
{
  "customer": { "id": "C001", "loyaltyTier": "Gold" },
  "context":  { "channel": "STORE_SO", "businessDate": "2026-02-15" },
  "items": [
    { "article": "SKU-A", "qty": 2, "listPrice": 100.00 },
    { "article": "SKU-B", "qty": 1, "listPrice":  80.00 }
  ]
}

→ 200 OK
{
  "promotions": [
    { "type": "BONUS_BUY", "trigger": "SKU-A x2",
      "effect": { "article": "SKU-B", "discountPct": 50 } }
  ],
  "priceAdjustments": [ ... ]
}
```

## 其它三个不该被忽略的更新

OPPS 是 2602 release for Retail 里架构含义最大的一个，但其它三个改动也有看头：

**1. Joule 进入 Assortment Module Management**

品类规划这个动作以前对工具的依赖很重——计划员要在多个 Fiori 应用之间跳转，理解 assortment module 的层级、有效期、产品-门店匹配关系。2602 把 Joule 放在这条链路上，做的不是"自动决策"，而是"自然语言到系统操作"的翻译："给华南区门店在 3 月加一个春装品类模块"——Joule 解析意图，触发对应的 assortment 创建动作。

它没改业务逻辑——底层 module 模型还是原来那一套。改的是"操作员要不要懂系统结构"这件事。这种轻量化的 AI 嵌入，比那种"AI 自动决定要补什么货"的口号更实用。

**2. OSTA 实时库存**

传统流程里 POS 销售要批量过账才回 ERP，门店白天看到的库存数总是滞后的。2602 让 SAP Cloud ERP 直接读 SAP Omnichannel Sales Transfer and Audit（OSTA，全渠道销售转储与审计组件）里那些"还没过账"的销售记录——查可用量、做转移、做盘点的时候，看到的库存是"减去当天已卖、未过账"的真实数。

这事在零售落地里非常实际。出海品牌在欧洲、东南亚自营门店做实时调拨决策、做"线上下单门店发货"的就近发货判断，库存数对不对几乎是 SLA 的一部分。

**3. 店内销售订单的预付款流**

家具、家电、奢侈品类型的零售场景里，"先收订金、到货付尾款"是默认操作。2602 的 Manage In-Store Sales Orders 应用里直接支持定金录入——固定额或百分比都行，系统自动按交付式开票计划组织订单。一键生成 Down Payment Request 发票，店员开单和收款一气呵成。

这个特性听起来不性感，但它意味着以前要靠定制开发或 BTP 扩展去实现的店内财务流，现在标准产品就能跑——典型的把"项目题"变回"产品题"的演进路径。

## 和 CX 那一侧的几个连接点

S/4 Retail 在 2026 起划进 CX 产品组合，这个调整不是组织架构层面的合并报表——它对应的是产品形态在往一处走：

- **促销规则** ↔ Engagement Cloud（原 Emarsys）：营销侧定义的人群-促销联动，最终需要落到 OPPS 的规则池里。OPPS 接通 S/4 SO 之后，营销活动的覆盖范围从"小程序+APP"扩展到了"包括店内大单的所有渠道"。
- **商品 / 库存** ↔ Commerce Cloud：Article Master 主数据继续在 S/4 这一侧维护，电商侧通过 SAP CAR 或直接通过 API 同步——OSTA 实时库存这个能力补齐之后，电商展示的"门店可取"准确度会更高。
- **订单 / 退货** ↔ OMS（Order Management Foundation）：店内销售订单和电商订单的差异在缩小。OPPS 把价格统一了，OMS 的订单编排不再被"渠道间价差"打断。
- **客户画像** ↔ CDP（在 BDC 里）：OSTA 提供的逐笔销售数据是 CDP 重要的事件源——OSTA 实时化对 CDP 的画像即时性是顺带受益。

## 什么样的项目用得上，什么时候要绕开

OPPS 接通销售订单这条路径，**明确适合的**是这样的客户：

- 出海品牌做**多渠道（POS + 电商 + 大客户 / B2B 订单）**的零售业务，已经或计划用 SAP Cloud ERP 做核心 ERP；
- 有 **Bonus Buy、阈值促销、会员叠加**这类 ERP 定价过程做不动的场景；
- 已经在用 SAP CAR 或者准备引入 SAP Engagement Cloud（Emarsys）做营销，希望规则只维护一份。

**暂时要绕开**的情况：

- **2602 是 foundational integration**——首发版本覆盖的促销类型有限，复杂场景（多重折扣叠加、跨期累计返利等）建议跟 SAP 确认 roadmap 再上；
- 私有云老版本：这个能力是 Cloud ERP（公有云）路线上的，本地部署的 S/4HANA 私有云客户得跟产品确认；
- 纯内贸品牌：Cloud ERP for Retail 没有国内数据中心，落地路径只能是出海主体或在华外资公司用海外租户。

## 最后一个判断

OPPS 接通销售订单这件事在产品层面看是一个集成点，往大了看是 SAP 在做"促销定价 = 跨渠道服务"这件事的底座收尾。把这块拼图补上之后，再回看整套 CX 加 S/4 Retail 的图景——POS、电商、店内销售订单走同一套 OPPS；Article Master 在 S/4 维护、跨渠道分发；OSTA 提供实时事件流；OMS 编排订单；Engagement Cloud 触达消费者；CLM 把积分写回——这套链路第一次像一套"装得起来"的东西，而不是七八个产品的拼凑。

零售客户接下来三年最值得关注的不是"哪个产品又加了 AI"，是这种基础服务的归位——它们决定了你最终能不能把渠道一致性从一句口号变成一个可以被审计的实现。
