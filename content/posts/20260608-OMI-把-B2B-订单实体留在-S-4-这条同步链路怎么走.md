做 SAP Commerce Cloud B2B 项目的人都遇到过这个问题：客户在 storefront 上点了"加入购物车"，那一刻系统应该让谁去算价格？让谁去校验信用额度？让谁去决定这笔订单能不能下？

一种主流答案是把订单先收在 Commerce 里、走 OMS（Order Management Services）做 sourcing 和 orchestration、再异步落给 S/4。这是过去十年大部分零售客户的做法，订单中枢在 OMS，ERP 只负责"接住已经做完决策的订单"。

但 B2B 这条线从来不是这么走的。荷兰 SI 厂 Acorel 最近的一篇技术博客（2025 年 10 月）讲清楚了 SAP 给 B2B 准备的另一条路径——OMI（Order Management Integration Module），这条路径反过来：订单实体留在 S/4，Commerce Cloud 只做前端渲染层，每一次浏览、加车、结账都在同步调用 ERP 的标准 API。

## 为什么 B2B 不能照搬 B2C 的订单架构

B2C 的订单决策相对简单——商品有标价，库存按 SKU 实时扣减，支付当场完成。Commerce 自己的 OMS 已经够用，再异步推一份到 ERP 做财务确认就行。

B2B 的复杂度不在订单本身，在订单背后那一摞数据：每个 B2B Unit 有自己的合同价、阶梯价、佣金条款；客户有信用额度，超额必须挡单；产品对不同 Unit 有不同的可见性（Listing Exclusion）；交付要按 schedule line 拆，发票要按 incoterms 算税。

这些规则全部沉在 S/4 里。要么把它们复制一份到 Commerce（数据失同步是必然的），要么让 Commerce 每次都去问 S/4。OMI 选择了后者。

这背后是一个架构判断：**订单的"业务实体"应该和"业务规则"放在同一层**。如果定价规则在 ERP，那订单就别在 Commerce 落地，让它直接写到 ERP 里去。Commerce 不再持有订单的状态机，只负责把 ERP 的状态翻译成 storefront 上的那几个页面。

## 四次同步调用：订单生命周期里 S/4 何时被叫醒

把 OMI 的链路拆开来看，B2B 用户从登录到下单的整个旅程，Commerce Cloud 一共要打四次 S/4 的同步 API：

- **浏览商品**：调用 PIQ_CALCULATE 拿实时单价/净价，按当前登录的 B2B Unit 取合同价；
- **加入购物车**：调用 API_SALES_ORDER_SIMULATE_SRV，把 Sold-to / Ship-to / Product / Quantity 推过去，让 S/4 模拟一笔订单，返回含税总价、运费、信用额度校验结果；
- **提交订单**：通过 IDoc 把订单出站到 S/4，订单实体在 ERP 里创建，进入标准 O2C 流程；
- **售后查询**：API_SALES_ORDER_SRV / API_OUTBOUND_DELIVERY_SRV / API_BILLING_DOCUMENT_SRV 分别拉订单、发货、发票详情，让 storefront 渲染出最新状态。

关键的一刀切在加车那一步。传统 Commerce 的做法是先用本地缓存的价格表估一下，让用户先看到结果，下单时再去 ERP 校准——但这意味着用户看到的总价和最终扣款很可能不一致。

OMI 直接把这一步交给 ERP。每次加车、改数量都打一次 API_SALES_ORDER_SIMULATE_SRV。延迟会增加，但代价换来的是：用户看到的价格就是发票上印的价格，开票期的价格争议可以从根上消掉。对 B2B 大宗订单来说，这笔账值。

## SIMULATE 这一步具体在传什么

API_SALES_ORDER_SIMULATE_SRV 这个标准 OData 服务承担了 OMI 链路的核心负载。一个简化的请求大概长这样：

```
POST /sap/opu/odata/sap/API_SALES_ORDER_SIMULATE_SRV/A_SalesOrderSimulation
{
  "SalesOrderType": "OR",
  "SalesOrganization": "1010",
  "DistributionChannel": "10",
  "OrganizationDivision": "00",
  "SoldToParty": "B2B_UNIT_001",
  "ShipToParty": "B2B_SHIP_001",
  "to_Item": [
    {
      "Material": "MAT-A",
      "RequestedQuantity": "120",
      "RequestedQuantityUnit": "PC"
    }
  ]
}
```

S/4 会把整套定价过程跑一遍：基础价格条件、客户折扣、阶梯价、税码、运费——这些原本在 ERP 里跑给销售员开单用的逻辑，现在直接服务于 storefront。返回里除了金额，还有 Schedule Line（可承诺日期）和 Credit Status（信用额度）。如果客户额度不够，OMI 直接把"提交订单"按钮置灰。

这条链路必须经过 BTP 上的 Cloud Integration（CPI）。Commerce Cloud 不直接调 S/4，而是把请求扔给 CPI 上的 iFlow，由 iFlow 做协议转换、错误重试、消息归档。这也是为什么实施 OMI 的项目，BTP 必须先到位——没有 CPI，整条 OMI 链路就跑不起来。

## 异步那一半：哪些数据是不变的

不是所有调用都要走同步。OMI 同时定义了几条异步 IDoc 通道，按计划任务批量复制相对静态的数据：

- 产品主数据（Material Master）走标准 IDoc，按全量+增量定时同步到 Commerce；
- B2B Unit（Sold-to Party 主数据）也走 IDoc，新客户开户时单条触发；
- 自定义的目录、分类、层级（Catalog / Category / Hierarchy）按业务节奏同步，标准方案没覆盖的部分用 CPI 客制 iFlow 补。

区分原则很清晰：**变化频次低、不参与价格/信用决策的数据走异步；任何会影响一笔订单金额或可承诺数量的数据走同步**。把这条边界画清楚，OMI 的性能模型才有意义。

## 放弃了什么：OMI 不适合的场景

这套架构有它清楚的边界。每次加车、改数量、变收货地址都要打 S/4，意味着两件事：

- 同步调用的延迟会传到用户体验上。如果 S/4 的定价过程涉及大量条件类型（CPI Conditions），单次模拟可能要几百毫秒甚至更长；
- Commerce Cloud 的请求量直接打到 ERP，并发模型由 ERP 的 dialog work process 决定。零售场景的"双 11"洪峰显然不适合；
- 多渠道编排能力是缺位的。OMI 不做 sourcing、不做分仓、不做 ship-from-store——这些是 OMS 那条线干的活，OMI 没碰。

所以如果项目同时有线上零售大流量、需要 ship-from-store 或 marketplace 的多源履约编排，OMI 就不是合适的方案——这种时候应该往 SAP Order Management Services 那条线走，让 OMS 来做订单中枢，S/4 只承接 fulfilled 之后的财务流。Acorel 这篇文章的隐含前提是 B2B 中大单、合同价、信用额度场景，没有零售那种尖峰流量。

## 什么样的出海项目可以选 OMI

对于做 B2B 出海的中国企业——比如把工业设备、零部件、原材料卖给欧洲、东南亚的代理商和直接客户——OMI 是一个被低估的方案。它的优势在于实施成本相对可控：标准 API 都是 SAP 维护的，不需要自己造一套订单引擎；信用额度、合同定价这些 B2B 痛点在 ERP 里已经有现成逻辑，不必在 Commerce 层重复实现。

实施判断的几条线：

- **看现有 S/4 的 O2C 是否健康**。OMI 的本质是把 ERP 的订单流复制到 storefront 上，ERP 流程本身有问题，OMI 项目只会把问题放大；
- **BTP 落位要先于 OMI**。Cloud Integration 是必备件，没 CPI 这条链路跑不起来。海外区域的 BTP 数据中心选型（欧洲优先 Frankfurt 或 Amsterdam）也要提前规划；
- **评估订单单据并发**。如果业务高峰是几百单/分钟，ERP 有压力；如果是几千单/秒，OMI 不是合适方案；
- **看是否需要多源履约**。要 ship-from-store、要分仓、要 marketplace，得加上 OMS；纯仓发、ERP 单仓体系，OMI 自己就够。

OMI 这条路走通了之后，团队会发现一个反直觉的好处：Commerce Cloud 的代码量明显减少。原本要在 Commerce 里维护的定价覆盖、税务计算、信用额度规则全部消失了，只剩下 storefront 渲染和 API 编排。这对 SI 团队的长期维护成本是真正利好。

代价是项目前期对 S/4 标准 API 的熟悉度要求陡然上升——以前在 Commerce 里写一个定价 hook 就解决的事，现在要在 ERP 那边把对应的条件类型配出来。这是一种技术能力的迁移，不是消失。
