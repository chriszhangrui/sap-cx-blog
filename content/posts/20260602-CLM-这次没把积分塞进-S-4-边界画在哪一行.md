在 S/4HANA Cloud Private Edition 项目里有一个绕不开的话题：会员积分到底放哪。

放在 ERP 里？销售订单创建时同步算一遍，事务一致，看起来天经地义。但每两年一次的 S/4 大版本升级，会把这一段逻辑拖进升级回归测试，节奏变成"业务想加一个新规则，先等下一个升级窗口"。

放在外面？又有人会问：那 Gift Card 折扣呢？这玩意儿必须在订单保存前生效，移出去怎么保证一致性？

SAP 在 4 月底放出的一篇 Clean Core 演示场景里，把这条边界画清楚了——不是把所有忠诚度逻辑一股脑塞到 BTP，也不是全留在核心，而是按"能不能延后再算"分两半。

## 一个被拆成两半的场景

原文给出的业务场景非常具体：一家公司有两套并行的奖励机制。

- Gift Card：销售订单创建时直接抵扣金额，立即生效
- Loyalty Program：销售订单创建后，按客户当前所在的会员等级，把订单金额的某个百分比累计成积分
- 会员等级可以申请升级，升级前需要管理员审批

如果按经典 ABAP 客制化的思路，这套东西大概率会被打包成：Gift Card 用 WebDynpro 维护，VA01 加 User Exit 接入礼品卡校验，积分用 Module Pool 程序，等级升级走 Classic Workflow。一个项目下来，S/4 核心被刻满了私货。

这次 SAP 的做法是把这四件事拆成两组：和销售订单一致性强耦合的留在核心，能解耦的全部移出去。

## 哪些必须留在核心：on-stack 的两条理由

Gift Card 这一组留在 S/4 内部，用的是 RAP（ABAP RESTful Application Programming Model）配合 on-stack developer extensibility。注意这不是回退到经典客制化——RAP 写的代码仍然在 S/4 系统里跑，但它必须满足 ABAP Cloud 的语法约束，由 ATC（ABAP Test Cockpit）做静态检查兜底。

为什么必须留在核心？两条原因，都和"销售订单这个业务对象"绑死了。

第一，Gift Card 维护应用本身要被销售订单的 Fiori 应用引用——做 value help、做金额校验、把折扣推到订单的 pricing 条件里。这一连串动作必须在订单保存的事务窗口内完成，跨系统调一圈外部 API 的延迟和事务边界都不合适。

第二，标准销售订单 Fiori 应用本身要扩字段、加按钮，让用户能在创建订单的时候选择 Gift Card。这种 UI 层的扩展，原文给的方案是 Key User Extensibility——在标准应用里加扩展字段和扩展逻辑，不动标准代码，但又能让标准应用看见这个新增能力。

> on-stack developer extensibility 在 SAP 的最新口径下被列入 Clean Core Level-A——这一点和很多人对"清洁核心 = 全部移出 S/4"的理解不一样。Clean Core 衡量的是是否使用了 ABAP Cloud 的稳定 API、是否能用 ATC 静态校验、是否会被升级影响，不是物理位置。

## 哪些必须移出去：side-by-side 解决的是升级节奏

Loyalty Points 这一组完全搬到 BTP ABAP Environment（Steampunk）上做 Side-by-Side 扩展。原文给出的判断逻辑里，最值钱的一句话其实是这样：

> In private cloud / on-premise, SAP ships a new major version every 2 years. By moving out of the core anything that can be moved logically without adverse performance, the customer can benefit from always being on the latest release.

翻译过来：S/4 私有云每两年一次大版本升级，能从核心里搬出去的逻辑都搬出去，客户的升级阻力就小一档。这不是技术决策，是项目交付节奏的决策。

而 Loyalty Points 恰好满足"能搬"的两个判断标准：

- 销售订单创建后再计算积分，不影响订单本身的一致性，可以异步
- 会员等级、积分倍率这种业务配置，频繁变动，不希望每次改规则都要走 S/4 的传输请求

原文还顺手回答了"为什么不用 CAP 而用 ABAP Cloud"——这里的判断是中性的：取决于团队技能。如果手上有 ABAP 顾问，BTP ABAP Environment 是更顺的选择；如果是 Node.js / Java 背景的团队，CAP 同样可行。两者都满足 Clean Core 要求，没有谁更"现代"的问题。

## 两段中间夹的那条总线

S/4 这边订单一保存，得告诉 BTP ABAP Environment 那边"有一笔新订单进来了，按规则算积分"。这条通信走的是 SAP 自家的 Event Mesh（或 Advanced Event Mesh）。

订单创建事件在 S/4 里被发布到 Event Mesh 上，BTP ABAP Environment 上的 Loyalty Points 应用订阅这个事件，拿到订单 ID、客户 ID、订单金额，再按客户当前的会员等级查倍率，写入积分账户。

```
S/4 Sales Order Created
   ↓ (publish event)
Event Mesh : sap.s4.beh.salesorder.v1.SalesOrder.Created
   ↓ (subscribe)
BTP ABAP : Loyalty Points Calculator
   ↓
   读取客户会员等级 → 查倍率 → 写入积分账户
```

这里有一个容易被忽略的细节：积分计算和订单保存解耦之后，意味着积分写入失败不会回滚订单。这是个有意识的取舍——业务上"订单先成功，积分慢一点没关系"，可观测性补在 BTP 侧的事件消费监控上，而不是反向卡住 ERP。

## 等级升级为什么用 SAP Build Process Automation

原文里第四件事是会员等级升级——客户申请升级，管理员审批，通过后激活。

这件事在经典 ABAP 体系里用 Classic Workflow，写起来不难，但维护和审批人配置全要 ABAP 顾问介入。原文这次用了 SAP Build Process Automation：在 BTP 上画审批流，业务人员可以在 SAP Build 里调审批节点和条件，不用动代码。

这是一个典型的"把审批流移交给业务部门"的设计——loyalty 团队可以自己改"金卡升白金卡需要近 12 个月消费 8 万"这种规则阈值，而不用开 IT ticket。

## 对出海项目落地的几个判断

合适的场景：

- 客户已经在 S/4HANA Cloud Private 上，有明确的两年升级周期压力，希望把客制逻辑外置以减少升级回归测试范围
- 忠诚度规则相对稳定，但等级、倍率、活动机制经常调整——业务希望能自己改配置而不是发版
- 品牌已经在做或准备做出海，需要把忠诚度账户和后端 ERP 的财务核销对上（积分作为负债要在财务上记一笔）
- 已经有 BTP 投入，团队里有 ABAP Cloud 或 CAP 能力

谨慎使用的场景：

- S/4HANA Cloud Public Edition：本身就是 SaaS，几乎没有 on-stack 选项，整套设计要重新拆——Gift Card 这一段也得移出去，复杂度反而上升
- 忠诚度玩法极端复杂、有跨品牌联盟、跨币种积分实时换算的场景：先看 SAP 在 2026 推出的独立 Customer Loyalty Management 产品（不是 Emarsys 模块）是否能直接覆盖，自建一套侧扩展并不一定划算
- 团队没有 BTP 经验、也不打算培养：Event Mesh 配置、ABAP Cloud 开发、SAP Build Process Automation 的运行环境，这三块的运维成本和上手门槛都不能低估

踩坑警示主要有三个：

- Event Mesh 的事件 schema 是有版本的（如 v1）。一旦订阅了某个版本，S/4 升级带来的 schema 变化要在 BTP 侧做兼容映射，否则升级当晚事件会全部消费失败
- on-stack RAP 应用如果想被标准 Fiori 应用直接引用，扩展点是有限定的——做架构评审时一定要先确认目标 Fiori 应用是否提供了对应的 enhancement spot，没有的话整个方案要回炉
- BTP ABAP Environment 的成本不是按"每个应用一份"算的，原文也提到了：一个实例可以跑多个应用。如果只为了一个 Loyalty Points 起一个实例，单价确实不划算；要按整个 side-by-side portfolio 去摊

## 一句话收尾

CLM 这次最值得看的不是"积分引擎能不能配置出 N 种规则"——这种事 Loyalty 厂商遍地都是。值得看的是 SAP 把"和 ERP 强耦合的部分"和"可以解耦异步处理的部分"分开两层做架构，给出了一条在私有云 / 混合云体系下相对干净的扩展路径。

对中国出海企业的项目来说，这条路径的意义在于：积分这种业务规则上变化最快的东西，被搬出了 ERP 的两年升级窗口；同时财务侧需要保留的负债记账，又能借助 RAP 的 on-stack 能力直接挂在 S/4 内部，不用再做一次跨系统对账。

技术架构的合理性，最终还是看它有没有让"业务想改"和"IT 能改"的节奏对上。
