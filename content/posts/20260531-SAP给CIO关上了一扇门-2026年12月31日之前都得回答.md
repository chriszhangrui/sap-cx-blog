**SAPinsider 在 5 月 29 日抛出了一份给 CIO 的清单——5 个不能再拖的决策，截止日期最早就在今年年底。**

Sapphire 2026 之后，舆论焦点都在 224 个 AI Agent、51 个 Joule Assistant、€1 亿欧元基金这些数字上。但 SAPinsider 这篇分析把视角换了一下——这些发布之后，每一个跑在 SAP 生态里的 CIO 头上都多了几个有截止日期的决定。其中最早的一个，2026 年 12 月 31 日就到期。

文章把这场变化的本质讲得很直白——**Sapphire 2026 不是发布会，是 SAP 把企业软件的运行方式重新切了一刀**。BTP、Business Data Cloud、AI Foundation 三块产品合并成 SAP Business AI Platform，AI Agent Hub 在 Q3 GA 之后会成为整个 Agent 体系的指挥中心。Joule 也不再是聊天框——它现在的角色是接收用户意图、调度跨应用的 Agent、把一件事做完。

这五件事，按依赖关系排过序——

![5 个决策的时间窗口](https://sapinsider.org/wp-content/uploads/2026/05/Gemini_Generated_Image_hn0ld0hn0ld0hn0l-1.png)

**第一件，平台合并先做完，不然连 Agent Hub 的门都进不去。** 如果 BTP、BDC、AI Foundation 还在三份合同、三个 Workstream 上跑，等 Agent Hub Q3 上线那天，是访问不了的——这是架构层的硬约束，不是优先级排序的问题。文章建议第一步是审计这三类合同、找出合并路径、指派一个 Business AI Platform Owner 这个具体的人，对统一环境负责。

**第二件，Agent 治理体系必须先于第一个 Agent 上线就绪。** 224 个 Agent 跑在 Finance、供应链、HR、采购、CX 五条线上，治理责任落在 CIO 头上。Autonomous Finance Close 跑出错不是工单，是董事会层面的风险。文章给的清单很具体——一份活的 AI Agent Registry，每个职能都要有 Agent Owner，覆盖、例外协议必须写在 Go-live 之前。这里我想补一句：**CX 这条线是 Agent 治理最容易被忽视的地方**，Service Cloud V2 里的客服 Agent、Sales Cloud V2 里的销售辅助 Agent、Engagement Cloud 里的内容生成 Agent，每一个都直接面向客户。出错的代价不是数字对不上，是客户体验直接崩。

**第三件，ECC 迁移的窗口正在每个季度变窄。** 2027 年 12 月 31 日是 ECC 主流支持终止的硬期限，迁移本身要 18 到 36 个月。也就是说，2026 年下半年还不锁定 RISE 路径和 SI、不把预算放进 H2 计划周期，2027 年那道墙就会和「还没拿到 AI 能力」的另一堵墙同时压过来。这个对中国出海企业同样适用——很多在用 ECC 的中国制造商、跨境品牌的全球总部，到现在还把这件事当成「可以放到明年再谈」。

**第四件，是商务谈判窗口。** Agent Runtime 现在免费，但只到 2026 年 12 月 31 日。SAPinsider 和 Forrester 都点出了一件事——2027 年之后 Joule 的定价，目前在大多数客户的 FY27 预算里都是 TBD。这种 TBD 不是中性的，它是定价主动权倒向 SAP 的开始。文章建议把这件事直接拿到合同续签或扩展的桌面上谈，作为一个明确的条款而不是「等下一次 Renewal 再说」。€1 亿欧元的伙伴 AI 采用基金也是同一个窗口里的事。

**第五件，组织结构要跟着 Joule 一起改。** Joule 替换的不是按钮，是屏幕——意思是 Process Orchestration Analyst、Joule Experience Designer 这种角色，HR 大概率还没开始招。CIO 等 HR 反应过来再动手，那个时候再多的技术部署都救不回来。

除了这五件事，文章里还有一个判断我觉得值得拎出来——**大多数客户对自己 AI 成熟度的位置是高估的**。SAP 把人机协作分成三个阶段：Human Enacted（AI 建议、人执行）、Human Monitored（Agent 跑流程、人审例外）、Human Autonomous（Agent 端到端跑）。2026 年绝大多数 RISE/GROW 的部署还停在 Stage 1，但厂商的销售故事和客户的预期已经跳到了 Stage 3。CIO 想直接在 Stage 1 的组织上跑 Stage 3 的能力，结果就是 Agent 出错、Override 疲劳、采用失败这套熟悉的曲线。

文章里有一行被很多 SI 朋友划过线——**主数据的不一致不会让 Agent 给出次优答案，它会让 Agent 直接出错**。物料、供应商、客户主数据这三个域里的脏数据，过去对报表是噪声，对 Agent 是失效。Knowledge Graph 在主数据没清干净之前激活，是部署风险。这件事必须和 Agent 启用放在同一个预算周期里。

**几个我自己看到的延伸——**

第一，对 SAP CX 客户来说，这五个决策不是 ERP 项目的事。CX 这条线在 224 个 Agent 里有自己的份额——Service Cloud V2 的 case 路由 Agent、Sales Cloud V2 的报价生成 Agent、Engagement Cloud 的内容创作 Agent、Commerce Cloud 的会话商务 Agent，这些都是要进 Registry 的对象。CX 项目的 PMO 之前不太碰治理这一层，现在没得选了。

第二，€1 亿欧元基金这件事，对 SI 合作伙伴比对终端客户更重要。基金是合作伙伴主导的 AI 采用基金，意味着 SI 现在去帮客户做 Joule Assistant 激活、做 Agent 治理框架搭建，是有 SAP 出资支持的。中国的 SAP 生态合作伙伴如果还没有把这件事写进 H2 2026 的销售计划，就是把现成的预算让给了别人。

第三，对中国出海企业的总部 IT 部门，这篇文章的时间线尤其要看。RISE 客户在合同里已经包了三个 Joule Assistant，大多数组织一个都没激活——免费窗口结束之后，这三个 Assistant 不会消失，但围绕它们的运行时账单会开始计费。先把三个免费的跑起来、用 ROI 数据反过来谈 Stage 2 的扩展定价，是这个窗口期里最现实的打法。

文章最后那句话有点意思——SAPinsider 写的是「问题不是 CIO 要不要走向 Autonomous Enterprise，是按你的节奏走还是按 SAP 的节奏走」。把这话翻译到 CX 项目层面，意思也差不多：**Agent 治理框架你今天不画，明天 Joule Studio 就替你画了**。等到那一刻再回头补 Registry、补 Owner、补 Override 协议，成本是另一个量级。

时间窗已经开了。它有一个明确的关闭日期。
