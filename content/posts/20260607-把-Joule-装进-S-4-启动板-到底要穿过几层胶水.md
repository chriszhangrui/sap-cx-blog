很多客户第一次接触 Joule 的反应是：不就是一个 Fiori 启动板（FLP）右上角的 AI 图标吗，加个按钮的事。

直到他们要在自己的 S/4HANA 上把这颗图标点亮，才发现这条链路要穿七层东西：BTP 子账户、IAS 信任、Build Work Zone 订阅、Joule Formation、BTP Destination、Cloud Connector 隧道，最后才是 ABAP 这一端的 Shell Plugin。任何一层配错，图标要么不出现，要么点开是空的。

SAP Community 6 月初发了一篇官方端到端指南，把 PCE（S/4HANA Cloud Private Edition）和纯 OnPremise 这两条路线放在一起拆。读完会发现，这其实不是一篇"配置教程"，而是 SAP 把 AI 接入企业核心系统的整套架构选择，第一次摊开来看。

## 一、为什么不能直接把 Joule 装进 S/4 里

看完整张架构图最先想问的问题是：Joule 既然是给 S/4HANA 用户用的，为什么 SAP 不把它做成一个 ABAP 模块直接跑在 S/4 内核里，而要绕一大圈把它放到 BTP 上，再用一堆中间件接回来。

答案藏在每一层的角色分工里——

- **Joule 本身**是 BTP 上的一个 das-application 服务，本质是一个 Web 客户端 + LLM 编排层，跑在 sapdas.cloud.sap 域下。把 LLM 调用、提示工程、能力编排放在云端，是为了独立迭代，不绑死 S/4HANA 的版本节奏
- **Build Work Zone**（标准版）在这条链路里不是给用户打开的页面，它是 Joule 与 S/4 之间的内容桥（content bridge），负责把 S/4 的 Fiori 应用目录通过 CDM3（Common Data Model v3）同步过来，让 Joule "知道"这个租户里有哪些业务能力可以调
- **IAS**（SAP Cloud Identity Services）是身份层，所有 BTP 服务认证都走它。Joule、Work Zone、S/4 的 FLP 必须建立同一份信任，否则浏览器一刷新就 401
- **Cloud Connector**（SCC）才是把两个世界缝合起来的那块布——只允许出站连接的反向隧道，让 BTP 上的 Work Zone 能反过来读 S/4HANA 内网里的 /sap/bc/ui2/cdm3 这条 ICF 服务
- **Formation** 是 BTP 系统全景里的一个逻辑分组，把 Joule、Work Zone、IAS、S/4HANA 四个系统打包绑定。没有 Formation，Joule 不知道该跟哪个 Work Zone 对话，也不知道目标 S/4 在哪

这套设计的代价是：你在 S/4 这一端几乎做不了什么定制，所有 AI 编排逻辑都在 BTP 上。换来的好处是：S/4HANA 本身的代码不用动，Joule 升级跟客户的 S/4 升级解耦。SAP 把这条边界画得很清楚——AI 在云端长，S/4 在地上稳。

## 二、PCE 和 OnPremise 的差，恰好暴露了这套架构的真正分层

这篇指南最值得读的地方，是它在每一步都标注了"PCE 走哪条""OnPremise 走哪条"。两条路看着只是部署形态不同，实际上暴露了 SAP 这套架构的几条硬性约束。

**第一条差异：S/4 系统怎么注册到 BTP 的 System Landscape 里。**

PCE 走的是 Communication Arrangement（通信安排）的 token 注册——SAP 给 PCE 留了一组标准的通信场景，可以拿 token 直接跟 BTP 握手。OnPremise 没有这条路径，必须在 BTP 系统全景里手工 Add System，类型选 "SAP S/4HANA Cloud" 但实际上指向的是本地系统。这意味着，OnPremise 客户跑 Joule Booster 的时候，集成步骤里只能选 Work Zone，不能选 S/4HANA，否则 Booster 会卡在 token 注册那一步。

**第二条差异：内容同步的实时性。**

Work Zone 的 Channel Manager 给 OnPremise 系统做完首次 CDM3 sync 之后，会在报告里抛一个 callback registration 的错。这不是真错——是因为它想给 S/4 注册一个实时变更通知的回调地址，OnPremise 系统在 NAT 后面收不到这个回调。结果就是：你在 S/4 里改了角色或加了 Fiori 应用，Joule 那边不会自动知道，必须手工触发一次 sync。这条对运维有实际影响——如果项目里 Fiori 内容经常调整，得在 SCC 旁边加一个定时同步的脚本。

**第三条差异：BTP Destination 的命名规则。**

这是这篇指南里最容易踩的坑——Work Zone 只接受全小写、不带下划线的 destination 名字。叫 MCF_TC、JOULE_S4 这种命名会直接报错。原因不在 BTP 这一层，而在 Work Zone 的 Channel Manager 内部把 destination 名字当成 URL 路径片段在拼。这一条差异 PCE 和 OnPremise 都一样，但 OnPremise 客户更容易碰，因为他们要手工建 destination：

```
Name:           jouletc                   # 必须小写无下划线
Type:           HTTP
URL:            http://<scc-virtual-host>/sap/bc/ui2/cdm3
Proxy Type:     OnPremise
Authentication: BasicAuthentication
sap-client:     100
Additional Properties:
  HTML5.DynamicDestination: true
  WebIDEEnabled:            true
  WebIDEUsage:              odata_abap
```

URL 路径必须包含 `/sap/bc/ui2/cdm3`，少了这一段，Work Zone 那边会以为你拿的是 Fiori 启动板的元数据，直接报授权错误。

## 三、Shell Plugin：Joule 图标到底怎么出现在 FLP 上

前面十一步都通了，最后一步是在 S/4 这边把 Joule 图标"亮起来"。这一步的实现路径，比想象的更老派——它走的是 Fiori 标准的 Shell Plugin Target Mapping 机制。

具体做法是在 S/4HANA 里建一个技术型 Catalog（比如 Z_JOULE_TECH），在 Launchpad Designer 里给这个 Catalog 创建一个 Target Mapping：

- Semantic Object: `Shell`
- Action: `plugin`（手动输入，不在下拉里）
- 然后绑定一个 SAPUI5 Component，指向 Joule 在 sapdas.cloud.sap 上的 shell plugin 资源

最后把这个 Catalog 装进一个 PFCG 角色（Z_JOULE_S4HANA），分给目标用户。Joule 图标就出现在 FLP 头部。

这里有个值得注意的设计选择——SAP 没有用什么新的注入机制，没有走插件市场，也没有给 Joule 单独开一个 ABAP 注册表。它用的就是 Fiori 几年前就在用的 Shell Plugin 体系。这个选择的好处是：客户已经有的 PFCG 角色管理、Catalog 分发、Launchpad Designer 都能直接复用，不需要给 Joule 做特殊运维。代价是：你不能在 ABAP 端拦截 Joule 的请求做客制——这条链路的扩展点全部被推到了 BTP 那一侧的 Joule Studio 上。

## 四、信任域：最容易被忽略的两遍配置

Trusted Domains 这一步很多人会跳过，因为名字看起来像可有可无的安全设置。但跳过的代价是 Joule 面板根本嵌不进 FLP——浏览器会直接拒绝跨域 iframe。

这套配置要做两遍，BTP 一份、IAS 一份。两边接受的格式还不一样：

- **BTP Trusted Domains** 接受完整 origin，要带 scheme 和端口：`https://your-s4-host:44301`
- **IAS Trusted Domains** 只接受 hostname：`your-s4-host.example.com`

需要写进白名单的 origin 至少有三个：S/4HANA FLP 的 origin、Joule Web Client 的域名（`<tenant>.<region>.sapdas.cloud.sap`）、Work Zone 站点（`<site-id>.launchpad.cfapps.<region>.hana.ondemand.com`）。

这一层暴露了 SAP 在 AI 接入里对安全的态度——不走通用 LLM 那种 API 直连，而是把整个交互嵌进现有的 Web 安全模型里：CSP 头、CORS、跨域 iframe 通信、SSO 票据传递。这是企业级 AI 集成跟消费级 AI 应用最核心的差别。

## 五、什么样的项目适合走这条路

这套接入方式挺重，启动一个 PoC 就要 BTP 全局账户管理员权限、IAS 租户、SCC 安装、PFCG 角色调整、Catalog 设计师权限五件事一起到位。三个建议——

**第一种适合走的项目，是已经在 BTP 上有比较成熟落地的 S/4 客户。**

如果你已经在用 Build Apps、Build Process Automation，或者已经做过 BTP 侧扩展，那 Joule 这一套大部分基础设施已经在了——IAS 信任、SCC、Cloud Foundry 都现成。剩下的工作主要是订阅 Joule、配 Formation、建 Channel。一周内能跑出 PoC。

**第二种要谨慎的，是纯 OnPremise 的 S/4HANA 客户。**

原文反复强调 OnPremise 是 PoC 用途，不是生产路线。原因有几个：通信安排没法做、CDM3 实时回调不工作、SCC 在 NAT 之后的稳定性需要客户网络配合。如果你是出海企业总部对接的 IT 负责人，IT 团队基础设施还在传统数据中心里，建议把 Joule 试点和 S/4HANA 上 PCE 这件事放在一起规划，别在 OnPremise 上硬切 Joule。

**第三种暂时别碰的，是没有 IAS 治理基础的客户。**

很多 SAP 老客户身份认证还在 ABAP local login 或者第三方 IdP 上，没接 IAS。这条 Joule 链路强依赖 IAS 做 SSO——你想跳过 IAS 直接用 ABAP 用户登录 FLP，Joule 那一侧的 BTP 服务调不通用户上下文，整个 AI 助手就只是个空壳。要先把 IAS 这条身份治理底座建起来，Joule 才有意义。

## 最后一点

读这篇 13 步的指南，最有意思的不是它给出了一套配置清单，而是它把 SAP 的 AI 接入哲学第一次明明白白写了出来——AI 的算力和编排在 BTP，不动 S/4；身份和会话在 IAS，不动 ABAP 用户主数据；内容发现走 Work Zone，不走原生 Fiori 启动板的元数据接口；网络穿透走 SCC，不开内网入站。

这跟 Salesforce Einstein 那种"全部塞进同一个 Force.com 平台"的路线完全相反。SAP 选择的是一条更工程化的路：用现有的 BTP、IAS、SCC、CDM3、PFCG 这些已经在客户那里跑了好几年的东西做接入，把 AI 当成一个新的"工作负载"叠加上去，而不是重写整个用户接入模型。

代价是接入复杂度高、需要七层组件协同。好处是 SAP 老客户的运维体系不需要为 AI 单独建一套——这件事，可能比 Joule 本身的能力，更值得 SAP 生态里的架构师认真想想。
