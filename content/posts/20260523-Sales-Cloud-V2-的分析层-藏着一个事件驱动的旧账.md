Q1 2026 那批 SAP Sales & Service Cloud V2 的分析模块更新，列了四条能力：自定义服务实体接进 Embedded SAC、扩展字段的 Where-Used、Survey 单独成为一个数据源、还有一个不太起眼的"自动数据再同步"后台任务。

表面看是四个分散增强。但把它们摆在一块儿读，其实在补一笔 V2 落地时埋下来的旧账——分析层这次真的从业务层手里被剥出来了，副作用得逐个去填。

## V1 时代，分析就长在业务库里

做过 Cloud for Customer（也就是 V1）报表的人都熟悉这个套路：业务对象就在 HANA 里，CDS view 拿过去做语义建模，Embedded Reports 直接基于这套视图开报表。事务、读写、分析共享同一个库。一致性是免费的，因为压根没有一致性问题。

代价也很清楚：分析查询会跟业务事务抢资源；模型一改业务跟着颤；扩展字段加在业务表上，往报表上铺到底涉及哪些 Story，靠人脑记。规模小的时候忍一忍就过去了，规模一大、租户一多，这套耦合就开始拖整个平台的水平扩展能力。

Sales Cloud V2 选了另一条路。

## V2 把分析层物理拆出去了

![V1 与 V2 的数据流对比](https://community.sap.com/legacyfs/online/storage/blog_attachments/example.png)

V2 的底层是 cloud-native 的分布式微服务——这是 SAP 自己在原文里直接承认的措辞——每个服务有自己的存储边界，分析数据通过事件机制被复制到一个独立的 HANA 实例，再供 Embedded SAC 消费。

"事件机制复制到 HANA"这一句翻译过来就是：分析侧不再读业务表，业务事件通过流走到 HANA 的副本里，分析永远读副本。这是一次彻底的物理隔离——业务负载和分析负载各算各的资源，分析模型迭代不再影响业务事务，扩展性问题在架构层一次性了断。

好处显而易见。但工程上从来没有免费午餐，下面这条新增功能就是账单。

## Auto Resync：事件驱动的兜底永远绕不开

原文用了一段相当克制的描述：

> "Analytics data is replicated into SAP HANA via event-driven mechanisms. With high event volumes, rare inconsistencies can occur between source microservices and the analytics data store (HANA)."

翻成大白话就是：事件流在高吞吐情况下，偶尔会把数据搞丢、搞乱、或者顺序错位，导致业务源库跟分析库对不上账。

这不是 SAP 的问题，是事件驱动架构的物理性。任何在生产里跑过 Kafka 消费链路的人都知道：消息可能重投、可能延迟、消费者可能挂掉重启错过 offset；CDC（变更数据捕获）链路上下游版本不齐时也会丢数据。一旦你选了"异步复制"，最终一致性就是默认结果，强一致就再也回不来。

所以这次新增的"自动数据再同步"后台任务，本质上是一个 reconciliation job：定期扫描业务库和分析库的差异、主动修正不一致、调度跑在低峰时段。它不解决任何业务功能问题——它只解决 V2 架构本身留下的兜底缺口。

一句话：这是 V2 第一次正式承认事件驱动会丢数据，并把对账机制做成产品标准件。

## 另外三个增强，全都在补"分析层独立"这件事

回头看其余三条更新，会发现都不是孤立的功能点，而是在把"分析层独立"这件事做完整：

**自定义服务实体接进分析（Restricted GA）**。客户和合作伙伴用 Custom Service 扩展出来的实体，这次能自动生成一个 "Custom" 数据源，进入 Embedded SAC 的 Query Designer，还能跟标准数据源拼起来出 Story。前提是这个自定义实体要被标记为 "Analytics Relevant"，要分析的字段也得逐个标。

为什么需要专门做这件事？因为 V2 的分析侧是独立 schema，扩展实体不会自动出现在那边。要让自定义实体可分析，必须有一条专门的注册通道把元数据投递过去，并触发数据复制。这跟 V1 时代"建个 view 就能查"的逻辑彻底不同。

**扩展字段的 Where-Used**。管理员现在能在 Extensibility Administration 里看到一个扩展字段被哪些 Embedded SAC Story 引用。听上去是个治理小功能，但放在 V2 的语境里它的位置就清楚了——分析层在物理上独立之后，"删一个字段"这个动作的影响半径不再可见，必须把跨层依赖关系显式暴露出来，否则字段一删，下游 Story 静默崩掉。

**Survey 数据源**。问卷之前只能拿到设计层的元数据，回收上来的 response 拿不到。这次把 response 单独建成一个 standard data source。问卷和业务对象本来就不属于同一个微服务，要做交叉分析，必须给它建独立的复制通道——又一个事件流出口。

## 对实施项目意味着什么

如果手上的项目是从 V1 迁到 V2，或者新建 V2 项目并要求分析能力的，下面几件事在前期就得想清楚。

- **分析延迟从同步变成异步**。V1 里报表是"现在写、现在能查"，V2 里这条假设不成立。订单刚落库到能在 SAC 上看到，中间会有秒到分钟级的窗口。任何要求"实时看板"的场景，都要重新跟业务方对齐口径——是不是真的需要秒级，还是其实分钟级就够。
- **扩展字段必须显式标记 Analytics Relevant**。V1 里建个字段就能拉到报表，V2 里要想让它出现在 SAC，得在扩展字段定义那一步就勾选。漏掉了，字段在业务侧能用，分析侧看不到，迁移期间这种坑特别多。
- **自定义实体走 Custom Service 的**，要专门规划分析路径。Custom Service 实体先开 "Analytics Relevant"，再针对每个要进 SAC 的属性勾选；走 Restricted GA 阶段还得发 incident 到 CEC-CRM-ANA 申请白名单。
- **不要在分析侧做强一致校验**。比如"业务订单数 == 分析报表订单数"这种核对脚本，V1 时代成立，V2 时代会偶发不一致——Auto Resync 跑完才会收敛。把这种校验逻辑设计成"接受最终一致"或者"以业务库为准"，不然运维报警会被误报淹没。
- **Where-Used 要进上线 checklist**。删除或者重命名扩展字段之前，先翻 Where-Used 列表，确认没有 Story 在引用。这件事在 V2 上，比在 V1 上严重得多——V1 删错字段最多报表报错，V2 是分析层独立 schema，错误传导路径更隐蔽。

## 什么样的项目适合用、什么时候要谨慎

**适合直接上 V2 分析的**：业务量级会持续增长、需要多租户隔离、扩展实体多、对分析层独立扩缩有要求的——出海企业的全球部署、跨多区域的销售组织尤其匹配。V2 这套架构给到的水平扩展能力，是 V1 那套耦合体永远给不出来的。

**需要谨慎的**：业务上严重依赖"事务-报表实时一致"的——比如带强财务对账要求的销售订单、合规层面要求"分析数据等于业务数据"的场景——V2 默认的最终一致模型会让这类场景非常难做。要么把这类报表留在 S/4HANA 这种单库强一致系统里出，要么明确接受窗口期，并在前端表达"数据延迟 X 分钟"。

**更直白一点**：V2 的分析层不是 V1 的等价升级，它是一套不同假设下的新东西。前期只要把这套假设跟业务方讲清楚，后面的实施成本会下来很多；讲不清楚，上线之后吵的就不是技术问题，是预期问题。

Q1 这四个更新摞到一起看，能感受到 SAP 在 V2 落地这件事上是诚实的——架构的代价它没回避，反而专门做产品来补。这种姿态比"功能列表更长了"那种发布稿要值得参考得多。
