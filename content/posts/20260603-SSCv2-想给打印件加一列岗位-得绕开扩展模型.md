有个看起来非常小的需求：在 Sales Cloud V2 拜访（Visit）打印件里，把出席人的职位列出来。功能上不复杂——参会名单已经在那张表里了，无非是再多一列。

但只要你打开 SSCv2 的 Extensibility Administration，就会撞到第一堵墙：Visit 这个 Business Entity 只允许在 header 级别加扩展字段，参会人（attendees）作为子节点是不能直接扩展的。换句话说，标准模型给你画出来的扩展边界，刚好把这个字段挡在外面。

这一条限制顺着推下去，最后变成了一个跨三个组件的小型架构题：SSCv2 自己解决不了，得拉 BTP 进来；BTP 上要写 webhook 处理逻辑；写好之后还得回到 Adobe LiveCycle Designer 里改 PDF 模板。整个动作一个比一个不直觉。

## 第一关：扩展字段只能挂在 header 上

SSCv2 的扩展模型对 Visit 这种带子节点的实体有个硬约束：你能在 Visit 主单上加字段，但不能给 attendees 子节点加字段。这是平台级的设计选择，不是项目能调的开关。

这个约束让"在 attendee 这一行追加 jobTitle"这条直觉路径直接走死。剩下的方法就只剩一种：把多条参会人的信息编码进一个 header 字段，再在打印件渲染时把它拆开。原文用了一个非常朴素但很有效的格式：

```
50:Developer|23:Designer|107:Manager
```

用 `|` 切记录，`:` 切 ID 和职位。前提是这两个分隔符都不会出现在职位字符串里。原文也提到了备选方案——用 JSON 串，LiveCycle Designer 的 JS 引擎可以用 `eval("(" + jsonText + ")")` 解析。但只要不存在分隔符冲突，简单字符串永远比 JSON 省事。

## 整条链路：从 Visit 保存到 PDF 渲染

关键节点有四个：SSCv2 触发 Post-Webhook → BTP 上的 Node.js 应用接住载荷 → 反向调 SSCv2 的 contact-person-service 拿职位 → 把结果回写进 header 扩展字段，最后由 PDF 模板里的 LiveCycle JS 还原。

注意里面有一个反方向调用：webhook 是 SSCv2 推数据出去的方向，但拿到 attendeeId 之后，Node.js 还要反过来调 SSCv2 自己的 REST API 去取联系人主数据。这意味着 BTP 这一段需要有 SSCv2 这边的认证凭据，不是单纯接收消息就完事了。

## 为什么必须用 BTP Destination

原文里有个细节值得单独拎出来：作者明确没用 fetch 或 axios 去发起对 SSCv2 的调用，而是用 `@sap-cloud-sdk/http-client` 配合 BTP destination service。

```javascript
import { executeHttpRequest } from '@sap-cloud-sdk/http-client'

const SSCV2_DESTINATION_NAME = 'fw-web-extensions-sscv2';

const response = await executeHttpRequest(
  { destinationName: SSCV2_DESTINATION_NAME },
  { method: 'GET', url: finalUrl }
);
```

差别不在于哪个写得更短，而在于运行时凭据从哪里来。BTP destination 把目标系统的 hostname、用户名、OAuth 凭据全部托管给平台，应用代码里看不到任何 secret。换成 fetch + 环境变量的写法，凭据就漏到代码或部署配置里了——SaaS 应用走多租户后这种写法基本没法过审。

这也是为什么 SSCv2 这一类 SaaS 扩展项目，几乎所有的对外调用都被往 destination 这条路上推。本地调试的时候可以用 `cf create-service-key` 把 destination 凭据导出到 default-env.json，xsenv 加载之后照样能跑——这条路径让本地开发不用降级到不安全的写法。

## Webhook 载荷的两个小坑

**第一**，载荷格式不固定：

```javascript
// Support CloudEvents format (data wrapper) or direct format
const data = req.body.data || req.body
```

SSCv2 的 webhook 同时存在两种载荷形态——CloudEvents 标准（外面包一层 `data`）和直接格式。处理逻辑必须两种都接得住。

**第二**，sample payload 和真实 payload 字段不一致：

```javascript
// sample payload uses displayId, real payload uses visitId...
const visitDisplayId = data.currentImage.displayId || data.currentImage.visitId;
```

这种"测试时和生产里字段不一样"的情况在 SSCv2 webhook 里不是孤例。原文作者甚至专门写过一篇用 Node.js 做 HTTP debug monitor 的文章，就是为了在写业务逻辑之前先抓真实流量样本。

## 回写约定：必须按平台的格式返回

SSCv2 的 post-webhook 不只是被通知一下，它还会把响应里的内容写回到 Visit 记录上。响应体结构必须严格遵循 SSCv2 的约定：

```javascript
const responseData = {
  ...data.currentImage,
  extensions: {
    ...data.currentImage.extensions,
    PrintFormContactJobTitles: jobTitles
  }
}
const responseBody = { data: responseData };
res.status(200).json(responseBody)
```

这里的 `extensions` 节点是 SSCv2 标准模型上挂自定义字段的位置；外层的 `{ data: ... }` 包裹是平台要求的响应结构。任何一层错了，回写都不会落地，也不会报错——只是悄悄丢掉。这是 SSCv2 webhook 调试时最容易踩的坑。

## 第三段：在 PDF 模板里反序列化

到这一步数据已经躺在 Visit 的扩展字段里。但 PDF 模板看到的还是那一串 `50:Developer|23:Designer|...`。Adobe LiveCycle Designer 的 table initialize 事件里要做两件事：把字符串拆回对象，然后按行匹配填值。

```javascript
var jobTitles = {}; // 不是数组——是对象，attendeeId 当属性名

function initJobTitles() {
  var s = getValueFromDataSource(xfa,
    "xfa.record.extensions.PrintFormContactJobTitles");
  if (!s) return false;
  var pairs = s.split('|');
  for (var i = 0; i < pairs.length; i++) {
    var parts = pairs[i].split(':');
    jobTitles[parts[0]] = parts[1];
  }
  return true;
}

function enrichJobTitleTable() {
  var rows = this.resolveNodes("rowTableSection.rowTableItem[*]");
  for (var i = 0; i < rows.length; i++) {
    var row = rows.item(i);
    var id = getValueFromDataSource(row, "dataNode.attendeeDisplayId");
    if (jobTitles[id]) row.jobTitle.rawValue = jobTitles[id];
  }
}
```

注释里那句"不是数组"很重要：用对象当哈希表查找是 O(1)，attendee 多了之后差距就出来；如果用数组每次还得遍历去找。LiveCycle 的 JS 引擎不是浏览器引擎，能用的标准库非常有限，写法要更接近上世纪 90 年代的 JavaScript。

另一个细节是 `dataNode.attendeeDisplayId`——表格行通过 dataNode 反向取到当前绑定的数据记录。这是 XFA 模板的标准引用方式，和普通 DOM 操作完全两套体系。

## 这套设计放弃了什么、保住了什么

- **放弃了**对子节点扩展的开放度。如果 attendee 能直接加字段，整条链路根本不需要存在。
- **保住了**核心数据模型的稳定性。SSCv2 是 SaaS 多租户产品，子节点的 schema 一旦放开扩展，所有依赖这个节点的 API、报表、AI 模型、数据复制都要做兼容处理。这个代价大到几乎不可能接受。
- **把复杂度推给了 BTP。** 之前 V1 上类似场景可以靠扩展字段加模板调整搞定，现在这种事被推到 side-by-side。代价是项目门槛抬高，但好处是核心保持干净，升级时不用为这种自定义逻辑兜底。

这正是 SAP 在 V2 上反复强调的 Clean Core 思路在一个具体场景里的体现：核心模型的扩展点收紧，溢出的能力丢到 BTP 上自己写，由开发团队对扩展逻辑的可维护性负全责。

## 什么场景值得用、什么时候别碰

**适合走这条路的场景：**

- 出海制造业、消费品行业，零售拜访、医药代表拜访等场景里，需要按品牌定制打印件的
- 在华跨国企业的总部 SSCv2 实例，对接多个区域子公司的本地化打印需求
- 团队里已经有 BTP / Node.js 经验，destination + CAP 的技术栈不是从零开始

**建议绕开的情况：**

- 项目里只有打印件这一个扩展需求，没有别的 BTP 应用
- 业务方对修改频率高，LiveCycle Designer 的开发反馈链比 Web 模板长得多
- 团队没有人能维护 LiveCycle 模板——这个工具的活跃开发者群体在收缩

真正的踩坑警示是这一条：webhook 路径上的 currentImage 修改要确保**触发条件**。只有当 Visit 上某个字段被改动了，post-webhook 才会触发。如果你只在主数据里改了联系人的职位，但 Visit 没动，打印件读到的还是旧值。这是设计层的边界，不是 bug，但实施时如果不在前端加一层主动刷新逻辑，业务用户会觉得"系统是错的"。
