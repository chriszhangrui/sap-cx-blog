Sapphire 大会的 200 多个 Agent 摆上台之后，外界都在看模型选了谁、合作伙伴名单上有谁。但 5 月 12 日 SAP 官方发了一篇 BTP Fabric 首席产品官 Andre Lamego 写的技术稿，把另一件事讲清楚了：Agent 真正难的不是怎么调起来，而是怎么让它在企业里 安全地 跑起来。

这篇稿子里讲的是 SAP 和 NVIDIA 的一个深度共建动作，主角是一个叫 NVIDIA OpenShell 的开源项目。读完之后会发现，SAP 这次不是"用"了 NVIDIA 的东西，而是把自己的工程力压进了 OpenShell 的代码库里，目的是把 Agent 执行层做成企业能信任的样子。

## 这次官宣到底说了什么

OpenShell 是 NVIDIA 主导开源的一个 Agent 执行运行时。它要解决的是一个具体的问题：当 AI Agent 不再只是回答问题，而是真的去 调命令、写文件、访问网络、调 API、动数据库 的时候，怎么保证它出错的时候不会把企业搞炸。

OpenShell 给出的能力很硬核：隔离的执行环境、文件系统和网络访问的策略约束、运行时级别的爆炸半径限制——就算 Agent 的逻辑出问题、被 prompt 注入了、调用了错误工具，OpenShell 也能把损害圈在沙箱里。

SAP 在这件事上贡献的不只是站台。Lamego 说得很直白：SAP 把 真实的 Agent 工作负载 拿到这次合作里来，让 OpenShell 接受企业级压力测试。具体投入有三件事。

- 把 SAP 客户对隔离边界、策略执行、可审计性的真实诉求，写进 OpenShell 的需求清单
- 派工程团队进驻 OpenShell 开源代码库，重点做四件事：运行时加固、策略建模、企业身份集成、审计与治理钩子
- 把 Joule Studio runtime 摆在 OpenShell 上面，作为 SAP 自己的"业务策略层"

最关键的是那条分工线，原文里写得很清楚：

> OpenShell 回答："这个动作 **能** 安全执行吗？"
> Joule Studio runtime 回答："这个动作 **应该** 发生吗？"

上面这两句话翻译成大白话：OpenShell 是技术层的安全网，Joule Studio runtime 是业务层的红绿灯。前者保证 Agent 跑不死系统，后者保证 Agent 跑的事符合业务规则、合规要求和岗位权限。两层都通过了，Agent 才允许动手。

## 为什么这件事比 Sapphire 那些大新闻更值得看

过去半年，企业 Agent 这条线上的讨论几乎全在两个方向打转。一个是模型——选 Anthropic 还是 OpenAI、选 Joule 还是别人家的 Copilot；另一个是用例——客服 Agent、销售 Agent、采购 Agent 各发了多少个。但凡到落地，都卡在第三件事上：客户的安全和合规团队不放行。

这件事在 SAP CX 项目上特别明显。Service Cloud V2 上现在已经有 case 自动分诊的 Agent，Sales Cloud V2 上有报价生成的 Agent，Commerce 那边的 Agentic Commerce 也在路上。客户拿到 Demo 看完都说好，到了真要灰度一部分流量进去时，安全审查那一关就开始反复——这个 Agent 是用谁的身份在调 API？它执行错了谁负责？审计日志能给多详细？

大多数厂商的回答是"你装个监控吧"或者"我们有审计接口"。这都不是企业要的答案。企业要的是：从执行的第一行代码开始就 有边界、可控制、留痕迹，不是事后再补一层审计。

SAP 这次和 NVIDIA 共建的方式，本质上是把这件事往前推了一步：执行层的安全模型，由两家头部厂商一起在开源里把骨架定下来；上面的业务策略层，留给 SAP 自己用 Joule Studio runtime 做差异化。这个结构对客户来说，意味着 OpenShell 这一层是开源、可审计、不锁定 SAP 的；Joule Studio 那一层才是 SAP 真正卖的产品。

这是一个挺聪明的边界划法。安全运行时是基础设施，谁都用得上，开源做得越广越好；业务语义和治理才是 SAP 最有积累的地方，留在自家产品里收钱。

## 这意味着什么

对正在做 SAP CX 项目、特别是已经在选型 Joule 的中国出海企业，这条新闻里有两件事值得特别留意。

第一件，未来评估一个 Agent 方案的时候，问题清单要从"它能做什么"扩到"它的安全边界长什么样"。OpenShell 的几个能力维度——隔离执行、策略约束、爆炸半径——基本上会成为之后客户安全团队的检查项默认模板。如果某个 Agent 项目的供应商讲不清这三件事，无论 Demo 多惊艳，都建议先暂缓。SAP 这次把分工讲得这么清楚，等于给行业做了一份评估清单。

第二件，Joule Studio runtime 这一层的价值，会比想象中关键。中国出海企业的 CX 项目里有一个常见痛点：业务规则和合规要求很多是地区性的，欧盟数据驻留、东南亚跨境支付审计、北美 SOX 审计……每个地区都不一样。Agent 跑在哪个市场，就要遵守哪个市场的规矩。Joule Studio runtime 这一层做的就是把这些规矩翻译成 Agent 能理解的策略。这件事如果客户自己做，工作量会很可怕；如果靠厂商默认提供，得选那个本身就在多区域跑过的厂商。

还有一个旁观者的判断。SAP 把 OpenShell 摆在执行层底座的位置，意味着将来 Joule Studio 上跑的 Agent，理论上也能跑非 SAP 的应用——只要那些应用愿意接进 OpenShell 的运行时。这是 Agent 互操作的另一种解法：不在协议层卷（像 MCP 那样），而是在运行时层卷。如果这条路真跑通，SAP Agent 治理这把锁，可能比 Forrester 之前担心的"控制权之争"更有意思一些。

当然，OpenShell 现在还很早期，SAP 投进去的工程量也才刚开始释放代码。这次合作能不能撑起 Sapphire 上承诺的 200 多个 Agent，还要看接下来几个季度的产出。短期内，CX 项目里讨论 Joule 落地，仍然会面对同样的几个问题——Agent 用谁的身份、做错了谁负责、审计日志给到哪一层。这次合作，至少把答案的方向划出来了。
