2026 年的 Sapphire 大会，SAP 把数字摊开来：50+ 个 Joule Assistant、200+ 个专项 Agent、€100M 合作伙伴基金、Dremio 和 Prior Labs 两笔收购、跟 JPMorgan 把通用账目搬上 SAP。一个核心叙事被反复推上台——Autonomous Enterprise，自治企业。

这个词听上去很大，落地起来很重。Clarkston Consulting 在 Sapphire 之后写了一篇复盘，把"自治"这两个字拆成 5 块前置条件。这 5 块对今年要做 CX 项目的人来说，是项目启动会之前就该过的清单——不是因为新鲜，而是因为容易在兴奋里被跳过。

下面这 5 件事，每一件都决定了 200 个 Agent 上线那天，到底是出价值还是出事故。

## 一 · AI 这次真的从"建议"切到"执行"了

过去几年的企业 AI，多数停在"提建议"那一层。给一个销售推荐回访话术、给一个客服总结工单背景、给一个运营起草一封邮件。人还在中间，AI 像个副驾。

Sapphire 2026 的转向是 Agent 开始动手干活。SAP 演示的画面里，Agent 直接在 Sales Cloud 里更新 opportunity、在 Service Cloud V2 里改派工单、在 Commerce Cloud 后端跑一次促销规则的 A/B、在 Emarsys 里把一段 segment 的触达频次从每周 3 次降到 1 次。人审一下，Agent 执行。

> "AI 不再是生产力插件，是跨流程的协调和执行层。" 这句话决定了你今年做 CX 项目的姿态——不是给销售装个副驾，是把销售流程的某几段直接交出去。

一个跨境电商做出海的客户最近问，Service Cloud V2 上线 6 个月，客服 KPI 怎么定。原来按响应速度+一解率算。Agent 接手 60% 工单之后，这两个数都失去意义——Agent 几秒解一个，问题不在快不快，而在哪些工单 Agent 不该碰。KPI 要换成"Agent 处理覆盖率""人工覆写率""一次解决率分布"这种新指标。这是个看上去小、改起来动筋骨的事。

## 二 · 业务上下文，是 LLM 和企业之间的翻译器

第二件事，业务上下文。Clarkston 的原话是 business context 决定 AI 能不能给企业用。Sapphire 上 SAP 把 Business Data Cloud 推到了核心位置，再叠上 Knowledge Graph 和 Domain Models，一整套就是为了一件事——让 LLM 听得懂企业自己的语言。

通用大模型知道"客户"是什么，但不知道你公司里"重点客户"指的是过去 12 个月成交超 50 万、且签了战略合作协议、且 NPS 在 8 分以上的那群人。这个定义在哪儿？散落在 Excel、人脑、销售复盘 PPT 里。Knowledge Graph 把它结构化进来，Agent 才能用得对。

所以 BDC 的价值不在"又一个数据平台"，而在它把客户主数据、产品主数据、合同条款、流程定义这些东西，喂给 LLM 用的语义层。这个语义层不准，下面跑 200 个 Agent，错误就放大 200 倍。Clean Master Data 不再是一个项目阶段，是 Agent 项目的前置条件。

## 三 · Clean Core 不是技术债话题

Clean Core 这个词 SAP 喊了三年。前两年很多客户当成迁移到 S/4 Cloud 的话术听。今年 Sapphire 之后，性质变了——它直接关联 AI 落地速度。

逻辑很直接：客制化越深、扩展越多、流程越偏离标准，Joule 和 Agent 能预先理解的部分就越少。SAP 出厂的 Domain Models 描述的是标准流程。你的客制开发不在这个模型里，Agent 看不见，Joule 帮不上，每一个客制流程要 AI 介入，都要重新一次"人工解释"。

> 客制化债务不再是 IT 的烦恼，是直接压制业务侧 AI 落地速度的瓶颈。每多一段非标客制，就多一次 AI 看不懂。

这事对中国出海企业尤其重要。出海项目里 Commerce Cloud 经常被改得很重——本地化支付、海关合规、跨币种价目、多语言 SKU 维护逻辑。这些客制 5 年里支撑了出海，但今年开始要算另一笔账：每一段客制化，都是 AI Agent 接管这段流程的成本。能 Clean 的尽量 Clean，能用扩展不用 Modify，能用 BTP Side-by-side 不用核心改造。

## 四 · 通用 AI 太空，行业 AI 才落地

200 个 Agent 不是 200 个通用助手。Sapphire 上 SAP 把它们按行业切——制造、零售、消费品、生命科学、能源、公共部门，每个行业都有自己的几十个专项 Agent。

为什么这么切？因为通用 Copilot 那条路，过去 2 年大部分企业试过，价值很难量化。"帮我写一封邮件"和"帮我把这单 RMA 跑完"是两件事。前者是个工具，后者是把一段流程从头跑到尾。

RWE 在风电场用 SAP 跑设备健康监测和预测性维护，不是因为 LLM 多聪明，是因为 Agent 直接接通了 SCADA 数据、维修工单系统、备件库存。H&M 用 Joule 优化时尚趋势分析和库存配比，是因为 Agent 看得见门店级 POS 数据、看得见 Emarsys 上的客户行为分群、看得见供应链上的 SKU 切换成本。

这些都不是 demo，是有具体数字撑着的——RWE 这个项目把维护工时减下来 18%，H&M 那边把单店缺货率压低 23%。这种数字才是 CFO 在 2027 年预算会上拍板续约的依据。

## 五 · Agent 一旦能动手，治理必须同步

最后一件事，治理。Sapphire 上 SAP 推 AI Agent Hub，把 Agent 的注册、权限、审计、成本、行为日志都集中管。Forrester 在会后的点评里说了一句很重的话——"如果 Agent 能动作，但治理没跟上，那不是创新，是事故源。"

这件事在 CX 上特别敏感。一个 Agent 在 Sales Cloud 改了客户的信用额度、在 Service Cloud 同意了一笔退货、在 Commerce Cloud 后台改了一段促销文案——这些动作每一个都有审计要求、有合规边界、有风控阈值。Agent 比人快 100 倍，意味着事故可以放大 100 倍。

Clarkston 提的实操建议是 3 件事：每一个上线的 Agent 都要在 AI Agent Hub 注册并定义权限边界；要有"动作回滚"机制，至少敏感操作要可逆；要有"人工接管"按钮，业务高峰、风控告警、规则冲突时人能立刻拿回控制权。这些不是事后补的，是 Agent 上线那一天就该有的。

## 如果你下个季度要立 AI 项目

把 Clarkston 这 5 块条件翻成下个季度立项前的检查项，大概是 3 个动作：

- 把 master data 的当前状态做一个评估，CX 这一侧重点是客户主数据、产品主数据、订单主数据，3 个维度的完整性、一致性、唯一性各打个分，低于 70 分的先治理后接 Agent。
- 把过去 5 年 Commerce / Sales / Service 上的客制化清单拉出来，分 3 类——可以直接 Clean 的、要换扩展实现的、必须保留但要单独治理的。这件事拖到明年做就晚了。
- 选 1 到 2 个有具体业务指标可以量化的 Agent 用例先跑——不是 demo，是要给业务侧承诺一个数字的那种。先有第一个跑出来的成功案例，后面 200 个才有路径。

200 个 Agent 不是终点，是企业 IT 架构和业务流程的下一种形态。前面 5 件事每一件都不性感，但每一件都在决定，明年这 200 个 Agent 上线那天，是给业务出价值，还是给业务出事故。
