做过零售或快消项目的人对这个场景应该不陌生：一笔线上订单进来，系统要在 200 毫秒内决定从哪个仓发、是否拆单、能不能从门店调货。决策依据通常是一棵 IF-ELSE 规则树——按预设顺序往下走，命中即返。

这套逻辑维护到第三年，规则树会变成一棵谁都不敢动的圣诞树。新增一个"优先利用满载率高的仓"的目标，不知道该插在第几条之前；调换两条规则的顺序，QA 要把所有场景重跑一遍。问题不在规则本身，问题在"规则顺序判断、命中即返"这个老底子的执行模型。

SAP 把订单中枢拆成 4 个独立计费的能力包之后，Sourcing & Availability 这一块的设计原则被悄悄换掉了。它不再让你写规则——它让你定义业务目标，给目标分配权重，剩下的让系统自己算。

## 规则引擎的天花板在哪

原文里有一段话点得很准——传统订单寻源（Order Sourcing）应用是规则驱动的：比如"从最近的站点发货"。要配置一个策略，业务用户必须基于多重假设来设定确定性规则。

> "Furthermore, rules are evaluated sequentially, with the risk of never even evaluating the rules that appear later in the sequence, if the system finds a solution it deems already acceptable."

规则按顺序评估，一旦找到"看起来可接受"的解就停。这意味着排在后面的规则可能永远跑不到。一个零售客户跟我吐过同样的槽：他们配了 17 条规则，但生产环境中常用的只有前 4 条，后面 13 条只在极端场景被命中过几次——可这 13 条仍然占着维护成本，因为没人敢删。

规则引擎本质上是一个"局部最优"系统。它在每一步选当前最像答案的那条路径，但永远证明不了这是全局最优。当业务目标只有"快速发货"一个维度时这没问题；当目标变成"履约成本+时效+库存周转+门店清货"四个相互制约的维度时，规则树就开始打架。

## 把目标当输入，让系统自己算

SAP Order Management for Sourcing & Availability 的设计思路是把业务目标本身做成一等公民。你不再写规则，你写目标和权重：

- 利用率最大化（最大化承运商满载率、仓库出库密度）
- 配送时效最优（依据运输信息计算预计到达时间）
- 履约成本最低（综合包材、运费、人力）
- 门店去化优先（线上订单优先消化滞销门店库存）

每个目标可以被赋一个权重，权重表达"这个目标对当前业务有多重要"。订单进来之后，系统不是按顺序判断，而是把所有目标作为一个综合评分函数同时评估，输出最优组合。原文用的词是 "evaluated simultaneously, with their assigned weight considered"。

这个差别看起来只是技术实现的不同，但落到运维层面是天壤之别。

## 寻源之前，先把"可用"这件事算准

寻源策略再聪明，喂进去的库存数据不准都白搭。S&A 把可用性数据（Availability）做成了一个独立的子能力，至少要解决三件事：

- **多节点聚合**：把分销中心（DC）和门店（Store）的库存放进同一个视图。门店库存是动态的，POS 销售随时在扣，必须近实时同步。
- **未处理销售（Unprocessed Sales）**：门店收银台刚扫了 5 件 SKU，TLOG 还没传到中央，但库存其实已经没了。系统必须把"在路上的销售"也算成已扣减，否则线上会把不存在的库存承诺给客户。
- **预留（Reservations）**：订单已经下了但还没发货那段时间，对应库存必须被锁定，不能再被其他订单看到——这个动作叫 product reservation，是避免超卖的核心机制。

原文把这三件事概括成一句话：

> "Expose centralized product availability information across fulfillment nodes to all your sales channels, based on imported availability and unprocessed sales as well as current reservations."

这一层做不准，目标加权算得再花哨也是把客户往超卖坑里推。所以 S&A 这个产品包，本质是把"准确的可用性"和"最优的寻源"两件事捆在一起卖——单独装一个寻源引擎接外部库存源，工程上是可以做，但你得自己保证数据一致性，那是另一个项目。

## 这个设计放弃了什么

目标加权模型不是没有代价，至少有三件事要心里有数。

**第一，可解释性弱了一截。** 规则引擎的优势是"为什么这单从 A 仓发"能一句话说清楚——因为命中了第 N 条规则。目标加权下，答案是"四个目标加起来 A 仓总分最高"，但"为什么 A 比 B 高 0.07"客服解释不了。所以这套模型必须配套一个性能监控视图（原文叫 monitor sourcing strategy performance against your business goals），能看到每个目标的达成率、权重的实际效果，而不是只看单条订单的判定。

**第二，权重的初始值是个问题。** 规则可以拍脑袋写，权重不行——给"履约成本"配 0.5 还是 0.3，业务结果差很大。这意味着上线前必须有寻源仿真（Sourcing Simulation）这一步：拿历史订单数据回放，看不同权重组合下的整体表现。S&A 把仿真做进了产品，没仿真直接上权重的项目，第一周必出事故。

**第三，对实时数据管道的要求高了一档。** 规则只看快照，权重要算综合分，必须吃到当前时刻的库存、运能、运价、门店状态。这就是为什么 SAP 把 S&A 放在 BTP 上独立计费、按 Orders Reserved 收钱——它消耗的不是一次查询，是一条持续运行的数据管道。

## 和 Commerce 的接口长什么样

出海的 B2C 项目里，前面常常是 SAP Commerce Cloud（或 Composable Storefront），后面是 OMS。订单从前端流到 OMS 的时点不同，影响很大。

在新的同步订单创建模型里（OMF API 2.1.0 之后），Commerce 不再保留订单副本，订单直接落到 OMF。这时 S&A 的可用性查询会被前端调用——下单页要展示"是否可送达"以及"预计何时到"，调用路径大致是：

```http
GET /availability/v1/inventory
  ?productId=SKU123
  &postalCode=200000
  &channel=B2C_WEB

# 返回：
{
  "available": true,
  "earliestDeliveryDate": "2026-06-04",
  "fulfillmentOptions": [
    { "node": "DC_SH", "stock": 42 },
    { "node": "STORE_PVG_001", "stock": 3 }
  ]
}
```

这个调用必须走得快——下单页面的库存提示是首屏关键路径。S&A 的可用性查询接口因此被设计成读优化的，预聚合后的库存视图直接返回，不去现场算寻源。寻源只在下单确认后才触发，那时调用的是另一组 API：

```http
POST /sourcing/v1/orders/{orderId}/source

# 系统返回 sourcing decision：
{
  "decision": [
    { "lineItem": "L1", "node": "DC_SH", "qty": 2 },
    { "lineItem": "L2", "node": "STORE_PVG_001", "qty": 1 }
  ],
  "reservationIds": ["RSV-..."],
  "scoreBreakdown": {
    "utilization": 0.82,
    "deliveryTime": 0.91,
    "fulfillmentCost": 0.74
  }
}
```

注意 `scoreBreakdown` 这个字段——它是把目标加权的中间评分透出来，给运营和客服看。这就是上面说的可解释性补丁，没有它，业务侧的信任成本会很高。

## 什么样的项目适合上 S&A，什么时候不要碰

**适合的场景**：

- 多渠道、多履约节点（DC + 区域仓 + 门店）的零售或消费品出海企业，履约决策本身就是多目标博弈。
- 已经在用 SAP Commerce Cloud 或在规划 Composable Storefront，需要一个能和前端解耦、独立演进的订单中枢。
- 业务在跨境/全球化运营中频繁调整履约策略（旺季要时效、淡季要成本），需要业务用户自己改权重而不是开 IT 工单。

**不要碰的场景**：

- 单仓发货、品类简单、寻源逻辑只有一两条规则的小盘口业务。这时候 S&A 的能力是浪费，老老实实在 Commerce 或 ERP 里写两条规则更划算。
- 数据底座没准备好的项目。门店实时库存、运能数据、运价表三件事任何一件没接通，目标加权就是空中楼阁，不如先用规则引擎把日子过下去。
- 没有仿真和监控配套预算的实施。只买寻源引擎不买仿真，等于让业务用户在生产上直接调权重——出事概率比规则引擎高得多。

## 实施前要先确认的三件事

- **可用性数据源是否齐全**：DC 库存、门店库存、未处理销售（unprocessed sales / 在途 POS）、预留状态。少一个环节都会让寻源结果不可信。
- **业务目标能否量化**：抽象的"客户体验最佳"没法做权重，必须落到具体指标（如预计到达时间小时数、单均履约成本元）。这一步在售前阶段就要和业务对齐。
- **权重调整的治理流程**：谁有权改权重？改完要不要审批？要不要 A/B 测试？这套流程没建起来，业务部门改一次权重，整个履约成本曲线就抖一次。

订单中枢这一层往独立产品方向走是 SAP 这两年很清晰的动作。S&A 的目标加权模型只是其中一块，背后是 SAP 把"按 KPI 寻源策略"和"中央库存"作为单独可计费能力的产品化判断。这个判断对了，OMS 的故事就成立；对不上，订单这一层就还是 Commerce 或 ERP 的附属物。
