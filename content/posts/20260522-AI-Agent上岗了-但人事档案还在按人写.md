想象一下，公司新来了一批员工，他们不走 HR 入职流程，没有工号，没有直属领导，没人给他们做权限审计。他们的"指纹"是 API key 和 OAuth token，散落在十几个 GitHub 仓库和配置文件里。他们干活比人快几百倍，能在一分钟内调用 SAP S/4 改主数据、再调 Coupa 走采购、最后调 Salesforce 改 deal 状态。年底审计来了，问"这些人是谁、归谁管、做了什么"，IT 主管摸了半天电脑，答不上来。

这就是 SAP Joule、Microsoft Copilot 和各种 RPA bot 现在在 ERP 系统里干的事。SafePaaS 上周发了一篇长文，把这件事的术语叫"非人身份"（Non-Human Identity，NHI）。一个名字，揭开了一个被忽视很久的合规黑洞。

这事的别扭之处在于：SOX 也好，等保也好，过去几十年的内控框架都默认一个前提——动财务系统的，是人。是有名有姓、能签字、能被开除、能被起诉的人。结果 AI Agent 来了，一脚把这个前提踢翻。

## 一个不太恰当但很有用的类比

把 AI Agent 比成"实习生"是个常见的说法，但其实很误导。实习生再不靠谱，也是有学校档案、有合同、有指导老师的。AI Agent 更像一个临时工外包大军——某个项目经理一拍脑袋，让 DevOps 同事在 BTP 上注册一个服务账号，给它绑了 SAP 几十个授权对象，让它跑一个"自动开发票审核"的流程。这个账号没有 owner，没有业务目的描述，没有定期 review，跑了半年没人管。

SafePaaS 那篇文章里有句话挺扎眼："在很多企业里，非人身份的数量已经超过了人。"

> 传统 IAM/IGA 工具能回答"谁能登录哪个系统"，但回答不了"哪个身份——人或 AI——能在 Oracle、SAP、Workday、SaaS 之间执行哪些高风险交易"。这个差别不是细节，是治理模型的代际差。

为什么这事在 2026 年特别紧？因为 SAP 在 Sapphire 上发了 200 多个 AI Agent，Joule Studio 开放给客户自己造 Agent，客户的 Agent 还能挂到 AI Agent Hub 里互相调。每个 Agent 都需要一组权限——访问哪些系统、读哪些表、调哪些 API。如果按现在的"项目经理拍脑袋开账号"模式跑下去，三年后审计师面对的会是一片身份废墟。

## 三个具体的崩坏方式

SafePaaS 把 AI Agent 治理失败的方式分成三类，每一类都有具体的画面感。

**第一类，权限蠕变。** 一个 AI Agent 在生命周期里会经历多次权限调整——上线时给一组、踩坑时再加一组、新增场景时又加一组——但很少有人回头做"权限再认证"。结果就是这个 Agent 的权限只会涨不会减。一年后回头看，它有 SAP 里 60 个授权对象、Salesforce 里 12 个 profile、Coupa 里 8 个 role。哪些还在用、哪些是历史遗留，没人知道。

**第二类，跨系统职责分离失效。** 传统 SoD 检查在单系统内做——不能让同一个人既申请采购单又审批采购单。但 AI Agent 的活儿天然跨系统：在 SAP 里下单、在 Coupa 里审批、在银行接口里付款。如果 Agent 拿到了这条链上每一步的权限，等于一个人拿了所有印章。单系统的 SoD 工具看不见这种横向冲突。

**第三类，没有 owner。** Agent 上线时挂在某个项目的 staging 环境，项目结束后大家各回各家，Agent 还在跑。半年后这个 Agent 用 admin 权限改了一条主数据，触发了线上事故。复盘会上问"这是谁的 Agent"，没人认领。

这三类不是危言耸听。SafePaaS 引用 Federated Governance 报告里一个数字：92% 的可见性缺口——也就是说在大多数企业里，对非人身份的活动，能审计的比例不到 8%。

## 这事跟 SAP CX 客户有什么关系

SafePaaS 那篇文章主体讲的是 ERP 财务侧——SOX 合规、ITGC、ITAC、三单匹配那一套。但 CX 这条线一点也不能幸免，反而更脆弱。

想想看，SAP CX 五朵云加上独立产品，每一朵云都开始装 Agent。Service Cloud V2 里有 Digital Service Agent，Sales Cloud V2 里有 Joule for Sales，Engagement Cloud（原 Emarsys）里有 Send Time Optimization Agent，Commerce Cloud 里有商品推荐 Agent，Loyalty Management 里有积分异常识别 Agent。这些 Agent 跨系统调数据是常态——一个客户服务 Agent 要调 SAP S/4 看订单、调 BDC 看历史行为、调 Engagement Cloud 发触发邮件。

中国出海企业做欧美市场，要应对 SOX、要应对 GDPR 数据访问审计、要应对加州 CCPA。如果一个 Service Agent 在凌晨两点用 admin 权限调取了 5000 条客户主数据，去训练它自己的"客服情感模型"，这事在审计里要怎么解释？谁批准的？为什么是 admin？为什么没有 data scope 限制？

> "AI 现在能做的事，已经超过了你的内控框架能审计的事。这不是技术问题，是治理设计问题。"

SAP 自己也意识到了。Sapphire 上发的 AI Agent Hub 和 Joule Studio Agent Governance 模块，本质上就是想做这件事——给 Agent 上户口。但 SAP 的方案是封闭的：只管 SAP 自家或注册到 Hub 的 Agent。如果客户用了 ServiceNow 的客服 Agent、Salesforce 的销售 Agent、自研的某个 Python Agent，SAP 的治理 Hub 看不见它们。

SafePaaS 的视角是另一个极端：做一个跨厂商的"联邦控制平面"，不管这个 Agent 是 SAP Joule、Microsoft Copilot 还是 Oracle AI Agent，都要进来登记、做 SoD 模拟、跑生命周期管理、走访问认证。这个角度对中国出海企业是有借鉴意义的——我接触过的客户里，没有一家是纯 SAP 栈的，至少都搭着一个非 SAP 的工单系统、CDP 或营销自动化平台。

## 实际能做什么

如果你现在是某个 SAP CX 项目里的架构师或 IT 负责人，AI Agent 落地这件事大概率已经在路线图里了。下面这几件事，建议在 Agent 真正上线之前先做。

- 给每个 AI 用例建一个"Agent 户口"——owner、业务目的、目标系统、数据范围、风险等级。这个表不是 IT 部门内部的，要给审计、风控、业务方都能看。
- 在权限分配前做 SoD 模拟，而不是出事后再查。具体到 SAP CX，至少要看清这个 Agent 在 Sales Cloud + S/4 + Engagement Cloud 三个系统里的累计权限会不会构成业务流程上的角色冲突。
- 给所有 Agent 设强制的"项目结束日"。哪怕是生产 Agent，也要每 6 个月做一次 access certification，让 owner 主动签字续期。
- API key 和 OAuth token 进 vault，不进代码仓库。这个老生常谈，但 AI Agent 时代会被翻倍放大——每个 Agent 都可能拿好几个 token。
- 监控异常行为：一个本来只该读取订单数据的 Agent，突然开始批量改主数据，必须秒级告警。这不是 SAP 标准日志能给到的，得靠专门的工具或自建。

最后留一个开放问题。SAP 想做 Agent 治理的"中央枢纽"，Forrester 的分析师在另一篇文章里已经直接质疑过这个野心——客户该不该把所有 Agent 都注册到 SAP 这个枢纽里？把 Salesforce 的 Agent 拿来注册，相当于把竞争对手的活动也曝光给 SAP。但如果不注册，治理就破碎了。

这道题没有标准答案。但有一点是确定的——再继续按"项目经理拍脑袋开账号"的方式跑下去，2027 年的审计季会很难看。
