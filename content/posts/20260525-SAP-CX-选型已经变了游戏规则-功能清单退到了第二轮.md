买冰箱有两种思路。一种是先翻一本几十页的产品手册，比制冷功率、容积、能耗等级、抽屉数量、是否变频，把每一项打分加总，谁分高买谁。另一种是先量一下厨房——门多宽、电压几伏、左侧那道梁卡不卡、嵌入位预留几公分，把进不去的、电压不对的、风道方向反的先全部划掉，再在剩下的里面挑功能。

**过去十年的 SAP CX 选型，几乎所有项目都是第一种思路。今年开始，它正在被迫切换成第二种。**

5 月 23 日 CustomerThink 上有篇 David Raab 写的短文，题目直接叫做"系统选型不再是选功能"。Raab 这人有点意思，他是 CDP Institute 的发起人之一，过去十几年在 MarTech 圈维护着一份 RFP Generator 工具——就是那种用来生成营销技术选型问卷的小程序。最近他用 vibe coding 平台 Replit 把这个工具重做了一遍，几个小时跑通，但做完他自己也愣了一下：这玩意儿继续按"列功能、勾选项、看覆盖率"的老逻辑往下做，已经没什么意义了。

**他给出的判断很短：今天的系统不再是自包含的功能盒子，每一个新系统都只是更大架构里的一个组件。**

这话在 SAP CX 的语境里，分量比表面看起来重得多。

> 一家中国出海品牌选 Commerce Cloud，过去比的是促销引擎丰不丰富、SKU 上限多少、B2B B2C 是否双形态、Composable Storefront 跑得动几种语言。今年比的，是这套电商能不能跟北美总部已经在跑的 S/4HANA 共用一份订单主数据，能不能把 Engagement Cloud 那条 Marketing 事件总线接到 BTP 的 Event Mesh 上，能不能让欧洲分公司的 OMS 直接读到亚太仓的库存。

![传统选型 vs 现代选型对比](https://customerthink.com/wp-content/uploads/puzzle-1019769_1920-1080x675-pixabay.jpg)

**功能这一栏没消失，只是退到了第二轮。**

第一轮是架构筛。Raab 用了一个词叫 architectural fit——架构契合度。这个词翻成 SAP CX 项目里实际能听懂的话，大概是这么几个具体问题：

- 这个产品是不是站在 BTP 上扩展的，还是另开一个云？
- 主数据走哪边？跟 S/4 之间有没有标准 iFlow？
- 事件总线用哪个？跨产品之间的 event 走 Event Mesh、Engagement Cloud 自己的 streaming 还是第三方？
- 身份与同意流是不是过 CDC（Customer Data Cloud）？
- 数据要不要进 BDC？是 Zero-Copy 接入还是要再 ETL 一次？
- Joule 接进来之后，这个产品的业务上下文怎么暴露给 agent？

这六个问题里随便答错两个，后面 Demo 跑得再漂亮，上线之后都会变成一笔笔运维赤字。我看到的项目里，真正烧钱的从来不是功能买贵了，是架构错配——一个原本可以走标准事件流的方案，硬拼了几条 Custom 集成；一个本可以做 side-by-side 扩展的需求，被塞进 in-app 客制化；一个该用 BTP CAP 写的小程序，被塞进了 Commerce Cloud 的扩展点里。三五年下来，这种系统的升级路径基本就废了。

**Raab 文章里最值得抄下来的一句话是：今天的工具让用户能给买来的系统自己加功能，所以"找到刚好对的那组功能"，反而变得不那么重要。**

这句话放在 2026 的 SAP CX 上，含义更深一层。Joule Studio 已经把 agent 开发能力交到客户手里，BTP CAP/Kyma 把侧扩展模型摆好了，Build Code 让低代码也能挂进治理框架里——意味着客户和 SI 自己就能在产品边上长出新功能。这种长法不是过去那种"客制化魔改产品本体"，而是产品保留 clean core，扩展长在自家工程能力上。

在这种语境下，选 Sales Cloud V2 比选 Sales Cloud V1，最大的差别已经不是"V2 多了哪些 AI 助手"——这些功能你今年没买，明年的版本里也会有。最大的差别是 V2 更靠 BTP，扩展点更标准、API 更可控、跟 BDC 数据产品的对接更原生。买 V2 等于买了一张未来三年都能扩的车票，买 V1 等于买了一辆已经停产的车，零件越来越难找。

> Raab 还轻轻提了一句更扎心的：技术不是选型里唯一重要的事，定价、行业经验、专业服务能力、典型客户规模、本地落地能力都重要——但这些里面，最难量化也最影响成败的，是组织自身的就绪度。

他的原话是：新系统失败的最常见原因，绝大多数时候不在系统本身，在采购方组织内部。

这一点跟 Sapphire 那场关于 Joule 的喧嚣其实是同一回事。SAP 把 200 多个 Agent 摆出来，再多的 Demo 也代替不了客户内部的事：你的主数据干净吗？你的流程定义在系统里有没有跑通？你的业务规则是不是写在了某个老员工的脑子里、PPT 里、Excel 表里？这些东西不解决，再先进的产品装进来都是漂亮的空壳子。

**所以 2026 的 SAP CX 选型，真正该花时间做的三件事，其实和功能清单关系都不大。**

第一件，把现有架构画清楚。出海品牌的总部 ERP 在哪、海外的 OMS 在哪、营销云用哪家、CDP 是不是 Reltio、客服系统跟工单流向 S/4 的哪一段——这张图画不出来，下一步选型就是赌。

第二件，决定哪一层是自己写的。SAP CX 的扩展能力其实非常强，但是不是所有的扩展都该让 SI 包了去？跨境电商客户里我看到几家走得最稳的，是把 storefront 自己接，把 BTP 上的小应用自己写，把核心业务逻辑留在 Commerce Cloud 标准能力里——三层分得很清楚，每一层成本怎么算都明白。

第三件，把组织这一栏的题先答了。运营团队会不会用 Engagement Cloud 的 Loyalty 模块、IT 团队有没有 BTP 的开发能力、数据团队懂不懂 BDC 的 data product 模型——这些不是选型完了再补课的，是选型那一刻就决定了项目能不能跑。

回到开头那个买冰箱的类比。十年前选 SAP CX 像翻产品手册比参数，今天更像先量厨房尺寸。手册没用了么？也不是，只是它从主菜单变成了附录。

这一切发生得不算太快，但也已经不再可逆。
