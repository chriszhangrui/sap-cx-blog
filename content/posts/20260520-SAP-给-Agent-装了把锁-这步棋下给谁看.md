AI Agent 这一年最让人头疼的问题，从来不是它不够聪明，而是它太能干。一个销售助手能改 CRM 字段，一个财务 Agent 能调凭证，一个客服 Agent 能下退款单——它们都在跨应用、跨流程地"动手"，而 IT 团队连"它今天到底干了什么"都说不清。

这个老问题最近有了新进展。Sapphire 上 SAP 和 NVIDIA 把它们之间的合作往下推了一层——不是再搞一个跑分更高的模型，也不是再发一个新 Agent，而是给 Agent 装一套运行时（runtime）的安全骨架。NVIDIA OpenShell 焊进了 SAP Business AI Platform，作为所有 SAP AI Agent 的运行时安全层，包括 Joule Studio 里客户自己开发的那些。

这一步看起来不性感，但它可能比一堆 Agent 发布会都更重要。

## 两层运行时，分别管什么

SAP 的安排很清楚：OpenShell 管"技术上能不能做"，Joule Studio runtime 管"业务上该不该做"。

OpenShell 是 NVIDIA 的开源运行时，逻辑接近容器沙箱：把 Agent 关在一个隔离的执行环境里，对网络访问、文件系统操作都加规则。Agent 想做一个动作，先在沙箱里测试这个动作"安不安全"——如果它逻辑出错或者越权访问，至少别把底层基础设施搞挂。SAP 把这一块叫做基础设施级隔离（infrastructure level containment）。

> 这一层不关心 Agent 想干什么业务动作，它只问一句：你要执行的这条指令，在沙箱规则里允不允许。这是把 Agent 当作不可信代码来对待，跟过去 SAP 对 ABAP 自定义代码的态度完全是两个时代。

Joule Studio runtime 处理另一面——业务权限。这个动作 Agent 真的有权限做吗？它代理的那个用户角色能改这张订单吗？这个改动符不符合公司的业务规则？这一层负责的不是"安全"，是"合规"和"语义正确"。

把两层叠在一起，效果是 Agent 任何一次动作都要过两道闸：技术层先看你是不是越界，业务层再看你是不是越权。中间还要留下可审计的轨迹。

## 为什么 SAP 非得自己下场写代码

这次合作里有一个细节值得多看两眼：SAP 的工程师不是 OpenShell 的"用户"，是 co-developer，会把代码贡献回开源社区。这跟过去 SAP 对待第三方技术的方式不一样。

原因不复杂。Agent 的安全模型不是一个外挂能解决的问题。NVIDIA 懂底层运行时，但 NVIDIA 不知道企业里"采购员能改 PO 但不能改单价超过 10% 的 PO"这种规则该怎么映射到运行时校验。SAP 反过来——它的应用栈最懂业务权限矩阵，但它在 GPU 沙箱、容器隔离这些底层技术上不是专家。

两边谁也单干不成。SAP 拿自己的 ERP/CX 客户当真实场景去喂 OpenShell，把"企业治理到底每天长什么样"这种知识反向写进开源代码里。这是一种很务实的合作姿态——不是写个 PR 稿就完事。

## NemoClaw 接进来意味着什么

SAP 同时把 NVIDIA NemoClaw 集成进 Joule Studio runtime。这一步看上去是给开发者发糖，本质是把"开发出来的 Agent 怎么进生产"这条路修平：从 Agent 模板，到测试环境，到符合企业治理的部署，全程不用开发者自己拼一套安全框架。

这件事对 Joule Studio 里要做自定义 Agent 的客户特别有意义。在我接触过的 SAP CX 项目里，做完一个 PoC Agent 通常 2 到 3 周，但要把它推到生产环境，往往要再多 2 到 3 个月——这两三个月几乎都耗在"怎么证明这个 Agent 不会捅娄子"上。NemoClaw + OpenShell + Joule Studio 这套组合的目标就是把后面这段路压短。

能压到多短，现在还不能下结论。但方向对了。

## 这个方向我看好，但有保留

看好的部分，是 SAP 终于承认 Agent 不是聊天界面的事，是基础设施的事。一个能跨系统执行的 Agent，本质上和过去的接口调用是一类东西，但它没有人类提交工单，没有变更评审，没有 RACI——所以才需要一个新的运行时层来兜住这些原本由组织流程承担的责任。在这件事上 SAP 看得比很多 SaaS 厂商更早、更清楚。

保留的部分有两条。

第一，OpenShell 加 Joule Studio 双层校验，听起来稳，但任何"必经两道闸"的架构都会有性能代价。营销云做实时个性化、服务云做高并发工单分诊，这些场景对延迟敏感。如果每个 Agent 动作都要走两层 runtime 校验，落地时怎么平衡安全和性能，SAP 还没拿出公开的 benchmark。这个数字客户在做选型时一定会问。

第二，企业的业务权限模型千差万别。Joule Studio runtime 怎么知道每家公司"采购员、财务主管、区域销售总监"分别能干什么？这套权限映射是 SAP 自己内置一套通用模板，还是必须每个客户在实施时配？如果是后者，那原本被 SAP 宣传为"开箱即用"的 Agent，可能在治理这一层会拖出一条很长的尾巴。这件事尤其影响中国出海企业——它们的全球总部和各国分公司的权限体系往往不统一，做跨国 Agent 治理时这个尾巴可能更长。

## 给在做选型的人

如果你正在评估 Agent 平台——不管是 SAP 自己的 Joule，还是 Salesforce Agentforce 或 ServiceNow——值得多问几个问题：Agent 的运行时隔离怎么做的？业务权限校验在哪一层执行？审计日志能不能跨系统串起来？这些问题以前在传统应用里都是 IT 安全团队的常规问答，但到了 Agent 时代，很多厂商的产品图上还停留在"我们有 200 个 Agent"这种数量层面。

SAP 这次把答案具体了一些。具体得不够漂亮，但具体本身就是个进步。

至于这套架构能不能真的扛住生产负载、能不能真的让 Agent 大规模上岗——还要等 Q3 之后那批早期客户的反馈。先别急着下定论。
