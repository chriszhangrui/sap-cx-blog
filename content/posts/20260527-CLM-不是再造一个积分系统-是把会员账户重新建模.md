先看一个看似平常的实施场景：客户原本只有一个零售积分计划，半年后业务部门要加一个高端会员计划，再过三个月又要做一个跨品牌的联名计划。在传统 loyalty 系统里，这意味着每个计划单独建一套规则、单独建一张积分表、单独维护一份等级配置。会员同时参与三个计划，到底是同一个人还是三个独立账户，没人说得清。

这正是 SAP Customer Loyalty Management（以下简称 CLM）这次重新建模要解决的问题。它不是把传统 loyalty 引擎搬上云，而是把数据中心从 program 搬到会员个人。

## 把数据主键从 program 换成 member

2025 年的 SAP Commerce Cloud 与消费者行业年度回顾里，对 CLM 的描述只有一段话，但信息密度很高。原文写道：CLM 把客户数据和会员行为捕获到一个 cloud-based wallet（云端钱包）里，这个 wallet 充当 loyalty profile（会员档案）；平台支持多种 loyalty model 在一个统一界面里管理；与 SAP Cloud ERP Private、SAP Business Suite 集成，让 loyalty 相关的财务指标可见，营销团队可以追踪 promotion performance、redemption rates 和 liabilities。

关键词是 wallet 和 loyalty profile。中文翻译成"会员档案"很容易误读成 CRM 里的客户主数据。要做的区分是：传统 loyalty 系统里，program 是一等公民——零售积分计划、高端会员计划、联名计划是三张独立的表，每张表挂着自己的会员、积分余额、等级状态。CLM 倒过来：member 是一等公民，program 退化为 wallet 上的一个属性维度。

这个差别看上去抽象，落到实施上就是建模顺序的反转。以前先定义 program → 配规则 → 收会员，新建一个计划等于新建一个数据世界。CLM 的顺序是先有会员 wallet → 在 wallet 上挂载 program 实例 → 每个 program 实例只是 wallet 上的一段状态。新增一个计划不动数据模型，只动配置。

## wallet 里到底装了什么

从原文给出的功能描述反推 wallet 的数据结构，至少包含五段状态：

- **points_balance[]**：跨 program 的多个积分余额。一个会员在零售计划里 1200 分、在跨品牌计划里 350 分，是同一个 wallet 上的两条记录，不是两个账户。
- **tier_state[]**：每个 program 的当前等级、晋升进度、降级倒计时。等级是 program 的属性，不是会员属性。
- **vouchers[]**：未核销券、已核销券、过期券。券有自己的生命周期，但归属于 wallet 而非 program。
- **activity_log**：所有积分获得、消耗、调整的事件流。这是营销团队追踪 redemption rates 的源数据。
- **liability_total**：会员未使用积分对应的财务负债额度。这是 ERP 集成的核心字段。

把这五段写成大致的 schema：

```
LoyaltyProfile (Wallet) {
  member_id: UUID                      // 会员唯一标识
  external_ids: [{system, id}]         // 跨系统 ID 映射
  points_balance: [{
    program_id, currency, balance,
    expiring_soon, last_activity
  }]
  tier_state: [{
    program_id, current_tier,
    progress_to_next, retain_until
  }]
  vouchers: [{
    voucher_id, type, valid_until,
    redeemed_at, value
  }]
  activity_log: [{
    event_type, source_system,
    delta, ts, ref_order_id
  }]
  liability_total: { amount, currency }
}
```

注意 external_ids 这个字段。CLM 不是孤立运行的，它要从 Commerce Cloud、Engagement Cloud（原 Emarsys）、CDC、线下 POS 同时收集会员行为，每个系统对同一个人有自己的主键。wallet 必须先解决身份归一，再谈积分。这一步如果偷懒（比如只用邮箱做主键），跨渠道场景下会员状态就会分裂——同一个人在 App 里是金卡、在网站里是普通会员，业务方第二天就来投诉。

## 为什么必须接到 ERP

原文说 CLM 与 SAP Cloud ERP Private、SAP Business Suite 集成，目的是让 loyalty-related financial metrics 可见。这个表述很克制，但底下藏着一条会计规则：会员手里没用的积分，对企业是负债，不是收入。

国际会计准则（IFRS 15）把客户激励积分定义为合同负债（contract liability）。会员花 100 元买东西，如果送 10 积分，企业拿到的实际不是 100 元收入，而是 100 元里减掉积分公允价值后的部分作为收入，剩下的部分挂在负债账上，等会员兑换或过期再确认收入。这套机制对小型工具型 loyalty 系统是噩梦——它根本没有合适的字段往 ERP 推数。

CLM 的设计上，liability_total 是 wallet 上的一等字段，不是事后算出来的报表。每次 points_balance 变动，liability_total 同步变动，再通过集成层推到 S/4HANA 的负债科目。这才是为什么原文要专门强调"营销团队可以追踪 promotion performance、redemption rates 和 liabilities 这三件事"——前两个是营销视角，第三个是财务视角，技术上都从同一个 wallet 出来。

实施层面，过去靠 CPI（Cloud Platform Integration）把积分确认事件回写 S/4 已经讲过，这次的角度是：积分发出去、积分使用、积分过期，这三个事件中至少要有两个能改 liability_total。如果只回写"积分使用"忽略"积分过期"，财务上的负债会越积越多，年终审计时会出问题。

## "统一界面管多种 loyalty model"意味着规则引擎独立

原文提到 CLM 在一个统一界面里支持多种 loyalty 模型。能这么做的前提是规则引擎和 wallet 解耦——wallet 只存状态，规则引擎只算变化。

实操上规则配置大概是这种粒度：

```
Rule {
  trigger: "order.completed"
  conditions: [
    { field: "order.amount", op: ">=", value: 500 },
    { field: "member.tier", op: "in", value: ["gold","platinum"] }
  ]
  actions: [
    { type: "earn_points",
      program_id: "RETAIL_2026",
      formula: "order.amount * 2" },
    { type: "issue_voucher",
      voucher_template: "WELCOME_BACK_50" }
  ]
}
```

规则是 program 级配置，wallet 是会员级状态。新增一个计划等于加一组规则，wallet 字段不动。这是 CLM 跟传统 SAP CRM Loyalty Management（基于 SAP CRM 7.0 BAdI 出口扩展）和 Emarsys 内置 Loyalty 模块（基于 contact list 与 Smart Insight）都不一样的地方——前两者本质都是"在已有客户表上挂积分字段"，CLM 是"先建钱包、再挂规则、再连 ERP"。

## 什么样的项目适合用，什么时候不要碰

从架构判断回到落地建议。CLM 这套模型并不是所有项目都需要。

- **适合用**：跨品牌 / 跨地区运营的零售集团，会员在多个子品牌之间流转；航旅或酒店集团这种本身就是多 tier 多伙伴的业态；出海品牌需要把线上线下、海外多市场会员合并管理；财务部门对积分负债在内部审计或 IFRS 报表上已经吃过亏的企业。
- **暂时不要碰**：单 program 单品牌的小规模业务，wallet 模型相对单 program loyalty 系统是过设计；只想做一个营销活动级别的"满减券计划"，CLM 太重；ERP 还停留在不能接受 API 实时回写的版本（比如本地老 ECC 没有合适集成中间件），先把 ERP 集成层准备好再上 CLM，否则 liability 那条链就是断的。
- **踩坑警示**：实施第一阶段最容易低估的是身份归一。external_ids 必须在第一个 program 上线之前就设计好，等会员数据进了 wallet 再回头改主键策略，迁移成本会很高。第二个常见坑是"先做 program 配置、留 ERP 集成到第二阶段"——这等于让营销侧先发积分，财务侧后算账，过渡期账目对不平。两条线必须同期走通。

CLM 这次发布的真正价值不在功能清单，而在它选择的数据模型方向。把 program 降级、把 member 升级、把 liability 拉到一等字段——这是为复杂 loyalty 业态留出来的扩展空间，不是为单一计划设计的工具。
