客服 AI 这件事，过去十年的承诺基本没变过——"AI 来接电话，你的客服就解放了"。多数项目最后落地的是一个让客户更想骂人的聊天机器人，加一块没人看的仪表盘。

Service Cloud V2 选了另一条路。它不在前台放一个机器人去跟客户硬聊，而是把 AI 装在客服身后，做的是分类、路由、摘要、起草。客服还坐在那里，但他们处理一个 case 时手上的工具变了。Joule Studio 在 2026 年 Q1 进入 GA 之后，这条路线又往前走了一步——你可以自己定义一个 Agent，让它在人接手之前去 S/4 里把保修信息查清楚。

这套设计到底好不好用，得拆开看。

## Joule 在 V2 里默认提供的五件事

![Service Cloud V2 Joule 架构](https://www.spadoom.com/blog/heroes/sap-service-cloud-v2-digital-service-agent.webp)

SAP 在 2026 年公布的数字是：350+ AI 能力、2400+ Joule skill，分布在整个云组合里。落到 Service Cloud V2，目前可用且有客户在用的，是下面这五件。

**第一，实时情绪分析。** 每一条进来的消息——邮件、聊天、Web 表单——都会被实时打标签。和老一套的"正向/负向"二分法不太一样的是，Joule 跟踪的是**对话级情绪轨迹**：客户开头还心平气和，三轮之后突然急了，系统会标出这个拐点并自动调整 case 优先级。在 B2B 场景里，这件事的价值很直接——一个大客户一年贡献六七位数收入，能在客户写邮件给他的 Account Manager 之前发现情绪滑坡，就是真金白银。

**第二，基于机器学习的 case 路由。** 这是 V2 跟 V1 之间最值得说的一处架构改动。V1 的路由是写死的规则——"产品=X 且 Region=EMEA → 派给 Team A"。组织一调整、有人休假、新产品线一上，规则就崩。V2 的路由模型会综合 case 内容、客户历史、客服技能、当前负载、历史解决记录这些维度，把 case 派给"**历史上解决过类似 case 最快的人**"，而不是技能矩阵里挂着 "ERP" 标签的任何一个人。原文里提到一个客户在切换 ML 路由后，case 重新分派率（reassignment rate）下降了 35%。

**第三，回复草稿建议。** 客服打开 case，AI 已经基于 case 描述、分类、客户历史、相似已解决 case、相关知识库文章这五个输入起草了一份回复。常见类问题（订单状态、配置、已知 bug）的草稿基本 80–90% 可用，复杂 case 也至少给一个有结构的起点。

**第四，case 摘要。** B2B 工单常常拖好几周，30 条消息、内部备注、三次交接是常态。Joule 会生成结构化摘要——客户报告了什么、试过什么、还开着什么、目前停在哪一步。一个新接手的客服 30 秒就能拿到上下文，不需要花 15 分钟翻线程。

**第五，知识库文章推荐。** 分类的同时把相关 KB 文章推给客服。这个能力的天花板完全取决于知识库本身的质量——文章过期、标签混乱、内容残缺，推荐就是噪音。

## Joule Studio：当默认能力不够用的时候

上面五件事覆盖了大约 80% 的常规场景。剩下 20% 是每家公司自己独有的工作流——这部分原来的处理方式是定制开发或 BPM 流程，现在 Joule Studio 给了另一个选项。

Joule Studio 在 2026 年 Q1 GA。它本质是一个让你定义"自定义 Agent"的开发环境：你声明这个 Agent 干什么、能访问哪些数据、能采取哪些动作，Studio 负责把它接进 Service Cloud V2 的 case 处理链路。不需要从零训练 ML 模型。

原文里给了一个很具体的保修核查 Agent 例子。某制造业客户每周收 200+ 保修索赔，原本流程是客服打开 case、读索赔内容、拿产品序列号去 S/4HANA 里查购买日期、保修状态、过往服务记录——光这一步就要 4–6 分钟。换 Studio 之后的逻辑变成这样：

```
读取 case → 抽取产品序列号
   ↓
通过 BTP Destination Service 调 S/4HANA
   ↓
拿到购买日期 / 保修状态 / 历史索赔
   ↓
对照保修条款（保修期、免责、索赔上限）做规则校验
   ↓
回写 case：附上保修核查摘要

人工客服打开 case 时，结论已经在那里了
```

结果是保修类 case 平均处理时间从 12 分钟降到 5 分钟以下。客服的工作从"查数据"变成"和客户沟通"——这是 AI 真正应该接管的那部分。

## 架构上的一个判断：为什么 V2 选 "AI behind the agent"

如果只看市场宣传，所有云厂商讲的都是"AI Agent 端到端解决客户问题"。Service Cloud V2 在产品层做的取舍其实更现实——B2B 服务里的复杂 case（多系统问题、合同纠纷、多干系人升级）需要人的判断、共情和领域知识，这些东西今天的 AI 替不了，硬替的代价是客户体验崩盘。

SAP 的策略不是"让 AI 顶到前台"，而是**把 AI 嵌进客服的每个动作**。客服打开 case 看到的是已经分类好的 case、已经路由对的队列、已经写好初稿的回复、已经被压缩成几行的历史。客服点的是 "Send"，不是从空白文本框开始。

差异跟谁比？跟 Salesforce Service Cloud 的 Agentforce 路线比，SAP 的 Joule 更克制——内置能力围绕"分类/路由/摘要/建议"这四件事打磨，自定义 Agent 通过 Studio 走，且明确告诉你这是 low-code 不是 no-code。

## 什么样的项目适合上，什么时候不要碰

- **适合：** 已经在用 Sales Cloud V2 / Service Cloud V2，BTP entitlement 已开，主数据干净的 B2B 服务团队。先开五件内置能力，3–4 周可上线。
- **适合：** 跨境制造、有 S/4HANA 后台的工业品企业——保修核查、订单状态查询、配置咨询这类强数据查询场景，Joule Studio 自定义 Agent 收益最直接。
- **适合：** 在华外企的总部对接客服、跨国 SI 项目里负责 Service 模块的团队。
- **不要碰（暂时）：** 知识库一团糟、SOP 没整理、案例分类标签随意填的团队。garbage in, garbage out 这件事 AI 没改变。
- **不要碰：** 纯内贸、没有 BTP / AI Foundation entitlement、没有 S/4 集成预算的客户。Joule 需要单独的 SAP AI Foundation 授权，不是 Service Cloud V2 订阅自带的。

## 几个容易踩的坑

> **坑 1：** 把 Joule Studio 当 no-code 卖给客户。营销话术写的是 "build AI agents without coding"，落地时你需要懂 BTP 集成、数据模型、工作流设计的人。可以不写 Python、不训练模型，但不能没有技术底子。

> **坑 2：** 没有反馈机制。回复建议是基于历史 pattern 的，客服如果照单全收坏建议、不去标记，模型不会自己变好。

> **坑 3：** 分类准确率的预期。开局 70–80% 是正常的，靠客服三四个月持续纠错才能爬到 85–90%。
