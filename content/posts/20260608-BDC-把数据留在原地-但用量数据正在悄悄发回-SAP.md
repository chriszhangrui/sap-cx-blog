# BDC 把数据留在原地，但用量数据正在悄悄发回 SAP

Linda 是一家中国家电出海品牌的全球营销总监，每周一早上做的第一件事是把过去七天的渠道数据拉到一起：BDC 里有订单和退货，Databricks 里堆着站内搜索日志、广告投放和客服 NPS。她要的并不复杂——一张能说明欧洲市场上周转化率为什么掉了的图。流程上她要先让数据团队把 BDC 数据导出成 Parquet 上传到 Databricks，第二天再开会讨论。这种"等明天"的节奏，在一个 AI Agent 已经能 24 小时盯盘的世界里，越来越像在等绿皮火车。

现在有人在试图把这趟火车换掉。Databricks 在 6 月 3 日更新了一篇官方文档，正式介绍 SAP BDC Connector for Databricks——双向、零拷贝、走 Delta Sharing。这一步比想象中关键，但藏着的细节也比想象中多。

## 所谓零拷贝，到底零在了哪一段

SAP 这两年讲零拷贝讲得很多，先是 Snowflake、再是 AWS、然后是 Databricks。普通听众容易把它当成口号，但它真正改写的是企业数据的物理位置。Databricks 这次的文档把链路画得很清楚：BDC 里的 Data Product 通过 Delta Sharing 协议，被 Databricks 端的 Unity Catalog 直接挂载成一张可查询的表。数据从来没有离开 BDC 所在的存储，Databricks 这边读的是一个授权的"实时窗口"。

这意味着 Linda 那位数据工程师再也不需要写每天凌晨三点的 ETL 任务。但更重要的不是省了那个工程师的 ETL 工时，而是 BDC 里那张订单表上的字段注释、主键外键关系、治理 Tag——所有这些语义信息——会自动同步到 Unity Catalog。Databricks 那边的分析师在 Catalog Explorer 里点开这张表，能直接看到"客户 ID"对应的是 SAP S/4 里的哪个对象，能看到这张表的数据敏感级别是什么。

这条链路也是双向的。Databricks 上跑出来的客户分群结果、ML 模型预测，可以反向写回 BDC 当作 Data Product 暴露给 Joule Agent、SAP Engagement Cloud (Emarsys)、Sales Cloud V2。SAP 的 Agent 拿到的不再只是 ERP 里的事实数据，而是已经被 Databricks 加工过的洞察。这一层对客户体验产品线来说才是关键——因为那一侧的 Agent 真正缺的从来不是数据，而是 ready-to-use 的洞察。

## 藏在脚注里的那一行：用量数据回传 SAP

Databricks 的文档里有一段话写得很克制，但意思非常硬：

> 如果你选择用 SAP BDC Connector 把 BDC 数据共享到 Databricks，Databricks 可能会向 SAP 披露与你使用该数据相关的一些用量与运行信息，包括以非聚合、非匿名、按工作负载维度的方式标识你的组织。

具体披露什么？BDC 数据量、BDC 数据与非 BDC 数据的占比、工作负载执行的日期时间、以及"你的组织在 Databricks 上的有效单价"。这是计费需要——SAP 要按 BDC 数据被消费的程度来收费——但它的副作用是 SAP 第一次有了一个稳定的窗口，能看到客户在 Databricks 上跑了什么样的 AI 工作负载、跑了多少。

这不是隐私问题，企业级数据共享本来就是双向的合同。但对于做出海的中国企业总部来说，这件事在签约前就要想清楚一个问题：你在欧洲跑的数据负载里，有多少 BDC 占比、定价是什么——这些信息现在会被 SAP 看到。GDPR 谈判桌上多了一行细节。

## 语义元数据自动同步，听起来像配菜但其实是主菜

表注释、列注释、主键、外键、治理 Tag——这些东西过去从 SAP 系统出来就丢失了。导到湖仓里的是一张张光秃秃的表，分析师要花大量时间去问 SAP 那边"这个 KUNNR 是什么意思""这两张表怎么 join"。Databricks 这次把这部分元数据接进了 Unity Catalog，分析师拿到的是带语境的数据。

Genie Spaces 是 Databricks 自己的自然语言查询工具。当 BDC 的语义结构同步过来之后，分析师对 Genie 说"上周欧洲渠道下单后退货的客户主要在哪个国家"，Genie 知道客户、国家、订单、退货这些概念之间在 SAP 那边的真实关系。语义没了，AI 答的就是猜的；语义在了，答案才是基于业务模型的推理。

这件事跟 SAP 自己讲的 Knowledge Graph 是同一个问题在两侧的解法。SAP 在自己这边搭 Knowledge Graph，让 Joule Agent 能理解业务语义；现在它把语义包同时打包送到 Databricks 那边的 Unity Catalog——这才是为什么 SAP 要押宝 Databricks 而不是自己造一个数据湖。

## 如果这条链路真落地了，Linda 的周一早晨

回到开头。Linda 不再需要等数据团队跑 ETL。她在 Databricks 上打开 Genie，问"为什么上周德国市场转化掉了"。Genie 拉的是 BDC 里实时的订单数据加上 Databricks 里实时的广告投放数据，两边都带着完整的语义信息。30 秒后，她看到一个候选结论：上周三某个 SKU 的退货率突然飙升，触发了客服系统里 178 张工单——这部分客服数据是通过 Engagement Cloud (Emarsys) 进入 BDC 的——而退货又被 Sales Cloud V2 的 Joule Agent 标注成"产品质量问题"。

她不需要召开周一会议。她直接把这个发现转成一封邮件给德国分公司的产品经理。三十分钟前发现，三十分钟后行动。

前提是这套架构真跑得起来。当前的 Databricks 文档讲的是连接器机制，签约和成本结构对中国出海企业来说是另一个赛道——你的 BDC 部署区域、Databricks 集群所在云厂商、跨区数据传输的合规口子，都决定了这条链路能不能在欧洲、东南亚、拉美各跑一条。

技术地基在 6 月 3 日已经铺好。剩下的事，是商业。
