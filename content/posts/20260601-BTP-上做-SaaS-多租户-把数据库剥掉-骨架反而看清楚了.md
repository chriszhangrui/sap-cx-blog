SAP 在 BTP 上做 SaaS，最容易踩的不是写不出业务逻辑，是搞不清楚一笔订阅请求到底走过了哪几个组件。

最近看到一篇实战博客，作者把 CAP 多租户应用做了一个极简版：不挂数据库、不搭 HANA、只保留多租户必需的那几样东西。剥到这个程度之后，BTP 上 SaaS 的真正骨架就显出来了——这正是想看清楚 CAP 在侧扩展架构的好材料。

## 从无数据库版本切入，反而看得最清楚

大多数 CAP 教程的多租户示例，开头就上 HANA、配 MTX（Multitenancy and Extensibility Toolkit）、做 Schema 隔离。这些东西很重要，但它们把多租户这件事的本质遮住了——你看到的是 HANA 在做 schema 创建，不是 BTP 在做租户路由。

把数据库去掉之后，BTP SaaS 真正剩下的只有三个组件：Approuter（请求入口与租户识别）、XSUAA（多租户 JWT 鉴权）、SaaS Registry（订阅生命周期管理）。这三件东西一旦理清楚，再加 HANA、加 MTX、加 Fiori，都只是往这个骨架上挂业务模块而已。

![CAP多租户架构](https://community.sap.com/t5/image/serverpage/image-id/405973i43A4845F84FEF3BC/image-size/large?v=v2&px=999)

## 第一道关：Approuter 怎么知道这笔请求属于哪个租户

SaaS 应用在 BTP 上跑，所有租户共享同一份代码、同一个 Approuter 实例、同一个 XSUAA 绑定。请求一进来，必须先识别出"这是哪个租户在调"，才能找到对应的 identity zone 去解 token。

CAP/Approuter 用的方法是把租户标识放进 hostname 的 subdomain。配置项叫 `TENANT_HOST_PATTERN`，本质上是一个正则：

```yaml
properties:
  TENANT_HOST_PATTERN: "^(.*)-${org}-${space}-${app-name}.${default-domain}"
  SAP_JWT_TRUST_ACL:
    - clientid: "*"
      identityzone: "sap-provisioning"
```

部署到 Trial 上 org 是 `7ce04bc6trial`、space 是 `dev`，Approuter 的 FQDN 就是 `7ce04bc6trial-dev-cap-saas-approuter.cfapps.us10-001.hana.ondemand.com`。当 subdomain 为 `consumer` 的租户访问，完整 URL 是：

```
https://consumer-7ce04bc6trial-dev-cap-saas-approuter.cfapps.us10-001.hana.ondemand.com
```

Approuter 拿正则去匹配 hostname 的第一段，把 `consumer` 提取出来当作租户 subdomain，再交给 XSUAA 去找对应的 identity zone。整个识别过程发生在请求到达任何业务代码之前。

## 订阅生命周期：SaaS Registry 是怎么把租户接进来的

SaaS Registry 是 BTP 上托管的服务，专门负责订阅。在 mta.yaml 里以 managed-service 形式声明，关键不是它本身，而是 `appUrls` 这一段：

```yaml
resources:
  - name: cap-saas-app-registry
    type: org.cloudfoundry.managed-service
    requires:
      - name: srv-api
    parameters:
      service: saas-registry
      service-plan: application
      config:
        xsappname: cap-saas-app-xsuaa
        appName: cap-saas
        appUrls:
          onSubscription:   ~{srv-api/srv-url}/callback/v1.0/tenants/{tenantId}
          onUnSubscription: ~{srv-api/srv-url}/callback/v1.0/tenants/{tenantId}
          getDependencies:  ~{srv-api/srv-url}/callback/v1.0/dependencies
```

非常关键的细节：appUrls 指向的是 srv（CAP 服务），不是 Approuter。SaaS Registry 调订阅回调是直接打到业务服务上的，绕过 Approuter 的鉴权链路——它用的是 BTP 平台层的 `sap-provisioning` 租户身份。

## CAP 的 bootstrap 钩子：在 OData 之外开两个原生 Express 路由

CAP 默认是 OData 服务，订阅回调却是 REST。两套路由怎么并存？答案是 `cds.on("bootstrap", ...)`——这个事件在 Express app 创建之后、CAP 中间件挂载之前触发，正好是注册裸 Express 路由的窗口。

```javascript
const cds = require("@sap/cds");
const express = require("express");

cds.on("bootstrap", (app) => {
  app.use(express.json());

  // 订阅：必须返回租户对应的 Approuter URL，作为纯字符串
  app.put("/callback/v1.0/tenants/:tenantId", async (req, res) => {
    const { tenantId } = req.params;
    const subscribedSubdomain = req.body?.subscribedSubdomain || tenantId;
    const approuterFQDN = (process.env.APPROUTER_FQDN || "")
      .replace(/^https?:\/\//i, "")
      .replace(/\/+$/, "");
    const tenantUrl = `https://${subscribedSubdomain}-${approuterFQDN}`;
    res.status(200).send(tenantUrl);
  });

  app.delete("/callback/v1.0/tenants/:tenantId", async (req, res) => {
    res.status(200).send(`Tenant ${req.params.tenantId} unsubscribed.`);
  });
});
module.exports = cds.server;
```

项目里反复犯的错：订阅回调返回的 URL 必须是 Approuter 的 URL，不能是 srv 的 URL。原因是 SaaS Registry 把这个 URL 存下来，作为消费者将来访问应用的入口——而 srv 应用本身不带登录处理，XSUAA 的 OAuth flow 全在 Approuter 一侧。返回 srv URL 的话，租户后续打开链接就直接 401。

## 业务代码这一层：tenant 是怎么"自动出现"在 req 上的

真正写业务逻辑的时候，CAP 把多租户的复杂度全部抽象掉了。`req.tenant`、`req.user`、`req.locale` 是 CAP 在 XSUAA token 校验通过之后自动填进去的，不需要手工解 JWT：

```javascript
// srv/info-service.cds
@requires: 'authenticated-user'
service InfoService {
  function getSubaccount() returns String;
}

// srv/info-service.js
module.exports = cds.service.impl(async function () {
  this.on('getSubaccount', async (req) => {
    const tenant = req.tenant || 'unknown';
    const user   = req.user?.id || 'anonymous';
    const locale = req.locale || 'en';
    return `Tenant: ${tenant} | User: ${user} | Locale: ${locale}`;
  });
});
```

CAP 的自动绑定靠的是文件名约定：`info-service.cds` 和 `info-service.js` 同名，CAP 启动时会自动配对。文件名不一致，运行时抛 `501 No handler`——另一个项目里反复出现的坑。

## 几条容易翻车的细节

- `xs-security.json` 里 `tenant-mode: shared` 必须打开，否则 XSUAA 实例只能服务单租户，订阅根本接不进来。
- `redirect-uris` 必须用通配符覆盖所有可能的 Approuter 地址（`https://*.cfapps.us10-001.hana.ondemand.com/login/callback`），否则租户回跳时 OAuth flow 失败。
- BTP Trial 上不开放 wildcard 路由，每订阅一个租户都要手工 `cf map-route` 一次。生产环境（CF 商业账户）才有 routing service 自动做这件事。这是判断"演示环境"和"生产环境"的硬性差异。
- Approuter 上的 `SAP_JWT_TRUST_ACL` 要写明信任 `sap-provisioning` identity zone，否则 SaaS Registry 调过来的请求会被 Approuter 拒掉。

## 什么场景值得这么搭

无数据库的 SaaS 骨架，最适合的是合作伙伴在 BTP 上做"轻应用型扩展"：核心数据还在 S/4 或 Sales Cloud V2 里，BTP 上跑的只是租户感知的 UI 层、规则引擎、或者把外部 SaaS（比如 Engagement Cloud）的事件接进来做编排。出海企业里见过的几个真实场景，都是这个形态——业务系统已经在用 SAP，要给不同子公司或品牌做差异化的扩展逻辑，但又不想为每个租户单独跑一套实例。

不适合的场景也清楚：应用本身就是数据密集型（订单、主数据、客户档案这一类），租户隔离一定会落到 HANA Schema 或独立 HDI Container 上，那就回到 MTX 的标准路线，无数据库版本帮不了你。

真正值得从这篇博客里抽出来的是一句话：BTP 上的多租户能力，本质上是 Approuter + XSUAA + SaaS Registry 三件事的组合，CAP 只是把这三件事用 Node.js/Java 的开发体验包了一层。读懂这个骨架，CAP Operator、MTX、Kyma 上的 SaaS Operator 都只是同一个抽象在不同 runtime 下的换皮。
