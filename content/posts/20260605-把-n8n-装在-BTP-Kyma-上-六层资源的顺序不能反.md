本地一行 docker run，n8n 就能跑起来。装在自己电脑上自己用，没毛病。

问题是企业用——团队几十个人共享、要 7×24 在线、要和 SAP 后端对接、容器一重启工作流不能没——本地那套就立刻撑不住。

很多人第一反应是"找台云主机装上 Docker 不就行了"。能跑，但代价是你自己运维这台机器：磁盘、备份、TLS 证书、域名、重启策略，每一项都得自己接住。当一台 EC2 / ECS 变成团队的生产工具，运维量就开始失控。

SAP BTP（Business Technology Platform）的 Kyma runtime 是另一条路：托管的 Kubernetes，控制平面 SAP 来管，你只管把 workload 丢上去。今天这篇拆的就是这条路——把 n8n 部署到 Kyma 上，**不只是把容器跑起来，而是把"企业级"的几层资源摆对顺序**。

## 为什么是 Kyma，不是自己装一个 K8s

Kyma 不是 SAP 自己造的 K8s 发行版，它就是上游 Kubernetes，加上一层 Istio 服务网格、Oathkeeper 访问控制、还有 Serverless / Eventing / Application Connectivity 这些 SAP 加的扩展。你拿 kubectl 进去，看到的就是标准的 Pod / Service / Deployment / PVC。

关键差异有三点：

- **控制平面托管**。集群升级、API server 高可用、etcd 备份这些活 SAP 干，你只对 Worker Node 上跑的东西负责。
- **外网入口零配置**。Kyma 起手就给你一个 `*.kyma.ondemand.com` 的二级域名 + 自动 TLS，不用你去搞 cert-manager 和域名解析。
- **就近 BTP 服务**。和 SAP AI Core、HANA Cloud、Destination Service 在同一个 BTP subaccount 下，调用走内网，鉴权用 BTP 自己的身份体系。

代价是你失去了一些底层自由度——节点池规格选择有限，能装的 CRD 受 SAP 策略约束。但对一个跑 n8n、跑 CAP（Cloud Application Programming Model）、跑各种 BTP side-by-side extension 的团队，这个 trade-off 通常是划算的。

## 六层资源的部署拓扑

先把全貌摆出来。一次部署，从浏览器到容器，要落地的资源有六层：浏览器 → APIRule（Istio + Oathkeeper 网关）→ Service（n8n-service，selector 锁 Pod）→ Deployment / Pod（n8nio/n8n:latest 镜像）→ PVC（5Gi 持久化）+ Secret（N8N_ENCRYPTION_KEY）。

看着不复杂，但**顺序不能反**：PVC（PersistentVolumeClaim 持久化存储声明）和 Secret 必须先于 Deployment 创建，Service 必须先于 APIRule 配置。

## 第 0 步：把 BTP Cockpit 和 kubectl 接上

在 SAP BTP Cockpit 进 subaccount，左侧找到 Kyma Environment，点 Enable Kyma。SAP 后台会花几分钟把集群拉起来，状态从 Provisioning 变成 Created，对应的 Dashboard 链接和 KubeconfigURL 就出来了。

把 kubeconfig 下载到本地，比如 `~/.kube/kyma-config.yaml`，然后告诉本机 kubectl 用它：

```bash
export KUBECONFIG=~/.kube/kyma-config.yaml
kubectl get nodes
```

能列出 Worker Node 列表（Status: Ready），就说明本机已经在跟 SAP 云上的 K8s API server 通话了。

## 第 1 步：Namespace + PVC

```bash
kubectl create namespace n8n
```

n8n 的工作流定义、保存的凭据、执行历史、配置——**全部写在容器本地磁盘上**。容器一重启数据没。在 K8s 里 Pod 重启是常态，所以 PVC 必须先 apply：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: n8n-pvc
  namespace: n8n
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
```

```bash
kubectl apply -f n8n-pvc.yaml
kubectl get pvc -n n8n
```

看到 STATUS 是 Bound 才算落实。

## 第 2 步：那把"决定一切"的密钥

n8n 在保存任何凭据时都会先用 `N8N_ENCRYPTION_KEY` 这个环境变量做对称加密。**这把密钥丢了，存过的所有凭据就全废了**。

```bash
openssl rand -hex 32

kubectl create secret generic n8n-secret \
  --from-literal=N8N_ENCRYPTION_KEY='<your-generated-key>' \
  -n n8n
```

不要把这把 key 写进任何提交到 Git 仓库的 YAML 文件。

## 第 3 步：Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: n8n
  namespace: n8n
spec:
  replicas: 1
  selector:
    matchLabels:
      app: n8n
  template:
    metadata:
      labels:
        app: n8n
    spec:
      securityContext:
        runAsUser: 1000
        fsGroup: 1000
      containers:
        - name: n8n
          image: n8nio/n8n:latest
          env:
            - name: N8N_ENCRYPTION_KEY
              valueFrom:
                secretKeyRef:
                  name: n8n-secret
                  key: N8N_ENCRYPTION_KEY
            - name: N8N_HOST
              value: "<your-kyma-domain>"
            - name: WEBHOOK_URL
              value: "https://<your-kyma-domain>/"
            - name: N8N_PROTOCOL
              value: "https"
            - name: N8N_PORT
              value: "5678"
          volumeMounts:
            - name: n8n-data
              mountPath: /home/node/.n8n
      volumes:
        - name: n8n-data
          persistentVolumeClaim:
            claimName: n8n-pvc
```

几个细节值得停一下：

- `runAsUser: 1000 / fsGroup: 1000`：n8n 镜像里用的是非 root 的 node 用户，这两行确保挂载进来的 PVC 文件夹权限对得上。
- `N8N_ENCRYPTION_KEY` 用 secretKeyRef 注入，不要直接写明文。
- `N8N_HOST / WEBHOOK_URL` 要填 Kyma 实际域名，比如 `n8n.abc1234.kyma.ondemand.com`。

## 第 4 步：Service

Pod 的 IP 是临时的，每次重启都会变。Service 是 K8s 给一组 Pod 套的稳定壳。

```yaml
apiVersion: v1
kind: Service
metadata:
  name: n8n-service
  namespace: n8n
spec:
  selector:
    app: n8n
  ports:
    - port: 80
      targetPort: 5678
```

`selector: app: n8n` 必须和 Deployment 模板里 labels 的 `app: n8n` 完全对得上。

## 第 5 步：APIRule

进 Kyma Dashboard，左侧 Networking → API Rules → Create：

- Service 选 `n8n-service` / port 80
- Host 填 `n8n`，得到 `https://n8n.<subaccount>.kyma.ondemand.com`
- Access Strategy 起步选 `NoAuth`

真要上生产，把 Access Strategy 切成 JWT，关联 SAP IAS（Identity Authentication Service）做 OIDC 校验，请求在到达 n8n 容器之前就被网关挡住——这才是 Kyma 的价值所在：**鉴权前置到 Sidecar，应用层不用改**。

## 几个容易踩的坑

- **资源顺序反了**：先 apply Deployment 再创 PVC，Pod 会因为找不到 volume 反复 CrashLoopBackOff。
- **`image: latest` 上生产**：会在某次 Pod 重启时悄悄拉到新版本。生产环境固定到具体版本。
- **5Gi 撑不了多久**：n8n 默认会把每次执行的输入输出全量保存。要么调高 PVC、要么开 EXECUTIONS_DATA_PRUNE。
- **Trial subaccount 跑 Kyma 吃力**：内存配额有限，生产用 enterprise subaccount。

## 什么场景适合走这条路

- 已经在用 SAP S/4HANA Cloud 或 SAP Commerce Cloud，想做 IT 流程自动化、跨系统数据同步。
- 出海企业的海外子公司 IT，需要把 SAP 业务系统和当地的 SaaS 拼起来，鉴权直接复用 BTP 的 IAS。
- SAP 实施伙伴给客户做 side-by-side extension，需要一个低代码编排层做 Demo / POC。

不太适合：纯前台业务、没有任何 SAP 后端、对 K8s 完全陌生的小团队，n8n Cloud 或单台 VM 装 Docker 就够了。
