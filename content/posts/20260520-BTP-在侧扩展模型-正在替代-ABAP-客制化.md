十年前给 SAP 系统做客制化，几乎只有一条路：在 ECC 里写 Z 开头的程序，加 BAdI、改用户出口、扩字段。代码就藏在核心系统里，跟标准模块一起跑。

这种方式短期省事，代价在升级那一刻才暴露：每一次 EHP 升级、每一次大版本迁移，那几千行 Z 代码都得逐个 review，看有没有跟新版本冲突。一个中型客户在做 ECC 到 S/4 迁移时，光做客制化代码评估就花了五个月——还没开始动手改。

到了 2026 年，这个问题被 Joule 重新放大。SAP 的 AI Copilot 要在你的业务流程里跑得动，前提是它能读懂核心数据模型。如果在 S/4 里塞了一堆魔改字段和私有 BAdI，Joule 看到的就不是一个标准 ERP，而是一团没人能解释清楚的代码。

于是 Clean Core 这个口号——以前更多是架构师圈子的洁癖——变成了真正的工程约束。Side-by-Side（在侧扩展）成了主路径，BTP（Business Technology Platform，业务技术平台）是承载它的平台。

## 三层扩展模型：什么放核内，什么下沉到 BTP

SAP 在官方文档里把扩展能力分成三层。这张图把对应关系画清楚了——

![SAP BTP 三层扩展模型](https://mmbiz.qpic.cn/sz_mmbiz_png/lWqJzSMIBLXZTgiaBLYRTf16M4R2GYcTfSEjP6iabRVueSYAO04BBxoLeevCdxgMfjibSxSjjVa4JnZBpnSZWF5Tuhicia9gIqMF6py2l6c78iaBA/0?from=appmsg)

三层不是替代关系，是分工。理解这点，架构决策才不会拍脑袋。

- **Tier 1 · In-App（核内扩展）**：紧耦合于核心数据，比如要给客户主数据加一个自定义字段，或者在销售订单保存事件里加个校验。这种逻辑天生离不开核心，硬下沉到 BTP 反而是绕远。用 ABAP Cloud 写在核内是合理的。
- **Tier 2 · Side-by-Side（在侧扩展）**：复杂逻辑、外部系统集成、要用非 ABAP 语言（Node.js/Java/Python）、要扛流量峰值、要接 AI 服务——这一类全部跑在 BTP。本文重点。
- **Tier 3 · UI-Only（前端扩展）**：只是想给老板做一个仪表盘、给业务做一个审批表单，不动后端。走 SAP Build 低代码就够了，连开发资源都省了。

做 SAP 项目的团队最容易踩的坑，是把 Tier 2 的活儿用 Tier 1 的方式做——觉得 ABAP 顺手，所有逻辑都丢进核心。这种思路在十年前确实跑得通，但今天它会让你在升级、对接 AI、扩展并发能力时全面被动。

## 为什么「在侧」这件事，2026 年和过去不一样

Side-by-Side 这个词其实不新，从 NetWeaver 时代就有。真正变化的是它的工作方式。

过去的扩展程序，本质上是个被动调用的服务：核心系统通过 RFC 或者 Web Service 主动喊它干活，干完返回结果。这种模式在前 5G 时代够用，但跟现在的事件驱动架构格格不入。

现在的 BTP 扩展，更多是反过来——核心系统发生事件（一笔销售订单创建、一个采购合同签署），通过 SAP Event Mesh 把事件广播出去，BTP 上的扩展应用监听到事件后立刻响应。核心系统不再「知道」扩展的存在，扩展自己决定要不要接、怎么接、什么时候接。

> 从「调用扩展」变成「订阅事件」，本质是把核心系统和扩展之间的依赖反转了。核心保持干净，扩展自由演进。

这种解耦带来三个直接收益。一是升级零冲击：S/4 出新版本，扩展不会因为内部结构变了而崩，因为它从来就没依赖过内部结构，只依赖事件契约。二是多语言并行：团队里 Node.js 和 Java 工程师可以同时干活，不再被 ABAP 卡住。三是独立伸缩：促销季客户门户被打爆，BTP 上加资源就行，财务月结不会被拖慢。

## CAP 是开发模型，不是框架——这点很多人搞混

做 BTP 项目几乎绕不开 CAP（Cloud Application Programming Model，云应用编程模型）。但很多团队第一次用 CAP 都会问：它跟 Spring Boot、Express 是什么关系？

CAP 不是要替代它们，CAP 是一个建模优先的开发范式。先用 CDS（Core Data Services）声明式地定义数据模型和服务接口，然后 CAP 自动帮你生成 OData 端点、HANA 表、权限校验逻辑。底下跑的还是 Node.js 或 Java，但你不再手写大量样板代码。

举个最小例子，定义一个供应商证书实体加一个查询服务：

```cds
// db/schema.cds
namespace vendor;

entity Certificate {
  key ID         : UUID;
  vendorCode     : String(20);
  certType       : String(40);
  validUntil     : Date;
  status         : String(10);
  fileURL        : String(255);
}

// srv/service.cds
using vendor from '../db/schema';

service VendorPortalService @(requires: 'authenticated-user') {
  entity Certificates as projection on vendor.Certificate;
  action submitForReview(certID: UUID) returns String;
}
```

十几行 CDS，CAP 就给你生成了一个完整的 OData v4 服务，带 CRUD、过滤、分页、权限、HANA 持久层。同样的功能用裸 Java 写，至少要 200 行。

Joule 进入 SAP Business Application Studio 之后，这个生产力还在往上抬。Kellton 在 2026 年版的 Clean Core 指南里给出的数据是：Joule 能基于自然语言提示生成 60% 到 70% 的 CAP 服务模板代码——剩下 30% 真正的业务逻辑，才是工程师该花时间的地方。

## Cloud Foundry 还是 Kyma：选型不是性能题，是组织题

BTP 上有两套主流运行时，新人最容易在这里卡住。

**Cloud Foundry** 是 PaaS 路线。写好代码，`cf push` 一下就部署完了。SAP 帮你管运行环境、伸缩、日志。优点是上手快、运维负担轻，缺点是灵活性受限——能用什么 buildpack、什么版本，SAP 说了算。

**Kyma** 是 Kubernetes 路线。SAP 给你一个托管的 K8s 控制面，自己管 Deployment、Service、Ingress，自由部署任何容器化的工作负载。优点是想干啥干啥，缺点是团队得有 K8s 运维能力，否则一个 OOMKilled 就够查半天。

决策标准其实跟项目本身关系不大，更多是看团队画像：

- 没有 DevOps 团队，开发就是开发，那就走 Cloud Foundry，省心
- 已经在用 K8s 跑其他系统，希望 BTP 扩展也纳入统一运维体系，那走 Kyma
- 要跑 Stateful 工作负载、自带数据库、要装第三方 Operator，Cloud Foundry 做不了，必须 Kyma

做 Sales Cloud V2 或者 Service Cloud V2 客制化的项目里，绝大多数场景 Cloud Foundry 就够。只有当你已经有一支成熟的云原生团队，Kyma 才能发挥价值——否则它的灵活性就是负担。

## 一个真实场景：供应商可持续性证书门户

Kellton 在原文里给的案例很有代表性：欧盟客户因为 CSRD（企业可持续发展报告指令）合规要求，需要让全球供应商上传 ESG 证书。这个需求十年前的做法是在 ECC 里建一组 Z 表加几个屏幕，让采购员手工录入。

2026 年的做法是建一个 BTP 在侧扩展，组件关系是这样：

- 供应商通过外部门户登录（XSUAA 做身份认证，跟 S/4 的用户体系隔离）
- 上传证书 PDF，触发 BTP 上的 Document Information Extraction 服务（SAP AI Services）解析关键字段：证书编号、有效期、发证机构
- 解析结果通过 CAP 服务持久化到 BTP 自己的 HANA Cloud 实例
- 校验通过后，通过 Cloud SDK 调用 S/4HANA 的 Business Partner OData API，把「已认证」标记同步回供应商主数据
- S/4 这边只新增一个标准字段（用 Tier 1 In-App 扩展），其他逻辑、文件、AI 模型都在 BTP 上

结果是 S/4 核心保持干净——下次升级，Z 代码评估清单里没有这个项目。同时供应商门户用的是现代 Web 技术栈，跟 Fiori 的体感差着一代。

## 落地建议：什么时候用，什么时候别碰

过去两三年陆陆续续看了不少 BTP 项目，有做成的也有做砸的。挑出来几条经验：

**适合走 Side-by-Side 的场景：**

- 出海企业的客户门户、供应商门户、经销商管理系统——这些天生需要现代化 UI 和外部用户管理，跟 ERP 用户体系本来就要隔离
- 跨境电商或全球化运营，要对接当地支付、物流、税务系统——这些集成逻辑放进核心 ERP 是灾难
- AI 增强类需求，比如智能合同审阅、需求预测、客户流失预警——这些天然属于 BTP 的 AI Foundation 范围
- 在华外资企业总部，要把中国本地化的合规逻辑（电子发票、金税）做成扩展，又不污染全球模板——典型的 Side-by-Side 场景

**不要碰 Side-by-Side 的场景：**

- 只是给一个标准报表加个字段——这是 Tier 1 的活，硬上 BTP 是过度工程
- 逻辑跟核心数据强耦合（比如复杂的销售定价规则），延迟敏感且事务一致性要求高——放在核内 ABAP Cloud 性能更好
- 项目预算紧、团队没有云原生经验、上线时间窗口只有三个月——BTP 项目的学习曲线和环境搭建会吃掉这点时间

**典型踩坑预警：**

- BTP 子账号、空间、目录的治理一开始不规划，半年后会变成账单地狱。订阅一开就忘关，每月成本能差三到五倍
- Cloud Connector 没有做高可用，是单点故障——出海项目跨大区时尤其要注意
- 把 CAP 当成普通 Node.js 项目硬写自定义 Express 路由，等于自废武功——CAP 的价值正是建模优先，绕开它写就是用 Node.js 做了个非常贵的小项目

## 写在最后

Side-by-Side 不是 SAP 给客户的施舍，是它把「核心稳定」和「业务敏捷」拆开的工程答案。核心 ERP 在标准化方向越走越深，业务创新在 BTP 这一侧自由演化——两条路径速度不同，互不阻塞。

这种架构思路，习惯了在核心系统里写 Z 代码的工程师，第一次切到 BTP 时会觉得「为什么要绕这么多弯」。但当你经历过一次毫无障碍的 S/4 升级、一次扩展应用单独扩容、一次 AI Copilot 真的读懂了你的业务流程——那时候就会明白，绕的这些弯，正是为了下一个十年不再被绑死。
