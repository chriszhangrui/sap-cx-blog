十年前做 CX 项目，最常听到的一句话是「我们的客户数据是分散的」。十年后做 AI 项目，最常听到的话变成了「我们的 AI 助手是分散的」。**问题没变，只是换了个壳。**

每个部门一个 copilot，每个 copilot 一个数据集，每个数据集一套权限。营销云一个助手，电商一个助手，客服一个助手，销售一个助手。听起来很热闹，实际上是把过去十年的数据孤岛，又用 AI 复刻了一遍。

最近这个老问题有了一些新进展。Sapphire 2026 落幕之后，SAP 的 CMO Jessica Keehn 接受 CX Today 专访，把这场转向第一次讲得比较直白：**从分散的 copilot，走向一个统一编排的执行系统。**这话听起来还是有点 PR 味，但拆开看，确实有几层意思值得说。

**第一层意思：AI 不再是「助手」，而是「执行者」。**

过去两年所有人讲 AI in CX，话术都是「让营销人员更高效」「让客服更专注于复杂问题」。Keehn 这次的措辞变了，她说一个营销人员不应该还要去操心「哪个 agent 能识别人群、哪个能查库存、哪个能生成内容、哪个能触发下一步动作」。

换句话说，**用户应该只需要描述结果，剩下的让系统自己编排。**这其实是把 CX 工作台的边界往后推了一大步——以前我们说「集成」，意思是把多个系统的数据接到一个屏幕上。现在 SAP 的意思是，连屏幕都不要了，用户描述目标，系统调度 agent 跑流程。

这个方向，看上去激进，但有现实驱动。SAP 自己引用的数据是：95% 的企业 AI 项目失败，原因是 AI 系统跟真实业务流程、数据、规则脱节。说白了，不是模型不够强，是 AI 不知道你这个公司是怎么运作的。

![SAP 自治 CX 三层结构](https://www.cxtoday.com/wp-content/uploads/2026/05/Customer-Journey-Orchestration-16.png)

**第二层意思：底座、调度、入口，三件事一起做。**

三层结构里最关键的是底座，叫 SAP Business AI Platform。它把 BTP、SAP Business Data Cloud (BDC) 和 SAP 的 Business AI 能力焊成一块。这里面有个工具叫 SAP Knowledge Graph，给 AI agent 提供企业内流程和关系的语义图——这是回答「AI 不知道你公司怎么运作」这件事的技术答案。

调度层是 SAP Autonomous Suite，号称部署了 50 多个 Joule 助手，覆盖营销、电商、销售、服务以及财务。Keehn 反复强调一句话：**助手要在业务流程里协作，而不是各自为战。**这是和过去 18 个月行业流行的「每个产品发个 chatbot」做切割。

入口层叫 Joule Work，野心更大——它想替代「打开应用、填表单、跳页面」这套传统工作流。用户说「帮我把这个客户的 Q3 续约方案做出来」，系统在背后调用 Sales Cloud V2、Service Cloud V2、Engagement Cloud (Emarsys) 的相关数据和 agent，把工作完成。

**第三层意思：方向对，但落地这件事，我半信半疑。**

方向上没什么好质疑的。把 50 个 agent 编排成一个有上下文、有审计、有治理的执行系统，这条路本来就是企业 AI 必须走的。SaaS 时代留下的最大遗产是「每个工作流都被一个独立的应用切走」，AI 时代如果继续这么搞，我们就是把孤岛从「数据孤岛」升级成「智能体孤岛」。

但落地这件事，**最难的不是技术，是组织。**让一个营销总监放弃她现在熟悉的 Emarsys 仪表盘，改去用一个「告诉我你想做什么」的对话框，这个心智迁移不是六个月能完成的。Keehn 自己也承认，CX 团队的角色「会演化成更战略、更人性、更注重共情」——翻译过来就是，这一波下来，团队会瘦身。

另一个隐忧是底座绑定。**Joule Work 想做整个企业的入口，意味着它要对所有业务系统有强控制权。**对深度用 SAP 全栈的客户来说没问题，但对那些「SAP + Salesforce + 自研中台」的混合架构客户，这个故事要怎么讲？SAP 给的答案是「extends beyond SAP into non-SAP environments」，这话好听，但凡做过跨厂商集成的都知道，魔鬼在细节里。

**第四层意思：对中国出海企业，这个时间窗很关键。**

我接触过的出海企业里，目前在 SAP CX 这条线上的客户大致分两类：一类是已经上了 Commerce Cloud 或 Engagement Cloud 单点产品的中国出海品牌，另一类是欧美总部决策、中国分支跟随的跨国制造和零售。这两类客户当下的共同问题是——单点产品已经在跑，但跨产品的协同基本没有。

举个具体场景：一个做跨境 DTC 的品牌，Commerce Cloud 跑电商，Emarsys 跑邮件，Service Cloud V2 跑客服。客户在网站上加购但没付款，触发邮件挽回；客户收到邮件点回来，咨询客服；客服查不到购物车上下文，让客户重新描述问题。这个旅程里每一段都有 AI，但 AI 之间没有上下文。

SAP 这次讲的「连接的客户旅程」——基于 BDC 做统一数据层，Joule 在上面做编排——如果真的能落地，是直接解决这个场景的。但我会建议想清楚这件事的客户：**先把 BDC 这个底座放进 2026 年的规划，再谈上面的 Joule 编排。**没有底座的编排，是空中楼阁。

另外一个观察：SAP 这次把 Engagement Cloud (Emarsys) 的事件总线开放，把 Sales Cloud V2 的 V_V2 实例往 BDC 上靠，这两件事比 Joule Work 更早落地，也更靠谱。做出海的客户如果今年要动 CX 选型，**优先看哪些产品已经接进了新的事件架构，而不是优先看哪些产品已经有了 Joule。**

Keehn 在采访最后说了一句相对克制的话：「过去那种基于断点快照的客户参与，会变成基于实时业务信号的连续对话。」如果只看营销话术这句没什么，但放在 SAP 用一年时间收购 Reltio、Dremio，重塑 BDC，重写 Joule，把 50 多个 agent 集成进同一个 Suite 的背景下看，这场转向是认真的。

方向上我看好，节奏上我谨慎。SAP 把所有牌都摊在桌上了，剩下的事情是落地——而落地这件事，从来不是 SAP 一家说了算。
