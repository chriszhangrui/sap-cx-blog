在 BTP 上做一个能卖给多个客户的多租户 SaaS 应用，CAP 框架那一层其实不难——难的是把 onboarding、租户路由、Schema 迁移这些"运维型"逻辑从应用代码里剥出去。剥不干净，每加一个客户都要改代码、重新部署，clean-core 就成了一句口号。

这就是 SAP 最近力推 CAP Operator 的真正原因。它不是又一个部署工具，而是要把 SaaS 应用必须自己处理的那一层运维逻辑，整体下沉到 Kubernetes 控制平面。

之前讲过 CAP Operator 的运行时架构，那篇偏理论。这次一篇 SAP 官方的 hands-on 文章把它放到 Partner Reference Application（PRA，SAP 给合作伙伴提供的复杂 SaaS 参考实现）上做实改造，能看出更多东西。

## 为什么是 Partner Reference Application

SAP 写过的 CAP 示例不少，但绝大多数是 hello-world 级别的——单租户、demo 用法。PRA 不一样，它是 SAP 自己用来教合作伙伴"如何在 BTP 上构建可商用 SaaS"的 reference 工程，里面塞了几个真实生产环境绕不开的东西：

- 多租户隔离：每个 tenant 独立 schema，数据访问路径要分开
- 与 BTP 核心服务的绑定：XSUAA（认证）、Destination（连接配置）、SaaS Provisioning Service（订阅生命周期）
- 显式的 onboarding / offboarding：客户订阅时建 schema、退订时清理

> 用 PRA 这种"足够复杂的真实工程"做迁移演示，是想说明 CAP Operator 不是只能玩玩 demo——它能扛得住企业级 SaaS 的真实复杂度。

## 关键动作：从命令式到声明式

整个迁移路径的核心，是把项目里的 Kubernetes Deployment、StatefulSet，加上散落在应用代码里的 mtxs（多租户扩展性）调用，统一替换成 CAP Operator 定义的几个 Custom Resource：CAPApplication、CAPApplicationVersion、CAPTenant、CAPTenantOperation、Domain。

抽象一点说：原来你要写一坨 yaml 来描述 Pod、Service、Ingress，再写一坨 Node.js 代码来响应 SaaS Provisioning 的 onboarding 回调；现在你只声明"这个应用叫什么、域名怎么分、用哪些 BTP 服务"，CAP Operator 自己去 watch 这些 CR，自己去拉 Pod、配路由、调 mtxs 接口建 schema。

## 四步迁移路径

**第一步：注入 plugin 推导配置**

不要从零写 Kubernetes manifest，而是依赖 CAP 生态的工具链：

```
npm add @cap-js/cap-operator-plugin -D
```

这个 plugin 会读取项目里已有的 cds 模型和 `mta.yaml` / 配置 schema，自动推导出对应的 CRD 配置文件以及容器化所需的模式。这一步看似只是省了几个 yaml 文件，但意义在于：CRD 不再和 cds 模型脱节，模型变了配置自动跟着走。

**第二步：容器化推到 Registry**

常规做法。把 CAP 应用的几个服务模块（业务 Server、MTX Sidecar、Approuter）分别打成镜像，推到 Kyma 集群可访问的容器仓库。原文用的是 Docker Hub 或 GitHub Packages，企业部署里通常是私有 Registry。

**第三步：用 Custom Resource 替换原生工作负载**

这一步是真正的转折点。原来 PRA 项目里那些 Deployment / StatefulSet 全部删掉，换成一个 CAPApplication 的声明，大致长这样：

```yaml
apiVersion: sme.sap.com/v1alpha1
kind: CAPApplication
metadata:
  name: pra
spec:
  btpAppName: pra-saas
  globalAccountId: ...
  provider:
    subDomain: pra-provider
    tenantId: ...
  domains:
    primary: pra.example.com
  btp:
    services:
      - name: pra-uaa
        class: xsuaa
      - name: pra-saas-reg
        class: saas-registry
```

原来要在 Node.js 里写代码处理 mtxs 的租户注册流程，现在不用写了。CAP Operator 监听 CAPTenant 资源，新建一个 CAPTenant 对象就触发租户 onboarding，删除就触发 offboarding，整个生命周期被 Kubernetes 控制器接管。

**第四步：BTP 服务交给 SAP BTP Service Operator**

XSUAA、Destination、SaaS Provisioning 这些 BTP 服务的实例创建和 binding，由 SAP BTP Service Operator 统一管。和 CAP Operator 是两个独立的 controller，但搭配使用——前者负责"BTP 这一侧的资源"，后者负责"应用这一侧的资源"，二者通过 secret 串起来。

## 这个设计放弃了什么、解决了什么

**解决了什么：**把 SaaS 应用必须自己处理的多租户编排从业务代码里抽走。开发者写 cds 模型、写业务逻辑，不再写 onboarding 回调、不再维护租户路由表、不再调度 schema 迁移脚本。clean-core 在 SaaS 场景下第一次有了可执行的形态——你的代码仓库里只剩业务逻辑，运维语义被 CRD 接走。

**放弃了什么：**对 Kubernetes 的依赖被钉死了。以前在 Cloud Foundry 上跑的 CAP 多租户应用，运维逻辑是写在 mtxs 库里的 Node 代码，迁移性还可以；现在这条路径上 CAP Operator 是 Kyma/K8s 原生的 controller，离开 Kubernetes 控制平面跑不了。换言之，BTP 的 SaaS 开发模型正式从 Cloud Foundry 时代切到 Kyma 时代。

**跟竞品比：**把 SaaS 多租户编排做成 Operator 这条路径，业界并不孤独——Crossplane、KubeVela 都在做类似的事。但 CAP Operator 的差异是它绑死了 BTP Service Operator 和 cds 模型，相当于给"BTP + CAP"这个组合定制了一套专属 controller，深度集成换来了开发体验，但也意味着锁定。

## 什么场景适合上、什么场景先别碰

对做出海 SaaS 的中国合作伙伴和有海外业务的企业 IT 团队，几条务实建议：

- **新建项目优先选这条路。** 如果正要在 BTP 上做一个面向海外客户的多租户 SaaS（合作伙伴常见场景），从第一天就用 CAP Operator + Kyma，不要先写一堆 Cloud Foundry 时代的命令式部署再迁移。后迁的成本远高于前置。
- **已有 CF 上的 CAP SaaS 应用，先评估再决定。** 迁移收益是 clean-core 和运维简化，迁移成本是镜像化、CR 改造、CI/CD 流水线重做。应用越复杂、租户越多，迁移收益越大；轻量应用迁不迁差别不大。
- **团队 Kubernetes 经验不够，先补课。** CAP Operator 抽象了很多 K8s 细节，但出问题排查时绕不开 kubectl。如果团队过去只熟悉 cf push 那一套，先把 K8s 的 controller / CRD / Operator pattern 啃下来再上。
- **合规敏感场景先不要碰。** Kyma runtime 在中国大陆不可用。如果客户对数据驻留地有强约束，这条 SaaS 路径目前只能服务海外或在华外资的总部对接场景。

## 实践层面的几个坑

- **容器镜像版本与 CAPApplicationVersion 的绑定关系容易混乱。** 升级应用版本时，新的 CAPApplicationVersion 和已有的 CAPTenant 之间需要明确 upgrade strategy，否则租户卡在旧版本上。
- **Kyma cluster 必须先装好 CAP Operator 和 BTP Service Operator。** 这两个 Operator 的版本兼容性矩阵要查清楚，混搭老版本会出现 CRD 字段不识别。
- **provider subaccount 的 entitlement 要提前规划。** SaaS Provisioning Service、XSUAA、HANA Cloud 等 entitlement 缺一个，租户 onboarding 就会卡在某一步而不报明显错误。
