> CLM 的工程难点从来不在积分计算本身。真正麻烦的是积分到账之后——那条把"你又赚到 200 分"递到客户眼前的链路，决定了这个忠诚度计划能不能跑起来。SAP Engagement Cloud Q2 2026 release 把这条链路换了一种姿势。

先看一个具体场景。某个出海零售客户跑了一个分级会员体系：白银会员每笔订单送 1% 积分，金会员 3%，铂金 5%。订单在 Commerce Cloud 完成、积分在 CLM 计算完毕，下一步是把"恭喜你又赚到 200 分"通知到用户。

过去这一步走的是 Push Notification——客户没开推送权限，消息发不出去；客户在地铁里一晃而过，通知栏被覆盖，消息也丢了。重发？换邮件兜底？再加一道 SMS？每加一条通道，就多一份成本和合规复杂度，最后形成一个"我已经送了你三遍但你都没看到"的尴尬循环。

Q2 release 里那个被低调放出的 **Embedded Messaging（Pilot）**，正是冲这件事来的。

## 从 push 模型切到 pull 模型

官方的描述很克制："a persistent, pull-based messaging channel that delivers inbox experiences inside mobile apps and websites—with no push opt-in required"。翻译成架构语言就是——这不是一条新的推送通道，这是一条新的"消息储存通道"。

差别在哪？Push 的本质是消息一旦发出就在网络里漂，对方在线就收到，不在线或者不允许就丢失。Embedded Messaging 把消息持久化在客户端 SDK 维护的本地收件箱里——客户什么时候打开 App 或者刷新页面，消息就什么时候出现。**消息不再依赖系统级推送权限，也不依赖客户当时是否在线。**

官方在原文里直接拿 loyalty 当例子来讲这个能力，不是巧合。"if your customer receives a loyalty reward but isn't ready to act immediately, the message persists in their in-app or on-site inbox until they are"——积分到账消息恰好是最不应该走 push 的那一类：用户不会因为收到一条积分通知就立刻打开 App，但下次打开的时候它必须还在。

## External ID 这次终于有了正经的待遇

同期一起放出来的另一条更新更值得做技术决策的人警觉——**Flexible External Contact ID Management（GA）**。

老问题是这样的：S/4HANA 那边客户主数据有自己的 ID，CDC 那边 UID 又是另一套，Engagement Cloud 接进来之后默认会拿 email 或自己的 contact_id 作主键。CLM 要把积分账户挂在某一个客户身上的时候，跨系统对账经常出错，因为同一个真人会因为 ID 不匹配被建成两条 contact。这条更新让你可以把外部系统的原生 ID 作为 custom field 保留，**而不是让它被覆盖或丢失**，配合 ID Mapping 做 1:1 或 N:1 的解析。

实施层面的差别是：

- 以前：CPI 上写一段 mapping 逻辑，每次同步前手动比对；遇到主数据补录就一次性回写，容易冲突
- 现在：原生 ID 在 Engagement Cloud 里有自己的 column 位置，可以直接 query、直接 segment、直接走 personalization token

配合 **Universal Schema Builder（Pilot）** 这次的升级——personalization 字段可以脱离 segment 独立使用、多个 campaign 并发引用同一个 schema——意味着你可以把外部数据库（比如 POS、仓储系统）当成一个独立的视图接进来，而不再用 Relational Data 这种偏离主流的折中方案。

## CDP 终于不用切系统了

**SAP CDP Audience Builder in Engagement Cloud（GA）** 把 CDP 的分群能力直接搬进了 Engagement Cloud 的界面里。这一步小，但意义大。

```
// 旧路径
SAP CDP → 在 CDP 里构建 segment → 同步到 Engagement Cloud → 在营销活动里引用

// 新路径
Engagement Cloud → Audience Builder（embedded）→ 创建 CDP segment
→ 自动落为 CDP segment 类型 → 直接用于 campaign / personalization / automation
```

差别不只是少一次切换。原来跨系统会引入数据"快照"问题——你在 CDP 里建好 segment、同步过来时已经过了几分钟到几小时，期间客户行为可能已经变了。新做法走的是同一份实时数据，segment 一建好就立刻对营销自动化可见。对那些靠"会员升级触发即时奖励"这种实时场景的零售和航旅客户来说，这是个分界线。

## 这次的架构判断在哪里

把这几条更新放在一起看，方向就清晰了：**SAP 这次没去重新发明积分引擎，而是在重构积分发出之后的那条触达链路。**

- **触达层**：从 push 单向通知改为 pull 持久收件箱，把"消息丢失"这个老问题从架构上消掉
- **身份层**：External ID 不再被覆盖，跨系统对账从写代码变成配字段
- **数据层**：Universal Schema Builder + 嵌入式 CDP，把外部数据接入和原生 segment 的边界打散

放弃了什么？放弃了"以推送为主、邮件兜底、SMS 紧急"这种多通道竞速的老模型。Embedded Messaging 不替代 push，但它把那些"用户当下不响应也没关系"的场景接管走，让 push 回归到真正紧急的通知。

和 Salesforce Loyalty Management 的差异也开始显出来。Salesforce 那边的强项是规则引擎和 benefits/promotion 体系；SAP 这次的赌注更明显押在**会员触达体验和数据底座的统一**上——前提是你已经在 Commerce Cloud / S/4 / CDC 这套生态里。

## 什么样的项目适合上、什么时候不要碰

**适合的**：

- 跨境零售 / 出海消费品牌，已经在用 Commerce Cloud，且会员触达多通道带来运维负担的
- 航旅 / 酒店行业的常旅客计划，需要在 App 内嵌持久化的会员状态和奖励信息
- 已经在 SAP CDC + S/4 + Engagement Cloud 这条链路上，受 ID 重复和数据不同步困扰的项目

**暂时别碰的**：

- Embedded Messaging 还在 Pilot 阶段，要走 Customer Success Manager 申请，时间和承诺不能按 GA 算
- 核心客户群在中国大陆且只做内贸的，Engagement Cloud 没有国内数据中心，不要硬上
- 需要把积分写入 ERP 财务账的项目，CLM 与 S/4 的回写还是要走 CPI，不在这次更新覆盖范围内

**实施踩坑警示**：Universal Schema Builder 和老的 Relational Data 是两套机制。如果你已经在 RD 上投入了大量配置，别急着迁移，原文给的措辞是 "improves upon existing Relational Data functionalities"，意味着 RD 还会存在，但新场景应该优先 USB。同样，Flexible External Contact ID 不是开关式启用——已经在跑的 contact 库需要重新规划主键映射，别在生产环境直接切。

---

CLM 真正难的从来不是"算出 200 积分"，是"让用户在最合适的时刻看到这 200 积分"。Q2 2026 release 没改积分公式，但它把那个"让用户看到"的链路重新画了一遍——这一步比新发布一个独立产品更值得记住。
