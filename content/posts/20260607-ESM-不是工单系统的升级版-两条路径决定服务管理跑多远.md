很多团队上 ESM（Enterprise Service Management，企业级服务管理）的第一反应是：把所有员工请求都丢进一个 Case Type 里，让 HR 共享中心慢慢分。三个月之后他们会发现，工单是收上来了，但同一类问题——比如休假申请、报销疑问、入离职手续——每个 agent 接到的字段都不一样，规则散在 agent 脑子里，统计跑出来全是手填字段。

这件事的根源不是工具不够好，而是从一开始就没在 Case Management 和 Service Request Management 这两条路径上做选择。SAP 在 SuccessFactors 里把 ESM 这一块的配置模型摆出来之后，这个选择终于不再是凭手感，而是有显式的配置点。

## 两条路径的真实差别

先把概念理一遍，因为很多文档把这两个名词混着写。

**Case Management** 是底座。它不强制结构化字段，不要求绑定流程，agent 拿到一个工单，几乎全靠自由文本和几个标准字段（类别、优先级、申请人）就能开干。它的优势是 ad-hoc 场景接得住——员工临时丢一句"我下周想申请特殊假期，要走什么流程"，没必要让他先填一张十二个字段的表单。

**Service Request Management** 是覆盖在底座之上的结构化层。它要求两件事：一是 **Forms（动态表单）**，二是 **Case Flow（流程引导）**。表单决定字段必填规则，Case Flow 决定 agent 一步步该干什么、该谁批。

关键判断在这里：**Service Request Management 不是 Case Management 的升级版，它是覆盖在 Case Management 之上的一层结构**。一个 ESM 实例同时跑两条路径，是 SAP 默认的设计意图，不是配置失误。

## 动态表单的绑定模型

这一层最容易被低估，也是早期实施踩坑最多的地方。

在 ESM 里，**多个 Form 可以绑定到同一个 Case Type**。系统会根据工单的 category、priority 或者其他参数动态决定展示哪一个。换成更直白的话：你不必为"病假申请"和"事假申请"各建一个 Case Type，而是一个 Case Type 下挂两张表单，按子类别切换。

这种"一个 Case Type 多张表单"的设计有两个直接收益：

- 报表口径稳定。所有休假相关都进同一个 Case Type，跑量、看趋势、做 SLA 都是一条主键。
- 配置可演进。新增一种休假类型只是加一张表单和一条切换规则，不必动 Case Type 本身和它后面的所有路由配置。

代价是：表单切换规则必须显式声明，哪个 category 走哪张表是个绕不过去的配置项。下面这段是常见的切换条件结构（按原文的语义还原）：

```
Case Type: HR_LEAVE_REQUEST
├── Form: LEAVE_SICK
│   └── Trigger: category = "Sick Leave"
├── Form: LEAVE_PARENTAL
│   └── Trigger: category = "Parental Leave"
└── Form: LEAVE_GRIEVANCE
    └── Trigger: category = "Grievance"
              AND priority = "High"
```

priority 在最后一条规则里加进去这件事值得展开说一下：同一个 category 在不同优先级下走不同表单，是 ESM 真正区别于"传统工单系统"的地方。传统工单系统通常只让你在创建时选模板，之后字段就锁死了；ESM 把表单的绑定移到了运行时。

## Case Flow 把 agent 的判断挪到配置里

Case Flow 这一层经常被理解成"流程图"，其实更准确的描述是：把 agent 的隐性判断显式化。

在没有 Case Flow 的世界里，agent 收到一张休假申请单，他需要自己判断：现在要不要让员工补材料？该转给主管批还是 HRBP 批？审批后要不要回写到 Employee Central？这些判断散落在 agent 脑子里，新人接手要靠师傅带。

Case Flow 把这些步骤拆成一串显式节点：

- **步骤定义**：每一步该干什么、该谁负责
- **责任分配**：tasks 可以指派到角色而不是个人，离职就不会留下死单
- **审批嵌入**：approvals 直接挂在 Case Flow 节点上，不再走"再开一个 ticket 让主管批"的影子流程

这件事的意义不在"自动化"，而在"统计颗粒度"。Case Flow 跑出来的每一步都有时间戳，第一次让 HR 共享中心能算出"病假申请平均卡在哪一步"——以前这个数字根本没法算。

## Basic 与 Advanced：不要一上来就跨层

SAP 在 ESM 里把 Service Request Management 又切成两层：

- **Basic**：表单 + Case Flow，全程在 ESM 内部完成。适合审批、HR 申请、物料请领这类不需要跨系统拉数据的请求。
- **Advanced**：在 Basic 基础上加自动化和外部系统集成。典型场景是入职：要触发 Employee Central 建档、IT 系统开账号、设备发放、培训系统注册——这些动作横跨多个 stakeholder 和多个系统。

实施里最常见的错误是：客户一上来就要做 Advanced，因为入职、休假、报销听起来都"复杂"。但 Advanced 的代价不在 ESM 自己，而在它背后那些被串起来的系统——iFlow 要写、API 要确权、错误重试要设计。任何一个外部环节挂了，整个 case 卡在中间，回滚很贵。

合理的顺序是先把 Basic 跑通三到六个月，等数据告诉你"哪几个流程量最大、规则最稳"，再挑一两个抬到 Advanced。原文里那句"Advanced is ideal when processes are frequent and automation provides real value"，翻译成项目语言就是：先用量证明它值得自动化。

## 怎么决定一个新流程走哪条路径

原文给了一个朴素的判断框架：volume、complexity、自动化潜力三件事一起看。我把它做成一张更可操作的决策表：

- 量小 + 不可预测 → Case Management。员工偶尔丢的奇怪问题，没必要为它建表单。
- 量中 + 规则稳 → Basic Service Request Management。表单 + Case Flow 就够了，先收集结构化数据再说。
- 量大 + 跨系统 + ROI 清晰 → Advanced。但要确认 ROI 不是 PPT 上的数字。

有一类陷阱要警告：**不要把"低频但合规要求高"的流程放进 Advanced**。比如申诉、调薪争议、特殊补偿——这些请求一年也没几个，但每个都需要 case-by-case 处理。把它们硬塞进 Advanced 自动化路径，反而会让合规审查跟不上自动化的速度，出问题更难追溯。这种场景留在 Case Management 里，让 agent 用判断处理，比配自动化安全。

## 出海企业的实操建议

ESM 跟 SuccessFactors Employee Central 的集成是它最强的卖点之一——员工档案、组织架构、审批链路这些数据进 ESM 不用再造一遍。对中国企业出海或在华外资来说，这一点的价值在于：欧美总部的 HR SSC 已经在跑 ESM，中国分公司接进去比自己再搭一套 ServiceNow 省得多。

几个落地里要先想清楚的事：

- **语言与本地化**：动态表单是按 category 切的，中文区的休假类型、津贴名目、合规要求和总部不同，要建一组本地表单，不要硬套总部表单的字段。
- **数据驻留**：ESM 本身没有国内数据中心，员工敏感字段（身份证号、工资）要不要进 ESM、进哪些字段，要在第一次 case 创建之前就和合规团队过一遍。
- **知识库分层**：员工自助门户的 FAQ 和 agent 工作台的 Solution 不要混着维护。Solution 给 agent 用，可以写得详细甚至带操作截图；FAQ 给员工看，必须经过法务和 HR 双审。

## 最后一句

ESM 真正的设计哲学不是"把所有员工请求标准化"，而是"承认有些请求永远不该被标准化"。Case Management 这条路径留下来的弹性，比 Service Request Management 跑得多漂亮更值得保护。一个只会跑结构化流程的 ESM 实例，三年之后会变成员工绕着走的官僚机器。
