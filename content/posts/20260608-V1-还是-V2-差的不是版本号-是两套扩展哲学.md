Sales Cloud V1（很多人还习惯叫它 C4C）和 V2，最容易被误解为"老版本和新版本"。但真把两边的实施项目摞在一起看，差别根本不在 UI 怎么画、AI 多了几个按钮——是 SAP 在重新画扩展和核心之间的那条边界。

这条边界画在哪一行，决定了一个 CRM 项目未来五年能不能跟得上版本节奏。

## V1 的扩展，是贴在核心里的

V1 已经在很多企业里跑了多年。lead → opportunity → quote → order 这条主链路稳定，跟 ERP 和 S/4HANA 的集成也都搭好了。问题不在功能，而在扩展机制。

V1 给定制留的口子非常宽：`in-app 字段`、自定义布局、规则引擎、流程编排，一直到 SDK 级别的代码扩展。这套机制好用，但代价是定制和核心是同一个生命周期——每一次平台升级，所有定制都要回归测试一遍。在那种已经塞了五年定制的租户里，每次发版都是一场赌博。

这就是 V1 在治理上的真实负担：扩展贴得越深，核心就越升不动。最后只能把版本冻在那里，新功能拿不到，旧定制改不动。

## V2 把扩展挪到了核心外面

V2 不是在 V1 上加几个新功能——它是 SAP 重新画的一张扩展图：

- **核心保持干净（clean core）**：标准对象、标准 API、标准 UI 走 SAP 的升级节奏，不让定制把核心拖住。
- **轻量调整还在系统里**：字段、布局、简单规则这种贴近业务的小改动，仍然在 V2 里直接配。
- **真正的客制跑到 BTP 上**（side-by-side）：复杂逻辑、自定义服务、跨系统集成、低代码应用，统一搬到 BTP——CAP、Build Apps、Kyma 任选。

这张图配合 API-first 才能跑得动。V2 把核心能力都暴露成 API，扩展应用通过 API 调用核心，而不是嵌进核心。结果是核心能独立升级、扩展能独立部署，两边的发布节奏从此解耦。

## 为什么 SAP 必须做这次切换

你可以把这次重做理解成 SAP 在还一笔欠了十年的技术债。

C4C 那一代的扩展模型，本质上是在 ABAP 思路上做云化——既要保留客户既有定制能力，又要跑在多租户云上。结果是租户的"标准对象"其实千差万别，SAP 自己每次出新功能都要绕开历史定制来实现。这套架构走到云原生时代，更新速度卡得越来越死。

V2 的解法是把这两件事彻底分开：核心由 SAP 演进，定制由企业自己演进，中间靠 API 和事件解耦。这跟 S/4 在 ABAP Cloud 上推 Clean Core，跟 BTP 推 side-by-side 扩展，是同一条线——CX 这边只是慢了几年才轮到自己。

## UI 和 AI 的变化，是这套架构的副产品

很多介绍 V2 的文章会把工作台式 UI、嵌入式 AI 当作主卖点。这些确实是体验差异，但它们能做出来的前提，是底下那套 API-first 架构。

- **工作空间式 UX**：V1 是按对象划屏的——账户、联系人、商机、活动各占一块，销售一天要在十几个 tab 间切。V2 把这些信息按"任务"组织，背后是 V2 用统一 API 把多对象组合成一个视图，V1 那种基于经典 OData 服务的对象边界做不到这件事。
- **嵌入式 AI**：V1 里的 AI 大多是 add-on——单独许可、单独建模、靠定制接进来。V2 是把 AI（包括 Joule、business information extraction、forecast tracker、deal intelligence）当作平台原生能力，跟业务对象在同一套 API 模型里直连。这个差异在出海项目里直接关系到许可成本和上线时间。

## 什么样的项目该上 V2，什么样的暂时别碰

这次 V1 → V2 的切换不是技术升级，是产品换代。这意味着不能用"升级"的预算和时间表去做。

**V2 适合：**

- 出海企业新建 CRM 平台，没有历史定制包袱，希望从一开始就走 BTP + clean core 路线。
- 跨国制造或外贸企业要把销售流程统一到全球总部，且销售团队对 UI 响应速度、AI 辅助有明确要求。
- CRM 现代化已经写进 IT 路线图，组织内部能扛住流程重构、报表重做、治理模型重写这一整套连锁动作。

**V1 暂时留着更稳：**

- V1 已经稳定运行多年，业务流程没有大调整需求，短期内没有转型项目立项。
- 系统里堆了大量 SDK 级深度定制，迁移之前必须先做解耦或重新设计——这种情况硬上 V2，第一步就是把定制全部拆出来重写到 BTP，工作量大于直接重做。
- 当前重点是优化现状（数据质量、用户采纳率、集成稳定性），不是换平台。

## 实施侧的几个真实坑

- **报表的预期要重设**：V2 的标准报表能覆盖大多数销售运营场景，但跨系统合并报表、复杂管理 KPI 还是要走 SAP Analytics Cloud 或外部数据仓库。别以为 V2 自带分析就能取代 BI 项目。
- **BTP 不是免费送的**：side-by-side 扩展听起来很美，但 BTP 的 CAP 应用、Kyma 工作负载、Integration Suite iFlow 都要单独算账。一个上 V2 的项目，BTP 那边的预算和团队能力必须同步立起来，不然写到 BTP 上的扩展就是空中楼阁。
- **治理模型必须重做**：V1 的扩展治理是"谁有 admin 权限谁能改"。V2 之后核心和扩展的边界要重新切——核心配置走标准 Change Project，扩展应用走 BTP 部署管线，两套机制不能混。如果原来的 IT 治理是松耦合状态，这次要趁机收紧。
- **不是所有功能都齐了**：V2 在某些垂直领域（特别是 utility 行业、部分 B2B 复杂报价）功能仍在补齐路上。立项前先把要用到的功能清单和 V2 当前 GA 范围逐项过一遍。

## 最后一句

V1 跟 V2 不是新旧之争，是两种产品哲学：一种把扩展贴在核心里换灵活度，一种把核心和扩展彻底分开换可持续。前者在过去十年是对的，后者在云原生时代成了 SAP 必须押的方向。

企业要做的判断不是"该不该上 V2"，是"现在的扩展资产能不能解耦、组织能不能接住治理变化"。这两件事想清楚了，版本选哪个反而是最容易的部分。
