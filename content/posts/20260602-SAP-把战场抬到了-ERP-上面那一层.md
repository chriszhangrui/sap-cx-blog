今天看到一条消息值得聊聊。Bain 在 SAP Sapphire 2026 之后发了一份 CIO 视角的简报，标题翻过来叫《ERP 不再只做交易，要去做编排》。署名是五个合伙人，写得不算长，但里面有一句话挺扎眼——**战略战场正在从 ERP 内核往上挪**。

说白了就是：以前 SAP 的护城河是"我家是 system of record，你家所有交易都得过我这本账"。现在 Bain 给出的判断是，这条护城河没消失，但已经不够用了。决定 AI 时代企业架构话语权的，是更上面那一层——谁拥有数据、业务上下文和编排逻辑，谁就拥有 AI Agent 必须趴在哪里跑的地基。

![Bain hero](https://www.bain.com/contentassets/86f0998dbd6d453bbf8ffff61eee6cbe/44933-16-9.jpg)

## "系统记录"和"系统上下文"，差的不是修饰词

Bain 这次用了一个挺克制的说法：SAP 在把自己从 system of record 推向 system of context。听上去像是在玩文字游戏，但落到产品上是非常具体的。

Sapphire 上把这件事拆成了四块拼图。Business AI Platform 把零散的 AI 能力焊成一个统一的入口；Business Data Cloud 提供"可信的企业数据和业务上下文"——注意"业务上下文"这四个字，它的意思不只是数据本身，还包括数据之间的语义关系；Joule 占住用户和 Agent 的交互层，所有人和所有 Agent 都从这里进；Knowledge Graph 负责让 AI 真正"看懂"流程、数据和决策怎么连起来的。

为什么要把这四件事一起讲？因为 AI Agent 不是"某个孤立系统里的智能模块"，它必须能跨 ERP、CRM、HR、供应链甚至外部平台拿数据。它需要的是一张已经被治理过、被语义连接过、能被信任的网，而不是几张孤岛之间的 ETL 接口。

## 对 CX 这条线意味着什么

Bain 这篇文章主要是给 CIO 看的，但落到 SAP CX 项目上其实有几个挺直接的推论。

一个是 Commerce、Sales Cloud、Service Cloud、Engagement Cloud 这些产品已经不能再当成"独立的客户体验应用"来讲了。它们正在变成 Joule + BDC + Knowledge Graph 这一层之上的"业务执行节点"。客户在 Commerce 下了一单，订单事件要进 BDC 被治理；Joule Agent 在 Service Cloud 里调一个工单的上下文，要从 Knowledge Graph 拿到这个客户在 Sales、Commerce、ERP 各处的全貌。

另一个是部署架构会变。过去几年 SAP CX 项目里"侧边扩展"是默认范式——客制逻辑放 BTP 上跑，CAP/Kyma 写应用。这套现在还成立，但它的角色变了：以前是"为了不污染 Commerce 内核"，现在是"为了把扩展变成可以被 Agent 调用的能力"。这两个目的写出来的代码不一样。

> Bain 原文里有一句直白的话："谁拥有交易引擎已经不再是唯一的战略问题，谁拥有 AI 系统所依赖的数据、业务上下文和编排层，才是新的战场。" 这句话翻译过来对实施侧的人是：以前你做完 SAP CX 项目，交付物是"上线了一个 Commerce + Sales 站点"；以后交付物里要多一项——"这套站点产生的事件、数据、流程是不是已经接进 BDC 和 Joule，能不能被 Agent 调用"。

## Clean core 这件事，被升级成了 AI 通行证

Bain 给 CIO 的建议里有一条值得单拎出来：Clean core 已经不是"技术规范"，而是"AI 价值的快速通道"。

这话听起来像 SAP 自己讲过几百次的口号。但 Bain 给的逻辑链条不一样：客制化越多、Shadow IT 越多的环境，数据越脏、流程越杂、语义越乱。AI Agent 在这种环境里要么调不通要么调错，跟你的模型多大没关系。所以 Clean core 在 AI 时代被重新定价了——它直接决定了你的 AI 项目能不能跑通。

这一点对中国出海企业的 IT 负责人特别值得想一想。很多在做海外业务的中国企业 IT 团队过去几年的常见动作是"先把功能做出来"，业务部门不停加需求，扩展层堆到看不懂。现在这种债是要还的——不是 SAP 收账，是 AI 跑不动了。

## 迁移路径变松了，但 AI 不是"减负魔法"

Bain 提到一个有意思的细节——SAP 自己在 Sapphire 上说，新一代 AI 工具能把 ERP 迁移工作量减半。

Bain 没否认这个数字，但它后面紧跟了一句话很关键："AI 可能减少交付动作的工时，但不会消除业务驱动的流程重设、组织变革、集成简化和数据修复。" 意思是 AI 能省的是"实施手活"，不是"业务设计活"。

他们的建议挺实在：让 SI 合作伙伴拿出具体证据，证明 AI 到底在哪一段、怎么省了时间或风险，能省多少，怎么衡量。这一点我觉得国内做 SAP 项目的客户应该开始问 SI 同样的问题——不要再听"AI 加持"这种笼统的话，要看 demo、看流程截图、看可量化的指标。

## 那个"4 月份悄悄改的 API 政策"

Bain 这篇文章里专门点了一段历史。2026 年 4 月，SAP 修订了 API 政策，要求 AI 驱动和 Agentic 接入模式必须经过 SAP 背书。SAP 的官方说法是"标准化保护，不是限制访问"。

Bain 给的判断是冷静的：随着企业平台供应商往"治理 AI 这一层"上走，伴随这种治理而来的商业条款，将会变成 TCO（总拥有成本）的一个重要组成部分。引用一位分析师在大会上的话——2026 年做出的平台选择，可能实质上决定了未来十年企业 AI 合同的条款。

这话翻译给做 SAP CX 选型的甲方听就是：你今天选哪个平台来跑你第一个跨厂商 Agent，等于在为你未来五到十年的 AI 账单签字。

## 我的判断是

Bain 这篇报告最有价值的地方不在结论——结论其实跟 Sapphire 主线讲过的差不多——而在它把"战场上移"这个抽象判断翻译成了 CIO 的待办清单：Clean core、迁移节奏、AI 成本可衡量、API 政策的长期含义、CIO 自己作为转型守门人的角色。

对中国做出海业务的 IT 团队来说，这五件事现在该排在做 SAP CX 路线图的优先级前面，而不是等明年再说。特别是 Clean core 和 API 政策这两件——前者决定你的 AI 项目能不能落地，后者决定你的 AI 账单怎么算。

Bain 在文末有一句话写得挺克制："企业还没完成的基础工作——干净的数据、标准化的流程、清晰的架构决策——决定了 AI 价值能不能兑现。" 这句话不浪漫，但它是 SAP CX 项目下一阶段的真实剧本。
