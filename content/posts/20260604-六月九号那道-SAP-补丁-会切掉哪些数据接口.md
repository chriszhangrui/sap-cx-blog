六月九号，下周一。

这一天 SAP 会推一个安全补丁出去。补丁本身并不耀眼，几乎不会出现在任何 Sapphire 主题演讲的录像里。但它会安静地把一类接口给关掉——具体说，是那些走 ODP-RFC 从 BW/4HANA 抽数据出去的链路。

SAP Note 编号 3255746。

如果你是甲方负责数据集成的，或者是一家做跨境电商的 IT 总监，这条 Note 的名字你可能从来没看见过。但很可能你某条夜跑的批处理、某条把销售订单同步到 Snowflake 的管道、或者某个挂在外面的 BI 看板，正是从这条接口里抽数据的。

补丁上线的那一刻，它就会开始挡。

## 先把背景捋一下

今年四月，SAP 发布了新版 API Policy，编号 v.4.2026a。一共两页，但行业里炸开了锅。

最大的争议条款叫 §2.2.2——简单讲就是：自主或生成式 AI 规划、调用、执行 API 序列的场景，原则上要走 SAP 认可的路径。这一条直接覆盖到 Salesforce 的 Agentforce、微软的 Copilot、ServiceNow、Workday Illuminate、Celonis 这些第三方 AI 平台对 SAP 的访问。

DSAG（德国 SAP 用户组）当时第一时间出来表态。主席 Jens Hungershausen 的原话很直白：**"问题在于，到底哪些接口被这条政策覆盖了？"** 董事会成员 Michael Bloch 直接说，SAP Business Accelerator Hub 的合同地位"无法接受"。

Forrester 也下场。给 CIO 的建议很直接——把这事顶回去（push back），别接受这种模糊状态。

这就是过去两个月的舆论场。SAP 给出的回应是 CTO Philipp Herzig 在 Sapphire 2026 上口头表态："政策不是要堵死，是要让 Agent 走可信的路。"——但客户最关心的那个问题，SAP 自己 FAQ 第 49 条写得很清楚：**没有也不会发布一份"哪些用法合规、哪些不合规"的清单。**

## 问题是这样的：你拿不到答案，但补丁已经在路上

六月二号，一位德国的 SAP 顾问 Marian Zeis（他是 The Register 那篇 AI 条款报道里被引用的几位独立顾问之一）发了一篇博客，把这件事的实操层面捅破了一层窗户纸。

他的判断是：**没有人能给你一个干净的"是"或"否"。但你可以拿着证据走进和 SAP 的对话，而不是空着手。**

于是他做了件挺反常的事——开源了一个工具：sap-api-policy-evidence。一个跑在 Claude Code/Cursor/Codex 里的 skill，背后挂着五个 SAP MCP server——SAP Business Accelerator Hub、SAP Notes、Road Map Explorer、SAP Docs、还有他自己的 ARC-1（一个只读的 ADT MCP）。

你把一个真实的接口场景描述喂进去，它返回的不是一个判决，而是一份带证据的评估表：

- 一个状态标签：Likely aligned / Likely not aligned / Needs SAP confirmation / Not assessable
- 一个置信度：high / medium / low
- 一张证据表：每条来源、说了什么、权威程度、抓取时间
- 残余风险、还需要补什么信息、要去问 SAP 哪些问题

最关键的一句话——他自己写的："任何工具如果敢给你印一个 COMPLIANT 或 NOT COMPLIANT 出来，那是骗你。"

## 同一个 Sales Order API，两种结局

这部分是整篇博客最有意思的地方。Zeis 用同一个接口——API_SALES_ORDER_SRV——跑了两次评估，结果一个是绿灯，一个是红灯。

**场景一：**

某家公司用 Boomi 中间件，把 Salesforce 里的销售订单同步到 S/4HANA Cloud。每天大约 500 单，走 OData V2 + OAuth 2.0。结果：**Likely aligned，置信度 medium。**

逻辑是这样：API_SALES_ORDER_SRV 在 SAP Business Accelerator Hub 上是 Published 状态，没被废弃；500 单/天属于"有界的运营性使用"，不是 bulk extraction；不是 AI Agent 在规划调用顺序——是一个确定性的中间件流程。所以 API 表面合规，使用模式也合规。

**场景二：**

同样调 API_SALES_ORDER_SRV，同样的鉴权方式，同样的频次。但调它的是一个第三方自主 AI Agent，而且走的是一个自建的 MCP Gateway。结果：**Likely not aligned，置信度 high。**

触发的是 §2.2.2(a)——"自主 AI Agent 通过自建网关规划和执行读写调用序列"。endorsed 的路径是什么？SAP Integration Suite 上的 MCP Gateway，或者 Joule 加 Agent Gateway。SAP 想让 Agent 进 SAP，但必须从 SAP 自己的那扇门走。

这个对比真正的意思是：API Policy 看的从来不是 API 本身，是用法。你用一个 API 调 500 次或者 5000 次，没问题；你让一个会"思考"的 Agent 去自由地调它——同样的 5000 次，性质就变了。

## 为什么这事对中国出海企业很重要

先说一组直接的：

- 你的全球数据仓库里如果在用 ODP-RFC 抽 BW/4HANA 数据——六月九号之后大概率会断。endorsed 的替代是 SAP Business Data Cloud 的 Delta Sharing（包括 BDC Connect for Snowflake）、ODP-OData，或者 SLT。
- 你的海外子公司用了某个第三方 AI Agent 平台（Agentforce、Copilot、ServiceNow Now Assist 之类）连进 SAP——如果是只读的开发助手，安全；如果是会自主规划业务调用顺序的，§2.2.2 这条要看。
- RPA 自动化机器人——FAQ Q40 给了豁免，确定性 RPA 不在 §2.2.2 范围。但如果 RPA 后面挂了一个 LLM 在做决策路径选择，就要重新评估。

这里有一件事跨境企业容易踩坑——欧洲那边对这套政策的反弹声很大，DSAG 会追着 SAP 要书面承诺。但中国出海企业的 SAP landscape 往往是混合的：总部在欧洲或者美国，海外子公司用 S/4HANA Cloud + 几个 SaaS LoB，本地业务可能还有一些 ECC 残留。

这种地理上的不对称，意味着你看到的"政策影响"和总部 IT 看到的可能不是同一回事。**建议在六月九号之前，做一遍自己的 SAP 接口盘点**——这件事 SAP 自己也提供了 Note 3439624 自评工具，ABAP Test Cockpit Cloud Readiness Check 也能跑一遍非释放对象的依赖。

## 真正值得讨论的是态度问题

SAP 的 FAQ 第 11 条和第 19 条里写了一句容易被忽略的话：对存量集成，SAP 想"先沟通，再限流"（dialogue first, not penalties）。意思是：六月九号补丁上线之后，SAP 不会立刻把所有违规调用全部 throttle 掉，会先找客户聊。

那个对话，迟早要发生。

真正的问题是：你是空着手走进那个会议，说"我们大概是合规的吧"——还是带着一份证据走进去，告诉 SAP："这是我们的接口 X，这是它在 API Hub 当天的状态截图，这是 Note 3255746 的相关条款，这是我们的实际使用频次和模式，请帮我们确认一下。"

这是两种完全不同的对话。

而 Zeis 这套开源工具——MIT 协议的 skill 加 Apache-2.0 的 MCP server——它最大的价值不是判决你合规不合规，而是把那张证据表自动收集好，让甲方 IT 能拿着它和 SAP 账户经理坐下来聊。

## SI 合作伙伴和 CX 项目，连带的一些新问题

做 CX 项目落地的，这两个月会感受到几个连锁反应。

第一，**中间件方案会被重新审视。** 过去几年很多 SAP CX 项目里——Sales Cloud V2 接 S/4HANA、Service Cloud 取 ERP 单据、Engagement Cloud 同步会员数据——大量用了第三方 iPaaS（Boomi、Mulesoft、自建 Kafka）。在 v.4.2026a 之下，这些方案如果调的都是 Published API、走标准 OAuth、没有 LLM 在中间做规划，基本仍然 OK。但那种"先把 SAP 数据全量同步到湖里，让上层 AI 任意取用"的架构——会撞墙。

第二，**Joule Studio 的 endorsed 地位会被进一步抬高。** 之前讲 Joule Studio，说它免费到 2026 年底，听起来像 SAP 在推广。但放在 API Policy 的语境下，Joule + Agent Gateway 是 SAP 给"AI Agent 进 SAP"指定的官方通道。这不只是产品推广，是合规路径。

第三，**BTP MCP Gateway 会成为 CX 集成项目的新标配。** SAP Integration Suite 上的 MCP Gateway 是 endorsed 的 Agent 接入点。中国出海企业如果在欧美子公司部署了第三方 AI Agent 平台，要把它们接进 SAP CX，未来一两年内推荐架构基本就是 MCP Gateway 这条路。

第四，**数据出 SAP 的官方路径，从 ODP-RFC 转向了 BDC Delta Sharing。** 这意味着你和 Snowflake/Databricks/BigQuery 的集成方式要重做。BDC Connect for Snowflake 这条线，SAP 5 月份刚和 Snowflake 联合宣布了 GA。Databricks 的合作也在路上。但要把现有 ODP-RFC 管道迁过去，是个工程项目，不是按个开关。

## 一句不是结论的结论

Zeis 在博客最后写了一句话，挺扎心：

> "说实话，我宁可不需要这套工具。如果 SAP 给出明确的指引，告诉客户哪些接口受影响，我们就不会被困在这种不确定的状态里。但在 SAP 改变之前，这是我能找到的最好的办法。"

六月九号还有 5 天。这之后，那道补丁会上线。会有些链路安静地断掉，会有些项目临时停下来开会。

真正的问题不是补丁。补丁是结果。真正的问题是 SAP 的 AI 战略已经选了一条路——把 Agent 调用 SAP 数据的入口收敛到自己的 Joule Studio 和 BTP MCP Gateway 上。这条路对甲方好不好、对生态好不好，是另外一回事。但路已经选定了。

现在每家用 SAP 的企业要回答的，是怎么在这条路上把自己的接口、自己的 AI 投资、自己的数据集成方案，重新摆一遍。
