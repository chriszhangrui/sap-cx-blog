SAP 把客服 AI Agent 这块地，正式向 AWS 开了一道门。Sapphire 2026 上 AWS 那篇博客里塞了不少东西，但真正值得嚼一嚼的，是 Amazon Connect Customer 要进 SAP Service Cloud 和 ESM 这一条。

这件事看起来只是又一个跨云合作公告，实际上对落地项目的影响比想象中大。

## 这次到底改了什么

AWS 的原话是：Amazon Connect Customer 是 Amazon Connect 一族里的"agentic AI 解决方案"，会和 SAP Service Cloud、SAP Enterprise Service Management（ESM）做集成，让企业可以"在所有渠道上规模化提供 agentic 客户体验"。

翻译一下：原本 Amazon Connect 是 AWS 自家做的云联络中心，语音、短信、聊天通通能接，AI 路由、转写、情绪识别全栈打包。现在它要把这套能力向前再推一步，让 Agent 不只接电话，还能直接调到 SAP 后台，把工单、客户主数据、订单、设备记录全拉过来用。Service Cloud 管的是企业对外的客户服务这一段，ESM 管的是企业内部跨部门的服务请求——比如员工开个 IT 工单、HR 自助、财务问询。两个场景一锅端。

配套还有一个细节：MCP 协议在 Amazon Bedrock AgentCore 上落地，意味着 AI Agent 通过 SAP Integration Suite 能"以协议驱动的方式安全访问 SAP 业务数据"。这句话其实是技术上的关键。MCP 是 Anthropic 推出的那套 Model Context Protocol，SAP 这边一直在 push 自家的 Joule Studio 用 MCP 做 Agent 间通信，AWS 这次在 Bedrock 上把它接住了。

> 这不是一个简单的"集成"公告。SAP 把客服 Agent 的"大脑"留给了自己（Joule、Knowledge Graph、Service Cloud 的业务规则），把"嘴和耳朵"——也就是渠道接入与对话流——明确分给了 AWS。

## 为什么是这个时间点

把这个公告放回最近半年的时间线里看会更清楚。

5 月初 SAP 宣布选 Anthropic 当首选模型供应商，Joule 背后跑 Claude；几乎同期，SAP 又和 Parloa 合作把 Parloa 的 voice AI 塞进 Service Cloud——Parloa 是德国一家做 conversational AI 的初创，重心在企业客服语音。再往前一点，SAP 自己的 Service Cloud V2 已经把"Digital Service Agent"做成了 Joule 在客服侧的产品形态。

这一连串动作排在一起，会发现一个结论：客服这条线，SAP 不打算自己端到端做。它选了一种"骨架自营、肌肉外包"的路子。

- 业务上下文、数据、规则、合规这一层，SAP 自己控住
- 渠道接入（PSTN、SMS、IVR、WebRTC）和对话引擎，谁强用谁——AWS 一份、Parloa 一份、Anthropic 一份
- Agent 之间的协议层用 MCP，避免被任何一家锁死

这种打法跟 Salesforce 走的"Agentforce 全栈自建"路线是反过来的。Salesforce 倾向把对话引擎、Agent Builder、Service Cloud 全部捏在一只手里。SAP 显然意识到自己在 conversational AI 这一块没那么强，与其追着补，不如把自己最值钱的东西——ERP+CX 后台的业务上下文——抬高，剩下的让伙伴接。

## 落地项目里要看几个细节

公告归公告，做项目的人关心的是另外一些事。

**一是中国市场怎么处理。** Amazon Connect 在国内没有部署，SAP Service Cloud V2 中国节点本身也还在路上。中国出海企业如果总部在欧美用这套组合是顺的，但如果客服中心放在国内，就要留意数据出境和落地节点。做跨境电商或者全球品牌的中国卖家，这层架构对海外业务很值，对国内业务暂时用不上。

**二是和现存呼叫中心的兼容。** 大量 SAP 客户的客服已经在用 Genesys、Avaya、华为、Cisco 这些。Amazon Connect 进 Service Cloud 不会一夜替换掉它们，更可能是给"新建客服中心""并购整合"或"AI Agent 试点"这类项目一个新选项。在华跨国公司全球总部统一平台时，这是一条值得评估的新通道。

**三是 ESM 这一段被合在一起，意义被低估了。** SAP ESM 是去年才正式立项的产品线，定位是"企业内部 Service Cloud"——员工服务、跨部门工单、IT/HR/法务自助。ServiceNow 看见这条线一定不轻松。Amazon Connect 进来之后，员工自助语音助手这种用例直接就能跑起来，不再需要客户额外搭一层 IVR。

**四是 MCP 这步棋更值得看。** SAP 在 Sapphire 上反复强调"agent-to-agent interoperability"，这次 AWS 用 MCP 接住了，意味着 SAP 想做的"Agent 也能跨厂商对话"不是 PPT。下一步要看 ServiceNow、Salesforce 是否愿意进这个协议圈——目前看 ServiceNow 偏向自己的 ACP，Salesforce 在观望。

## 一些保留意见

看好之外，要泼一点冷水。

第一，Amazon Connect Customer 这个产品名是 AWS 在 Sapphire 一并端出来的新东西，目前能查到的细节非常少，commercial 模式、计费模型、是不是 Bedrock 模型用量另算，都没披露。"plan to integrate"的措辞也说明 GA 还有时间——SAP 公告里没给具体季度。落地周期我估计要到 2027 上半年。

第二，从客户视角看，这又多了一层供应商。原本是 SAP+SI，现在变成 SAP+AWS+SI，加上底下可能还跑着 Anthropic 的 Claude。出问题的时候责任边界谁来划。这一点，做过跨云项目的人都懂。

第三，Service Cloud V2 自身的成熟度。V2 比 V1 是重写，一些行业模板和深度集成还在补，AI Agent 跑在上面意味着对 V2 的依赖加深，迁移到 V2 的客户会更多，但 V1 还在跑的客户压力也更大。

回到最开头那句话：SAP 决定不一个人打这场仗。这是一个看上去保守、其实激进的选择。承认自己做不来对话引擎，把它分出去，反而能更专心做"Agent 的业务大脑"。客服 AI 这场仗，赢的人不一定是声音最大的那家，可能是后台数据最干净的那家。

至少 SAP 是这么赌的。
