做 Service Cloud 的项目，最容易被问的一句是："你们 V2 的 AI 接 Joule 没？"——多数人脑子里跟着这句话浮起来的画面，是网页右下角那个聊天小窗。

这个画面没错，但它是最不重要的一层。

Adobe 2025 那份调研里有句话被反复引用：78% 的服务负责人预期 AI 会在 18 个月内承担一半的支持互动。这话听着像是在说 Chatbot 接管半壁江山，但你要是真做过 Service Cloud V2 的实施，会发现一个反直觉的结论——客户面那一端 AI 撑死能解决的就是 FAQ、订单状态、密码重置。复杂 case 一冒头，机器人立刻把人甩给坐席。投入巨大，回报浮在表面。

真正的钱在另一头：坐席侧。分类、路由、优先级、回复辅助、知识库匹配——全是看不见的部分。SAP 自己 Q1 2026 的 release notes 里，所有 Joule for Service 的能力扩展也都集中在这一层。

这篇就拆这件事：Service Cloud V2 把 AI 放在坐席身后到底动了什么、哪些已经能上、哪些还在画饼。

## 从案例分类说起：AI 真正落地的第一步

每一张工单进系统都得打三个标签：分类（category）、优先级（priority）、关联产品（product）。坐席平均要花 2-3 分钟看完描述、判定、点选。一千张工单一个月，就是 30-50 个小时纯粹耗在 triage 这一步。

V2 上的自动分类做法是：模型读 case description，自动写这三个字段。

关键数字（来自 Spadoom 的实施数据，2025-2026）：

- Day 1 准确率 70-80%（前提：历史 case 分类规范）
- 2-3 个月后稳定在 90% 以上
- 模型从坐席的"修正动作"持续学习

但这套数字有个隐性条件——历史数据干净。如果你前几年的工单分类是坐席随手打的、同类问题被分到三五个不同类别，AI 学到的就是这种乱。所谓 garbage in garbage out 在这里特别露骨。

这也是为什么 SAP 在 V2 的 AI Configuration 模块里把"训练数据集筛选"做成强制步骤：你得明确告诉模型哪些 case 拿来训练、哪些排除。配置上长这样：

```
// AI Classification — Training Set Filter
Filter:    Status = Closed
           Resolution = Resolved
           Created > 2024-01-01
           Category != "Other / Misc"
Min Cases: 1000 per category
Exclude:   reopened cases, escalated cases
```

那条 `Min Cases: 1000 per category` 是硬门槛。每个类别少于 1000 张历史 case，AI 给出的标签随机性比规则路由还大。这是项目里最容易被忽略、上线后最容易翻车的一条。

## 智能路由：把 25-30% 的"误派"砍掉

规则路由的故事大家都熟：产品 A 派给团队 1，产品 B + 区域华东派给团队 2。这套逻辑在 case 量小的时候管用，case 量一上去问题立刻显形——队列积压不均、复杂问题落到新人手里、跨产品工单两个队列互踢。

V2 的智能路由换了底层思路：不是匹配规则，是匹配"过去类似 case 谁解决得快"。它要看三件事：

- 坐席的 skill profile（专长领域、认证、产品熟悉度）
- 当前队列负载
- 历史相似 case 的解决人和解决时长

能拿到的最直接收益是 reassignment 比率下降 25-30%——也就是工单被踢回去重派的次数变少。一张 case 每被重派一次，平均加 2-4 小时响应时间，多个 hand-off 还会让 CSAT 直接掉一档。

但这个能力被列在"Needs Investment"区，不是因为模型不行，是因为前置条件没人愿意做：你得先把每个坐席的 skill profile 真的填出来。多数实施里的 employee master data 只到岗位、班组、语言三个字段，做智能路由要的是"擅长退款类争议、不熟工业资产维保、对德语 case 处理慢"这种细颗粒度。

这一步直接决定智能路由的好坏。模型再聪明，输入是空的也跑不出来。

## Joule 回复建议：唯一一个坐席自己求着开的功能

很多 AI 功能上线第一周都遭抵触——分类被坐席嫌打错、路由被嫌"凭什么这单是我"。Joule 的回复建议是个例外。

逻辑很简单：坐席打开 case，Joule 读完 case 内容 + 历史相似 case 的解决记录 + 关联知识库文档，给出一份草稿。坐席改、加细节、调语气、发出去。起点不再是空白对话框。

实测下来起草时间砍 30-40%。这个数字本身不算最惊人，最惊人的是采纳率——一周以内几乎所有坐席都会主动开启它，包括最初拒绝的人。原因也简单：从空白页开始写邮件比改稿子累多了，AI 接管那部分纯重复的开头/结构/客套，省下来的注意力可以放在判断和措辞上。

这个能力对 Service Cloud V2 的项目方有一个实际意义：在 AI 推广中"找一个第一周就能让坐席感受到价值"的功能，几乎只有这个。先开它，再开别的。顺序不能错——先开分类，坐席会觉得"AI 在监督我"；先开 Joule 建议，坐席会觉得"AI 在帮我"。同样的产品，心理认知完全不同。

## 知识库这条线的双向流：推荐 + 回写

这条是被低估的。多数 Service Cloud V2 项目把知识库当作"建一次、放那儿、希望坐席用"——结果就是文档越来越旧、半年无人维护、坐席宁愿自己 Google。

V2 的 KB 流是双向的。

**正向（推荐）**：每打开一张 case，相关 KB 文档自动出现在右边面板。坐席不用搜，不用记位置。这个对新坐席尤其重要——上岗前两周本来就是知识焦虑期，旁边像有个老带新。

**反向（回写）**：case 解决后，AI 分析 resolution 文本，做两件事——一是建议是否需要新增一篇 KB 文章覆盖这种问题，二是标记现有 KB 中"已经被新 resolution 推翻"的过时条目。

反向回写在"Needs Investment"档，原因不是技术问题，是流程问题——AI 给出的"建议新增"列表如果没人审核就直接进 KB，质量会迅速崩盘。最常见的失败模式：AI 把同一类问题的不同表述识别成不同文章，KB 里很快冒出 30 篇近似文档，坐席反而更难找。

所以这步的关键是托一个轻量级 review 流：knowledge manager 每周花 1-2 小时过 AI 建议、批准、合并。没有这个角色，KB enrichment 是个反向工程。

## 情感分析：分两档看，不要混用

"AI 能识别客户情绪"这事在 demo 里讲得很顺，落地要拆开看。

**二元情感（正向/负向）**是产线可用的。来一份措辞激烈的邮件，AI 标记 negative，结合客户分级（如 Strategic Account）自动提优先级。这个判断粗糙但稳，不会经常误判。

**细粒度情感**——讽刺、被动攻击、隐含不满——目前不行。一句"非常感谢你们这么及时的响应"可能是真感谢也可能是阴阳怪气，模型判断不出。如果有人在 demo 里给你看"AI 检测到客户在反讽"这种功能并说"已经稳定上线"，让他给三个生产案例参考。多半给不出。

实时语音分析（电话进线时同步分析坐席-客户对话情绪）也在 preview，目前只对极少数语言、极理想的录音条件起作用。出海企业里能用上的场景非常窄。

## 四个月落地节奏：分类 → 坐席辅助 → 路由

项目里最容易出问题的不是单个能力，而是开启顺序。一次性把七个能力全打开的项目，几乎都翻车——AI 反馈互相干扰、坐席接受不了同时被多个机器人"管"、KPI 评估失控。

稳妥的节奏是：

- **第 1-2 周**：历史数据审计。把 case classification 的一致性、KB 完整度、路由规则质量过一遍。这一步多数团队会发现自己数据质量并没有想象中那么好。
- **第 1 个月**：开自动分类。最低风险、最快产出。让坐席在过程中纠错，模型自己迭代。
- **第 2-3 个月**：开 Joule 回复建议 + KB 推荐。坐席侧采纳率最高，给整个 AI 项目积累正向反馈。
- **第 4 个月以后**：上智能路由。结构性收益最大但前置工作最多——skill profile 必须先到位。

这个节奏不是 best practice 文档抄来的，是项目踩出来的——每一步省下来的代价都比看起来大。

## 什么样的项目适合现在就做

Service Cloud V2 + AI 这套组合，落地条件比 demo 里讲的苛刻得多。能不能上，可以拿三件事去对：

- **历史 case 量级**：每个分类至少 1000 张已关闭 case。低于这个数，等数据积累再说。
- **KB 完整度**：至少每个产品/服务有 30+ 篇可用文档。空 KB 启动 AI 推荐没意义。
- **有人能维护**：knowledge manager 这个角色得有，每周愿意花几小时审 AI 建议。没有就别开 KB enrichment。

满足这三条，先开分类 + Joule 建议两个，半年内能看到坐席侧的 AHT 和 CSAT 双向改善。智能路由可以放第二阶段——它的 ROI 最大，但要等 skill profile 先建好。

不满足的，建议先做"准备工作"项目：补 case 数据、清理分类、建知识库，再谈 AI。这话说出来不性感，但比上线后翻车再回滚省成本。

## 写在后面

Service Cloud V2 这一波 AI 改造，本质上是把客服系统的注意力从"客户侧那个聊天框"重新拉回"坐席每天卡住的几步"。Chatbot 不是没用，是过去几年被估值过高。真正撑得起 ROI 那部分一直在后台。

对在华外资的呼叫中心、做跨境 B2B 售后的出海企业、海外子公司分布广的跨国制造商——Service Cloud V2 上 Joule 是一条可以走的路。前提是把数据先理清楚。

对纯内贸国内品牌：Service Cloud V2 没有国内数据中心，目前不是选项。这点不绕。
