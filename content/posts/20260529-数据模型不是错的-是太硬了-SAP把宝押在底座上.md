今天看到一条消息值得聊聊。CX Today 上周登了一篇文章，标题就是冲着 CRM 圈来的——《你的客户数据模型不是错的，是太硬，没法反映客户真实的行为方式》。这话乍一听像是又一篇方法论唠叨，但里面那两个数字让我停了一下：CRM 数据每年自然衰减 34%，英国企业平均跑 796 个应用却只有 33% 互通。看到这两个数我没忍住把全文读完，越读越觉得，这其实是在替 SAP 这两年押在 BDC、Engagement Cloud 事件总线、Sales Cloud V2 上的那条路线背书。

说白了就是，过去十几年我们做 CRM 项目的那套思路——把客户拍扁成"潜客→线索→商机→成交→续约"五个阶段，再加几十个固定字段——这套从工具角度没问题，从客户角度全是错位。原文那句话讲得很狠：CRM 是为了"追踪工作"而设计的，不是为了反映"客户怎么动"的。中间差着一个时代。

## 问题一：固定字段把动态客户压扁了

原文举了个特别贴切的例子。一个客户在你网站上点了三次定价页，看了帮助文档，开始填表单又中途放弃，然后联系了客服。一个传统 CRM 能把这五件事都记下来——但记下来等于看懂了吗？这是购买意图？是内部决策卡住了？还是单纯产品没看懂？

事件都在，故事不在。这就是僵化数据模型最致命的地方——它能存"事实"，存不下"含义"。我接触过的客户里，绝大部分单一客户视图项目最后都卡在这一关。把记录去重，把字段标准化，把数据治理流程跑起来——客户档案是漂亮了，决策依然慢半拍。

> **CORE INSIGHT**
> "history is for reporting. behavior is for decisions."
> 历史是给报表看的，行为才是用来做决策的。模型把客户冻在上周的样子，下一步动作就一定迟到。

这个分野其实早就该划清了。SAP 这两年的产品架构动作，仔细看下来，差不多就是按这条线在拆——把"分析层"和"决策层"分开，BDC 管前者，CDP 加 Engagement Cloud 的事件总线管后者。Sapphire 上喊的 Autonomous Enterprise 也好，Joule Agent 也好，其实底下扛的就是这个动作。

## 问题二：身份散在 796 个应用里

前面那个数字——796 个应用、33% 集成——值得多看一眼。这不是某家奇葩客户的特例，是英国企业平均水平。一个客户的邮箱在营销云里、设备 ID 在电商前端、loyalty ID 在会员系统、客服工单里写的是手机号——这四块拼不起来，CRM 里那条记录就只是一块碎片。

原文说，传统模型有个隐含假设——一个标识符就够了。现实是，客户是一串标识符的轨迹。所以身份解析这一步必须 deterministic（确定性匹配，比如手机/邮箱/loyalty 号）和 probabilistic（概率匹配，比如设备指纹+行为特征）两种方法混合用，而且要把"什么时候用确定、什么时候用概率"这条治理线明说清楚。

这件事 SAP CDC（Customer Data Cloud，原 Gigya）那一层其实有底子——它就是干身份的。但 CDC 之后还要把同意状态、loyalty 数据、行为流推到 Engagement Cloud，整条画像才接得起来。以前讲 Emarsys 改名 Engagement Cloud 那篇文章里说过，事件总线开放才是它真正的产品分水岭。把这两条线连起来看，"动态客户画像"才不是一句产品话术。

## 问题三：仓库不是为毫秒级决策设计的

这一点原文讲得很硬：数据仓库是给 BI 用的，不是给毫秒级决策用的。两件事的设计目标根本不一样。BI 要的是历史完整、维度丰富、查询灵活；决策要的是低延迟、流式处理、状态可活化。把它们塞进同一个引擎，BI 跑不快，决策跑不动。

所以原文给的方法论里有一条特别明确——live layer 和 analytical layer 必须分开。这两层共享数据，但绝对不共享性能预期。落到 SAP 的产品图上，BDC 的 Data Products 模型加上零拷贝是在解决"共享但不复制"，而真正的实时活化层还是 CDP+Engagement Cloud 这条路径。Snowflake 和 AWS 的零拷贝合作不是为了让 BDC 替代决策层，是让 BDC 和决策层之间不用再搬数据。

这点我觉得是国内一些做 SAP 项目的同行容易混的——把 BDC 当成"超级 CDP"，结果发现做实时个性化跑不动。BDC 那一层是分析底座，是给 Joule、给 Agent 喂上下文的；客户旅程那一边的实时事件还得靠 CDP 加 Engagement Cloud 的事件流。两条腿走路，不是一条腿。

## 那 Sales Cloud V2 算什么

原文有句话意味深长：CRM 还是有用的，只是它的活变了。CRM 应该支撑"前线执行"——客户经理看账户、客服处理工单、销售推进商机；而更广的客户数据层应该承担"理解"——身份连续、行为上下文、编排决策。这一段读到这里我直接想到了 Sales Cloud V2 的方向——它已经在往"事件驱动+AI 嵌入入口"那边走了，去年那篇讲 V2 在报价单入口装 GenAI 的文章里就有苗头。

但 V2 自己不存"客户全貌"——它存的是商机、活动、客户对应关系这些"工作记录"。客户全貌的活越来越多落在 BDC + CDP + Engagement Cloud 三件套上，V2 调用这一层的画像做下一步动作。这个分工其实更合理。CRM 不该想着自己当"单一客户视图"，那是上一代的思路。

## 出海企业的现实问题

这话题对中国出海品牌特别贴。一家做跨境 DTC 的客户跟我聊过——他们用的是国内自研 CRM 加海外 Klaviyo 加 Shopify，再加一个香港的客服系统。三块全是孤岛，海外活跃度怎么回流到国内复购预测，他们做了两年没做通。原文讲的那个 796 / 33% 在他们这儿是真实场景。

中国出海品牌做欧美市场扩张，或者做东南亚多国分销，最后绕不开的就是这个问题——海外行为数据是流的，国内 CRM 是档案的；想做一个能在迪拜门店扫码、在 TikTok Shop 触达、在 Shopify 复购的统一旅程，传统 CRM 这个底子根本撑不起来。这也是 SAP 在中国跑 Engagement Cloud 加 Commerce Cloud 加 BDC 这套组合的客户，几乎全是有海外业务的——纯内贸品牌买不到 SAP 的多数 CX 产品（除了 Commerce Cloud 有国内数据中心），这是一个硬约束。

## AI Agent 把这件事的赌注又抬了一倍

原文最后一段提了一句：实时放大错误的速度也很快。这句话现在听着就是给 AI Agent 量身定做的警告。Sapphire 上 SAP 一口气放了 200 多个 Agent，但凡数据模型还是僵化的、画像还是上周的、事件还没拼成时间轴的，Agent 跑得越快错得越快。

这就是为什么 SAP 这两年在数据底座上的投入比应用层还大——Reltio 收了，Dremio 收了，BDC 重新挂牌，Knowledge Graph 又拿出来讲——本质都是在垫地基。Agent 想真跑起来，前提是底下有一个能反映客户真实运动的数据层。否则就是把上一代 CRM 的"polite wrongness"（彬彬有礼地错着）用 AI 加速一遍。

> **MY TAKE**
> 我的判断是，SAP 这两年讲 Autonomous Enterprise，应用层那批 Agent 是表面文章；底下从 BDC 到 Engagement Cloud 事件总线、再到 CDC 身份层这条改造，才是真正决定 SAP CX 接下来三年走得有多快的关键。CRM 项目接下来选型的核心问题，不是"功能清单覆盖了多少"，而是"这套底座能不能让我的客户画像跟着客户一起动"。
